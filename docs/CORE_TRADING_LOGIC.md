# Ядро торговой логики

**Статус: нормативный документ.** Здесь записано, как система обязана торговать. Это
не описание текущего кода и не отчёт — это требование к коду. Расхождение кода с этим
документом является багом кода, а не устареванием документа.

Менять правила отсюда можно только отдельным коммитом, который меняет **сначала этот
файл**, и только по прямой просьбе владельца. Аудит, ревью, рефакторинг, «защитная»
проверка и починка другого бага такого права не дают.

---

## 1. Суть в пяти строках

1. **Мониторинг** — стратегия на бумаге. За минуту до закрытия (**T-1**) он сам решает
   выход и вход по списку наблюдения и своей позиции и записывает их в журнал.
2. Ни брокеры, ни их позиции, ни автоторговля, ни её флаги на мониторинг **не влияют**.
   Никогда.
3. **Автоторговля** — исполнитель сигналов мониторинга, и только при включённом общем
   переключателе. Выход мониторинга продаёт у брокера **всё**; вход мониторинга
   покупается только в **пустой** счёт.
4. Брокеры исполняются **отдельно и независимо**: состояние, ошибка, таймаут или запрет
   у одного не влияют на сделку другого.
5. Всё решённое и исполненное попадает в журнал **один раз и точно**.

Всё остальное в этом файле — расшифровка этих строк и перечень того, что считается их
нарушением.

## 2. Термины

| Термин | Значение |
|---|---|
| **IBS** | `(Close − Low) / (High − Low)` по текущему дневному бару, доля в `[0, 1]` |
| **T-11** | момент за 11 минут до официального закрытия сессии |
| **T-1** | момент за 1 минуту до официального закрытия сессии |
| **Мониторинг** | стратегия: список наблюдения, пороги, своя позиция и свои решения на T-1 |
| **Позиция мониторинга** | открытая строка журнала, не тестовая и не скрытая. Не больше одной |
| **Автоторговля** | исполнение сигналов мониторинга у брокеров |
| **Общий переключатель** | `autoTrading.enabled` — «Автоторговля включена». Выключен — автоторговли нет |
| **Флаги брокера** | `brokers.<имя>.enabled` / `allowNewEntries` / `allowExits`; действуют только при включённом общем переключателе |
| **Книга брокера** | позиции, которые брокер сам показывает на счёте сейчас |
| **Остаток** | любая бумага в книге брокера: куплена автоторговлей, руками, другой стратегией — неважно |
| **Очистка счёта** | продажа всех остатков брокера по рынку на выходе мониторинга |
| **Журнал** | таблица `positions`: строка = позиция мониторинга плюс нога каждого брокера |
| **Нога брокера (leg)** | что именно этот брокер исполнил по позиции: количество, цены входа и выхода, id его заявок |
| **Контур брокера** | всё, что принадлежит одному брокеру: флаги, авторизация, книга, заявки, нога, размер позиции, дедлайн его заявки |

## 3. Два слоя: мониторинг и автоторговля

Это главный раздел. Всё ниже ему подчиняется.

### 3.1. Мониторинг

- Держит **не больше одной** позиции — позицию мониторинга.
- На T-1, в таком порядке:
  1. **Выход.** Если позиция есть и IBS её тикера `> highIBS`, мониторинг закрывает её:
     строка журнала закрывается ценой и IBS этого чтения T-1.
  2. **Вход.** Если позиции нет (или она только что закрыта), мониторинг входит в тикер
     из списка наблюдения с самым низким IBS строго ниже `lowIBS`: в журнале
     открывается новая строка с ценой и IBS этого чтения T-1.
  Выход и новый вход в одном цикле — штатный исход, как в бэктесте.
- Котировки нужны только по списку наблюдения и по тикеру своей позиции — даже если его
  убрали из списка наблюдения: выход оценивается всегда.
- Мониторинг **не читает и не учитывает**: книги брокеров, открытые заявки, здоровье
  токенов, общий переключатель и флаги брокеров, сверку с брокерами, исход заявок.
  Решение мониторинга одинаково при включённой и выключенной автоторговле.
- Журнал не читается — мониторинг в этом цикле ничего не решает (`journal_unavailable`)
  и говорит об этом вслух. Запись решения не удалась — решения нет: мониторинг остался
  в прежнем состоянии, автоторговля по нему ничего не делает, ошибка — громкая.
- Решения мониторинга принимаются **только на T-1**. Кнопки «исполнить сейчас» нет:
  решение в другое время — это уже другая стратегия.

### 3.2. Автоторговля

- **Общий переключатель выключен — автоторговли нет.** T-1 не трогает брокеров вообще:
  ни решений по брокерам, ни заявок, ни продажи остатков. В отчёте одна строка
  «Автоторговля выключена». Включённые флаги брокера при этом ничего не значат.
- **Включена — следует только решению мониторинга этого цикла**, и только записанному в
  журнал. Своих решений по IBS у неё нет.
- **Мониторинг вышел** → каждый брокер (с `allowExits`) продаёт по рынку **всё, что
  есть в его книге**: тикер мониторинга и любые остатки, независимо от их IBS и
  происхождения. Затем ждёт подтверждения своих продаж и пустой книги.
- **Мониторинг вошёл** → каждый брокер (с `allowNewEntries`) покупает этот тикер,
  **только если его книга прочитана и пуста**. Есть остаток — вход у этого брокера
  пропускается (`broker_not_flat`, с перечнем остатков). Книга не читается —
  `broker_positions_unavailable`.
- **Выход и вход в одном цикле** → у каждого брокера своя цепочка: продал всё →
  дождался подтверждения и пустой книги → купил. Не дождался в пределах минуты — не
  покупает (`sells_not_settled`).
- **Сигнала мониторинга нет** → заявок нет. Остатки между выходами мониторинга никто не
  трогает — ни по IBS, ни по времени.
- **Вход посреди позиции не догоняется.** Включили автоторговлю, когда мониторинг уже
  держит X, — X не покупается; брокер ждёт следующего входа мониторинга.
- **Неудачная покупка не повторяется** в следующих циклах: брокер ждёт следующего входа.
- **Выключили, когда у брокера есть бумаги** — они не продаются: выключенная
  автоторговля значит, что владелец торгует сам.
- Неудачная продажа оставляет остаток у брокера: этот брокер не войдёт, пока следующий
  выход мониторинга не очистит счёт.

## 4. Инвариант A. Расписание

- **T-11 — только информация.** Обзор: IBS по наблюдаемым тикерам, позиция
  мониторинга, тикер, который был бы выбран, закройся сессия сейчас, и справка о
  бумагах в книгах брокеров. Заявок нет, журнал не меняется.
- **T-1 — единственная точка решений мониторинга и отправки заявок.** Значения IBS
  берутся заново, в этом же цикле. Предпросмотр T-11 решением не является.
- Расписание считается от **фактического закрытия из биржевого календаря**, включая
  сокращённые дни. Нечитаемый или просроченный календарь — день пропускается целиком с
  оповещением; вычисленное «наверное 16:00» не подставляется
  (`go/internal/scheduler/scheduler.go`, AUD-002).
- Окно тика: обзор уходит при `until ∈ [10, 11]`, решение — при `until ∈ [0, 1]`.
  Первый тик внутри окна забирает окно себе.
- Один день = одно исполнение. Гарантируется лизом `BeginT1Attempt` / `T1LeaseTTL`, а не
  тем, что «тик обычно один».

## 5. Инвариант B. Сигналы

- Пороги **строгие с обеих сторон**: вход `ibs < lowIBS`, выход `ibs > highIBS`.
  `ibs == lowIBS` входом **не является**.
- Значения по умолчанию: `lowIBS = 0.10`, `highIBS = 0.75`; пороги задаются на тикер и
  переопределяют глобальные. Тикер позиции, которого нет в списке наблюдения, берёт
  глобальные пороги.
- Единственная реализация сравнения — `ibs.IsEntrySignal` / `ibs.IsExitSignal`
  (`go/internal/ibs/ibs.go`). Ни мониторинг, ни UI не сравнивают IBS с порогом
  самостоятельно: живые пороги не имеют права разойтись с бэктестом.
- Нечисловой IBS (`NaN`, `Inf`, отсутствует) сигналом не является ни на вход, ни на
  выход. Это «нет данных», а не «нет сигнала на вход» и не «пора выходить».

## 6. Инвариант C. Выбор кандидата на вход

Среди **наблюдаемых** тикеров с корректной котировкой выбирается тот, у кого
**наименьший IBS, строго ниже `lowIBS`**. Если такого нет — входа нет, это штатный
исход, а не ошибка. Вход разрешён исключительно в наблюдаемый тикер.

## 7. Инвариант D. Независимость брокеров

Автоторговля покупает и продаёт у каждого брокера **отдельно**, чтобы брокеры не влияли
друг на друга.

### Персонально у каждого брокера

- флаги `enabled` / `allowNewEntries` / `allowExits`;
- статус авторизации и здоровья токена (`NEEDS_REAUTH`, `MISSING`);
- книга и её ошибка чтения;
- открытые (working) заявки и «занятые» ими тикеры;
- нога в журнале и трекеры заявок;
- очистка счёта, ожидание её подтверждения, размер покупки (от **его собственного**
  баланса), сама заявка и её ретраи.

### Общее — и это исчерпывающий список

- решение мониторинга этого цикла;
- рыночные данные: котировки, IBS, пороги, список наблюдения;
- общий переключатель автоторговли;
- биржевой календарь и время закрытия;
- дедлайн закрывающей минуты (общий момент времени, но расходуется параллельно);
- SQLite, которая сериализует записи сама.

### Следствия, обязательные к соблюдению

1. Брокеры исполняются **параллельно**, а не по очереди. Последовательный цикл отдавал
   второму брокеру остаток минуты только после того, как первый доработает свои таймауты
   и повторы (AUD-074).
2. Паника, таймаут, отказ авторизации или недоступность книги у одного брокера
   заканчиваются его собственным пропуском с причиной. Второй брокер продолжает и торгует.
3. Медленное чтение у одного брокера ограничено `T1ReadAttemptTimeout`, и
   `T1PlacementReserve` минуты неприкосновенен для отправки заявок. Зависший брокер не
   имеет права съесть окно здорового (CORE-02, `go/internal/live/deadline.go`).
4. Остаток у брокера X никогда не является основанием отказать во входе брокеру Y.
   Проверка «счёт пуст» смотрит только в книгу **своего** брокера.
5. Ни один брокер не ждёт чужую заявку: цепочка «продал → подтвердил → купил» у каждого
   своя (CORE-01 / AUD-043).

## 8. Инвариант E. Очистка счёта и повторный вход

- Выход мониторинга очищает счёт брокера **целиком**: продаётся всё количество каждого
  тикера из его книги.
- Тикер, по которому у брокера висит незавершённая заявка, в этом цикле не продаётся
  повторно (`symbol_order_in_flight`, AUD-072).
- После подтверждённых продаж лента позиций брокера ещё секунду-две может показывать
  проданные бумаги. Это отставание фида, а не позиция: второй SELL по ней не
  отправляется, вход ждёт пустую книгу в пределах бюджета минуты (AUD-071).
- **Повторный вход в тот же день разрешён** — после того как собственная очистка
  счёта этого брокера подтверждена исполнением и книга пуста. Брокер, у которого и так
  пусто, входит немедленно.

## 9. Инвариант F. Блокировки только адресные

Глобального «стоп-крана» в ядре нет. Любая проблема ограничивает ровно то, что она
реально делает опасным:

| Находка | Что блокирует | Что **не** блокирует |
|---|---|---|
| Журнал не читается | решение мониторинга этого цикла и заявки по нему | — |
| Книга брокера не читается | очистку и вход этого брокера | мониторинг, другого брокера |
| Working-заявка в тикере | новые заявки по **этому тикеру** у **этого** брокера (AUD-072) | другие тикеры, другого брокера |
| Открытые заявки брокера не читаются | вход этого брокера | его очистку, другого брокера |
| Отказ авторизации брокера | всё у этого брокера | мониторинг, другого брокера |
| Остаток у брокера | вход этого брокера | мониторинг, другого брокера |
| Нечитаемый календарь | торговые задания дня целиком | — |

## 10. Инвариант G. Бюджет закрывающей минуты

- Решение мониторинга принимается и записывается **до** любых обращений к брокерам и не
  ждёт их.
- Дедлайн цикла считается один раз в начале минуты: время закрытия ET минус
  `T1DeadlineSafetyMargin`.
- Первая попытка отправки идёт всегда, даже при малом остатке времени: пропустить её —
  гарантированно остаться без заявки.
- Повтор не начинается, если оставшегося времени меньше, чем занял прошлый заход.
- Отказ по исчерпанному дедлайну **сообщается** оператору. Молчание неотличимо от
  штатного «сигнала не было» и запрещено.

## 11. Инвариант H. Отсутствие дублей

- Один день — одно T-1 исполнение (лиз `BeginT1Attempt`).
- Одна позиция мониторинга: проверка «позиции нет» и вставка новой строки — одна
  транзакция.
- До отправки записывается намерение (`recordOrderIntent`) с `clientOrderID`;
  неопределённый ответ брокера проверяется запросом статуса, а не повторной отправкой.
- Уже существующий pending-трекер по паре (брокер, тикер, сторона) запрещает вторую
  заявку **этого** брокера.
- Невозможность прочитать журнал — это `journal_unavailable` и отказ от заявки, а не
  «значит, ничего не было».

Защита от дублей тоже подчиняется инварианту F: она обязана быть по-брокерной и
по-тикерной.

## 12. Инвариант I. Журнал: позиция мониторинга

Журнал — это учёт денег, а не отладочный лог. Он обязан отвечать на вопрос «что держит
мониторинг, по какому сигналу он вошёл и вышел, и что при этом исполнили брокеры» без
сверки с чем-либо ещё.

- **Таблица одна — `positions`.** Строка = позиция мониторинга: сигнал, который её
  открыл и закрыл, и рядом нога каждого брокера. Вторая таблица сделок и любая сверка
  журнала **с самим собой** запрещены.
- **Строку позиции открывает и закрывает только мониторинг** (сигналом на T-1) или
  оператор (ручные пути, инвариант L). Исполнения брокеров строку не открывают и не
  закрывают — они дописывают ногу.
- **Сигнальная часть строки:** `entry_date`, `entry_price`, `entry_ibs`, `exit_date`,
  `exit_price`, `exit_ibs`, `pnl_absolute`, `pnl_percent`, `holding_days`, `source`
  (`monitor`), `notes`, `is_test`, `is_hidden`. Цены и IBS — чтение T-1, на котором
  принято решение. PnL позиции считается **по ценам сигналов**.
- **Нога брокера** (`webull_*`, `rh_*`): `qty`, `entry_price`, `exit_price`,
  `entry_order_id`, `exit_order_id`. Нога — **факт исполнения**: сюда пишется то, что
  реально исполнил брокер, а не цена решения. Исполнение сигнальную часть не меняет.
- **Нога с `qty = 0` и без order id — «брокер не участвовал»**, штатное состояние
  (автоторговля выключена, вход пропущен, покупка не прошла), а не расхождение.
- **Остатки, которых нет ни в одной ноге, в журнал позиций не попадают.** Их продажа при
  очистке счёта — не сделка мониторинга: она остаётся в трекере заявки и в логе
  (`leftover_sold`).
- **Тестовые покупки** (`is_test = 1`) — отдельные строки, которые живут по исполнениям:
  открываются покупкой, закрываются, когда ноги проданы. Позицией мониторинга не
  являются.
- **Сверка с живыми книгами брокеров** (`liveConsistencyIssues`) — справочная. Она
  перечисляет, что лежит у брокеров, и не влияет ни на мониторинг, ни на решения
  автоторговли. В Telegram это нейтральная справка «у брокеров: …», а не
  предупреждение и не «наша позиция».

### Атомарность

Каждая операция журнала — «проверить и записать» в **одной транзакции**: открытие
позиции мониторинга, `AttachEntry`, `ExitLeg`, `ClosePosition`, `SplitPosition`,
`ClaimFillQty`.

Read-modify-write общей строки **запрещён**. Брокеры пишут ноги параллельно: тот, кто
прочитал строку раньше, а записал позже, восстанавливает уже обнулённую ногу соседа.

Порядок тоже часть контракта: сделка пишется **до** финального статуса трекера
(`finalizeTrackerStatus`). Ожидающий, который смотрит на статус трекера, не должен увидеть
`filled` без записи в журнале.

## 13. Инвариант J. Каждая заявка оставляет след

- **До отправки** пишется намерение (`recordOrderIntent`): строка `order_trackers` со
  статусом `submitting`, clientOrderID, тикером, стороной, брокером и торговой датой.
  Не записалось — **заявка не отправляется** (CORE-08).
- Попытка, которая заведомо не дошла до брокера, снимает своё намерение
  (`dropOrderIntent`), чтобы оно не висело как незавершённая заявка и не блокировало
  следующий вход.
- **Записывается факт, а не словарь брокера.** Если исполненное количество больше нуля,
  исполнение попадает в журнал даже под незнакомым статусом
  (`order_filled_under_unknown_status`).
- **Идемпотентность обязательна.** Одно исполнение может прийти дважды (опрос после
  перезапуска между записью сделки и фиксацией статуса трекера):
  - частичное исполнение списывается только в новой части — `ClaimFillQty` (CORE-04);
  - повторный вход с тем же order id и тем же количеством ничего не меняет (`AttachEntry`);
  - повторное исполнение выхода не переписывает записанную ногу.
- **Ноль — не цена.** Неподтверждённая цена исполнения оставляет поле `NULL` и помечает
  строку `fill_price_unconfirmed`. Пустая цена честнее выдуманной.
- **Ошибка записи журнала — громкая.** `local_trade_record_failed` /
  `local_trade_close_failed` / `journal_update_failed` плюс `raiseTrackerPersistBlock`:
  брокер, чью запись не удалось сохранить, дальше не торгует, **и только он** (инвариант F).
- **Фантомная заявка** (`terminal_absent`) удаляет строку, только если это строка самой
  заявки и вторая нога ничего не исполнила. Иначе чистится **своя** нога.

## 14. Инвариант K. Запись выхода — точная

1. **Выход мониторинга** закрывает строку на T-1, не дожидаясь брокеров:
   `status = closed`, `exit_date` (торговая дата `YYYY-MM-DD`), `exit_price` и `exit_ibs`
   чтения T-1, `pnl_absolute` и `pnl_percent` по ценам сигналов, `holding_days ≥ 1`.
   Ноги при этом не трогаются: бумаги у брокера ещё не проданы.
2. **Продажа брокера по тикеру позиции** дописывается в ногу этой строки — открытой или
   закрытой мониторингом в тот же торговый день: `qty` уменьшается на проданное,
   `exit_price` — фактическая цена исполнения, `exit_order_id` — заявка. Статус строки
   исполнение не меняет.
3. **Частичное исполнение** уменьшает ногу только на новую часть (CORE-04); остаток ноги
   остаётся видимым как непроданный.
4. **Продажа, которой нет ни в одной ноге** (остаток при очистке счёта, ручная бумага), —
   не выход позиции: она уходит в лог `leftover_sold` с количеством и ценой и не
   сопровождается тревогой.
5. Нога, которая так и осталась непроданной после выхода мониторинга, честно показывает
   бумаги у брокера; её продаст следующая очистка счёта.
6. **Проскальзывание** (`maxSlippageBps`) — порог **отчётности**, а не запрета: это
   рыночные заявки, исполнение обязано состояться. Отклонение цены исполнения от цены
   решения логируется и уходит в Telegram, но заявку не отменяет.

## 15. Инвариант L. Ручные пути не ломают учёт

Оператор — часть контура, поэтому ручные операции подчиняются тем же правилам.

- **Тестовая покупка** — реальные деньги у брокера, поэтому она в журнале, но с
  `is_test = 1`: вне статистики, вне страницы мониторинга и не позиция мониторинга.
- **Ручная продажа у брокера** (кнопка «Закрыть позицию» на странице брокера) дописывает
  ногу, но позицию мониторинга не закрывает: мониторинг выходит по своему сигналу.
- **Правка позиции (`PATCH`)** накладывается на **сохранённую строку**, а не на пустую.
  Пустой тикер отвергается.
- **Ручное закрытие позиции мониторинга (`POST /close`)** требует положительной
  `exitPrice`, подставляет торговую дату NYSE при пустой и проходит через ту же
  `ClosePosition`: закрыть дважды нельзя (409).
- **Правка журнала без браузера** — `go/cmd/closepos`: тот же `ClosePosition` из
  командной строки. Обязательные `-symbol` и `-dry` — страховка: сначала показать строку,
  потом писать. Своей SQL-правки журнала не существует ни в одном пути.
- **Ручное разрешение трекера** (`ResolveTracker`) обязано пройти тем же путём, что и
  автоматическое исполнение. Обязательный `note` и автор пишутся в лог.
- **Скрытые и тестовые строки** исключаются из витрин, но **никогда не удаляются** ради
  красивой статистики.

## 16. Отчёт T-1 и причины «сделки нет»

Отчёт T-1 состоит из двух частей, и они не смешиваются:

- **Мониторинг:** решение (выход / вход / держим / сигнала нет) с ценой и IBS, позиция
  мониторинга после цикла, качество котировок. Брокеры здесь не упоминаются.
- **Автоторговля:** «выключена» одной строкой — или по каждому брокеру, что отправлено
  и почему не отправлено.

Штатные причины мониторинга: `no_signal` · `lowest_ibs_signal` (вход) · `ibs_exit`
(выход) · `exit_threshold_not_reached` · `open_position_quote_unavailable` ·
`empty_symbol_universe` · `watchlist_unavailable` · `journal_unavailable`.

Штатные причины автоторговли (всегда **с именем брокера**): `autotrading_disabled` ·
`broker_disabled` · `entries_disabled` · `exits_disabled` · `NEEDS_REAUTH` · `MISSING` ·
`broker_positions_unavailable` · `broker_not_flat` · `sells_not_settled` ·
`symbol_order_in_flight` · `open_orders_unavailable` · `open_order_symbol_unknown` ·
`pending_tracker` · `pending_submission` · `tracker_persist_failed` ·
`journal_unavailable` · `broker_panic`.

Ни одна из них не является ошибкой системы и ни одна не должна расширяться на другого
брокера, другой тикер или на мониторинг. Пропущенная заявка без названной причины — баг.

## 17. Что считается багом (чек-лист ревью и аудита)

Изменение нельзя принимать, если оно:

1. делает решение мониторинга зависимым от книги брокера, его заявок, здоровья,
   общего переключателя или флагов автоторговли;
2. показывает остаток у брокера как позицию мониторинга, оценивает его выход по IBS или
   блокирует им решение мониторинга;
3. отправляет заявку или принимает решение по брокеру при выключенном общем
   переключателе;
4. продаёт остатки брокера без выхода мониторинга в этом цикле — или, наоборот, на
   выходе мониторинга оставляет у брокера что-либо непроданным без названной причины;
5. покупает у брокера, в книге которого что-то лежит;
6. догоняет вход мониторинга, пропущенный автоторговлей (включение посреди позиции,
   неудачная покупка);
7. вводит сравнение IBS с порогом мимо `ibs.IsEntrySignal` / `ibs.IsExitSignal` или
   делает порог нестрогим;
8. переносит решение с T-1 на T-11 или использует значения T-11 для решения;
9. делает исполнение брокеров последовательным или вводит общий барьер/мьютекс на
   отправку;
10. позволяет состоянию, ошибке, таймауту или флагу одного брокера изменить исход у
    другого;
11. расширяет блокировку с тикера на брокера, с брокера на систему или на мониторинг;
12. заставляет брокера ждать чужую заявку;
13. проглатывает пропуск молча — без причины, без имени брокера, без сообщения;
14. открывает или закрывает позицию мониторинга исполнением брокера, а не сигналом;
15. заводит вторую таблицу сделок или сверку журнала с самим собой;
16. пишет общую строку позиции через read-modify-write вместо одной транзакции;
17. отправляет заявку, намерение которой не удалось записать, или считает неудачную
    запись журнала «просто логом»;
18. записывает цену исполнения `0` вместо `NULL`;
19. допускает, что повторно пришедшее исполнение перепишет или задвоит записанную ногу.

Формулировки «на всякий случай», «чтобы точно не задвоилось», «пока не разберёмся» не
являются основанием ни для одного из пунктов выше. Правильная защита в этом проекте
всегда адресная.
