# Roadmap приведения Go-версии к паритету с React/Node

Итог полного аудита переписанного стека. Всего **~180 находок**. Детальные отчёты по областям — в этом же каталоге, ссылки в каждом разделе.

---

## Что это за документ

Старый стек: React (`src/`, ~46 000 строк TSX) + Node/Express (`server/`, ~14 500 строк).
Новый стек: Go (`go/internal/`, ~15 400 строк) + ванильный JS SPA (`go/web/js/app.js`, 3 341 строка).

Набор HTTP-роутов совпадает 1:1 по путям — расхождения не в том, каких эндпоинтов нет, а в том, что за ними происходит и что до них не дотягивается из интерфейса.

### Достоверность

Каждая находка ниже подтверждена чтением обеих реализаций с указанием строк. Отдельно отмечу, что проверка агентских выводов дала **5 ложных срабатываний** — они разобраны в приложении и в roadmap не попали.

Что проверено и оказалось **корректным портом** (это тоже результат, и он немаленький):

- пороги IBS (`ibs/ibs.go` ↔ `ibsSignals.js`) — строгие сравнения, те же дефолты;
- индикатор IBS (`indicators.go:130` ↔ `indicators.ts:169`) — включая обработку нулевого диапазона;
- **весь модуль метрик** (`metrics/metrics.go` ↔ `metrics.ts`) — формулы, константы (√252, 2 % безрисковая, 8 % рыночная), граничные случаи, имена полей JSON;
- подпись запросов к Webull (HMAC-SHA1) — побайтово эквивалентна Node;
- отсутствие XSS в SPA — проверено ~650 интерполяций и все 36 мест с `innerHTML`, экранирование сплошное;
- отсутствие path traversal, SSRF и SQL-инъекций;
- атомарный захват T-1 (`ClaimAggregateT1`) — корректная защита от двойного исполнения, переживает рестарт;
- инвариант дат: тесты Go одинаковы в UTC+13 и UTC−8, `go test -race` чист;
- сборка, `go vet` и все тесты — зелёные.

## Блок 0. Торговля и деньги — до возобновления автоторговли

Это то, что способно потерять деньги или остановить торговлю. Пока не закрыто — автоторговлю в бою включать нельзя.

Детали: [autotrade-manual.md](autotrade-manual.md)

### 0.1. Сделка пишется по факту отправки ордера, а не исполнения `A1`
`live/autotrade.go:340-358` вставляет записи в `broker_trades` и `trades` внутри `if res.Submitted`, где `Submitted` означает лишь «HTTP-запрос прошёл». Node (`autotrade.js:982`) создаёт запись **только** при статусе `filled`.
**Последствие:** отклонённый брокером ордер оставляет фантомную открытую позицию. `Evaluate()` видит `open != nil`, ветка входа больше не отрабатывает, ветка выхода продаёт то, чего нет. **Автоторговля встаёт намертво после первого отклонённого ордера.**

### 0.2. Цена сделки — котировка на момент решения, а не цена исполнения `A2`
`autotrade.go:353` пишет `entryPrice: quotePrice(ev, symbol)`. Node передаёт `tracker.fillPrice`, извлечённый из ответа брокера (`autotrade.js:1108-1122`). В Go `filled_price`/`filled_qty` не читаются нигде.
**Последствие:** весь P&L считается от цены, по которой сделки не было. При частичном исполнении неверно и количество.

### 0.3. Выход не записывает ни цену выхода, ни P&L `A3`
`autotrade.go:360-368` — `PatchTrade` только со `status` и `exitDate`. Сделки, закрытые автоторговлей, попадают в историю без финансового результата и **полностью выпадают** из статистики монитора (`app.js:810` фильтрует по `Number.isFinite(pnlPercent)`). Ручное закрытие P&L считает — данные в одной таблице разнородны.

### 0.4. Дробные акции округляются вверх в теле ордера `A4`
`webull_broker.go:75` — `fmt.Sprintf("%.0f", qty)` **всегда**, вне зависимости от `allowFractionalShares`. При этом расчёт количества дробные акции поддерживает (`sizing.go:216-220, 282`).
**Последствие:** позиция 1.73 акции при выходе превращается в приказ продать 2 — отказ брокера либо непреднамеренный шорт.

### 0.5. Отсутствие порога в конфиге вызывает немедленную ликвидацию `A6` + `A7`
`autotrade.go:201-202` — `cfg["lowIBS"].(float64)` при отсутствии ключа даёт `0.0` без ошибки, и этот явный ноль подавляет фолбэк в `evalWatch`. `highIBS = 0` превращает условие выхода в `ibs > 0`, истинное всегда → **любая открытая позиция продаётся на ближайшем T-1**. Симметрично `lowIBS = 0` — вход не происходит никогда.
Ключ может пропасть потому, что `Settings()` (`store/db.go:603-611`) использует `json.Unmarshal` в карту, а он **заменяет вложенный `autoTrading` целиком**, а не сливает с дефолтами. Node пересобирал `{...defaults.autoTrading, ...stored}` при каждом чтении (`settings.js:88-92`) и явно закрывал путь записи: `PATCH /api/settings` с ключом `autoTrading` возвращал 400 (`routes/settings.js:66-68`). В Go этот путь открыт.

### 0.6. `PATCH /api/autotrade/config` не валидирует ничего `A8`
`autotrade.go:34-44` — `for k, v := range updates { cur[k] = v }`. Node имел `sanitizeAutoTradingConfig` (`autotrade.js:493`): белый список полей, зажим `lowIBS`/`highIBS` в `[0,1]`, enum-проверки, удаление `dryRun`.
**Последствие:** `{"lowIBS": 5}` делает условие входа истинным для любого тикера — покупка на ближайшем T-1 без сигнала.

### 0.7. Автоторговля игнорирует персональные пороги тикеров `A5`
`autotrade.go:215` строит синтетический watch из глобального конфига. Монитор при этом читает настоящую запись watch (`telegram.go:111`), а Node использовал `getThresholdsForSymbol` в обеих ветках.
**Последствие:** монитор и автотрейдер расходятся в решении по одному тикеру — ровно тот рассинхрон, против которого в CLAUDE.md вводился единый `ibsSignals`.

### 0.8. При недоступной котировке Go торгует по вчерашнему бару `M1`
`live/telegram.go:376-390` — при неудаче запроса котировки IBS считается по последнему **дневному** бару и помечается `ok = true`. Node (`autotrade.js:571-592`) в этом случае ставит `ok: false` и **отказывается действовать**.
**Последствие:** сбой провайдера в момент T-1 приводит не к пропуску сигнала, а к реальному ордеру по устаревшим данным.

### 0.9. Универсум тикеров: объединение вместо пересечения `A13`
`configuredSymbols` (`autotrade.go:547-577`) складывает явный список и watch-тикеры. Node (`autotrade.js:528`) при `onlyFromTelegramWatches` брал **пересечение**.
**Последствие:** торговля инструментами, которые старая логика исключала.

### 0.10. `allowExits`/`allowNewEntries` при отсутствии ключа: Go включает, Node выключал `A14`
`autotrade.go:203-210` подставляет `true`. Node трактовал `undefined` как ложь. Для торгового контура направление отказа должно быть закрытым.

### 0.11. Ни одной `recover()` во всём Go-коде `A9`
Проверено: `rg "recover\(\)" go/internal` — пусто. Планировщик — единственная горутина с тикером 20 с (`scheduler.go:132-146`), из неё идут обращения к брокеру и разбор JSON с type assertion'ами; на каждый ордер поднимается своя горутина `trackerWheel`. `net/http` перехватывает панику только в горутине обработчика; паника в фоновой горутине **завершает процесс**. В библиотеке расчётов есть достижимая `panic()` (`indicators.go:132`).

### 0.12. Зависший трекер навсегда блокирует торговлю по тикеру `A10`
`ListPendingTrackers` (`live_persist.go:140`) не имеет ни срока жизни, ни предельного числа попыток. `trackerWheel` после 64 попыток молча выходит, не переведя трекер в финальный статус, а `Execute` (`autotrade.go:285`) при живом трекере отказывается торговать. Node всегда доводил трекер до финализации и удалял его.

### 0.13. Статус исполнения определяется поиском подстроки в сыром JSON `A11`
`webull_broker.go:92-95` — `strings.Contains(strings.ToUpper(raw), "FILLED")`. Поиск идёт по всему телу, **включая имена полей**: ответ Webull содержит `filled_quantity`/`filled_price`, что в верхнем регистре содержит `FILLED`. Условие истинно практически всегда. Плюс `PARTIAL_FILLED` засчитывается как полное исполнение. Node сравнивал точное значение поля со списком (`autotrade.js:806`).

### 0.14. Вложенный ответ брокера не разбирается `A12`
`webull_broker.go:205-215` не спускается в `data.orders[0]`. Node имел `extractOrderDetailPayload` плюс резервный поиск по `client_order_id` в списке ордеров (`autotrade.js:797, 1269`). Именно эту вложенность чинили последние коммиты на фронте.

### 0.15. Выход закрывает первую попавшуюся сделку монитора, возможно чужого тикера `A15`
`autotrade.go:363-368` берёт `OpenBrokerTrade(mon)` — первую запись со статусом `open` **без сверки тикера**.

### 0.16. Автопочинка рассинхрона monitor/broker не реализована `M2`
`live/monitor.go:84-95` — `Reconcile(apply)` вызывает `UpdatePositions()` (обновление позиций), а не применение предложенных действий, и возвращает `applied: true` независимо от результата. Понятия `proposedActions` в Go нет вовсе, все issue помечены `autoFixable: false`. Node применял автоприменимые действия и возвращал список (`monitorConsistency.js:242-265`).
Дополнительно: из трёх кодов в `blockingMismatchCodes` (`monitor.go:10-14`) `Consistency()` производит только один — предохранитель T-1 слабее, чем в Node, где кодов было около десяти.

### 0.17. `time_in_force` и `support_trading_session` захардкожены `A16`
`webull_broker.go:79-80`. При этом `supportTradingSession` **используется** для выбора источника покупательной способности (`sizing.go:129-137`): объём считается под ночную сессию, а ордер уходит с `CORE`.

## Блок 1. Корректность расчётов

Детали: [calc-backtest.md](calc-backtest.md), [metrics-and-api.md](metrics-and-api.md)

### 1.1. Системный дефект: явный ноль трактуется как «не задано» `C1`
`httpapi/helpers.go:52-63` подменяет дефолтами `lowIBS`, `highIBS`, `initialCapital`, `capitalUsage`, если пришёл `0`. В TypeScript ноль — полноценное значение.
Проверено: тот же приём встречается **в 17+ местах** — `single.go:51,55,59,63,115,141`, `options.go:34,37,40`, `clean.go:58`, `margin.go:66,70`, `bac4.go:33`. Это следствие того, что Go не различает отсутствие поля и нулевое значение при разборе JSON в структуру.
Самые тяжёлые проявления:

- **`capitalUsagePct: 0` означает «не вкладывать ничего» в TS и жёстко переопределён в «вкладывать 100 %» в Go** (`margin.go:65-68` против `margin-simulation.ts:56,75`). В маржинальной симуляции это разница между отсутствием риска и полной позицией.
- **`maintenanceMarginPct: 0`** даёт 1 % в TS (`clamp(0,1,95)`) и 25 % в Go — совершенно разные пороги ликвидации.
- **`riskFreeRate: 0`** — вполне осмысленный ввод для оценки опционов — подменяется ненулевым дефолтом (`options.go:34`).

**Фикс:** указатели или флаги «поле присутствовало» при разборе; отличать отсутствие от нуля.

### 1.2. Ошибка индекса в зонной логике EMA `C2`
Цикл по зонам продажи в `backtest/ema.go` обращается к неверному лоту после того, как более ранний лот удалён из среза. Дефект существует только в Go. Движок EMA — 579 строк, самый крупный в пакете, и он же практически не покрыт эталонами (см. блок 5).

### 1.3. Опционный движок мутирует контекст исходной сделки `C3`
`RunOptions`/`RunMultiOptions` работают с указателем на `Context` вызывающей стороны и меняют его на месте; TS всегда создаёт новый объект. Побочный эффект проявляется при повторных прогонах на одних и тех же данных.

### 1.4. `clean.go` переопределяет `maxHoldDays` вторым слоем `C4`
`clean.go` дополнительно подставляет значение из `RiskManagement`, если `Parameters.MaxHoldDays == 0` — двойное умолчание поверх уже описанного в 1.1.

### 1.5. Сплиты применяются автоматически на GET-запросе `API1`
`GET /api/datasets/{id}` (`server.go:373-382`) вызывает `adjustBarsIfNeeded`, который:
1. запускает эвристику `splits.Detect` (`splits/splits.go:75-99`) — гадание по разрыву цен;
2. **записывает** угаданные события в таблицу сплитов (`UpsertSplits`);
3. **необратимо переписывает** исторические цены и ставит `adjustedForSplits = true`.

Node применял сплиты только по явному `POST /apply-splits` и только из **подтверждённых пользователем** событий (`routes/datasets.js:254-284`); детектор в React (`ticker-data-processing.ts:17`) служил лишь подсказкой.
**Риск ложного срабатывания реален:** допуск ±3 % вокруг множителя 1.5 означает, что **обычный провал на −33 % за ночь** (отчётность, неудача испытаний, раскрытие мошенничества) распознаётся как сплит 1.5:1. Вся история цен до этой даты делится на 1.5, и каждый последующий бэктест и каждый расчёт IBS идут по искажённым данным. Исходные цены при этом не сохраняются.

### 1.6. Проверки целостности данных не перенесены `API2`
`evaluateDatasetPayloadIntegrity` / `evaluateOhlcMergeIntegrity` (387 + 165 строк в Node, с оповещением в Telegram) в Go-пути загрузки датасетов отсутствуют полностью.

### 1.7. `PUT /api/datasets/{id}` затирает поля вместо слияния `API3`
Отсутствующие в теле `companyName`/`tag`/`uploadDate` обнуляются. То же поведение у `handlePutSettings` (`server.go:328-336`).

### 1.8. `PUT`/`PATCH /api/splits/{symbol}` молча проглатывают ошибку разбора `API4`
Некорректное тело `PUT` приводит к `ReplaceSplits(symbol, [])` — **удалению всех сплитов тикера** с ответом 200 OK.

### 1.9. `GET /api/datasets/{id}/metadata` отдаёт весь датасет `API5`
`server.go:387-389` делегирует полному обработчику. Node возвращал лёгкие метаданные плюс `lastDate` (`datasets.js:70-84`). Эндпоинт создавался ради экономии трафика — экономии больше нет.

### 1.10. `refresh` читает не тот ключ настроек и обновляет иначе `API6`
Используется `enhancerProvider` вместо `resultsRefreshProvider`; вместо инкрементального слияния за 7 дней — полная перезагрузка 40 лет с перезаписью.

### 1.11. Паника на пустых данных в мульти-тикерных расчётах
`calc.go:224` — `tickersOrOne` не проверяет пустоту в ветке нескольких тикеров, тогда как одиночная ветка проверяет (`calc.go:227`). `indicators.IBS` на пустом срезе паникует (`indicators.go:132`). Достижимо из `/api/calc/single-position`, `/api/calc/ema-zone`, `/api/calc/buy-at-close-4`, `/api/calc/options-multi`, а также напрямую из `/api/calc/indicators` (`calc.go:129`). Обработчик роняет соединение вместо ответа 400.

### 1.12. Имя поля успеха разъехалось `API7`
Node — `{success: true}`, Go — `{ok: true}`, причём непоследовательно: `apply-splits` и `patch metadata` используют `success`, остальное — `ok`.

## Блок 2. Безопасность

Детали: [security-manual.md](security-manual.md), [security.md](security.md)

### 2.1. Ключи провайдеров утекают в браузер при сетевой ошибке `S-A`
`providers/client.go:140,168,192,248,281,312,349` собирают URL с ключом в строке запроса. При любой транспортной ошибке `c.HTTP.Do` (`client.go:81`) возвращает `*url.Error`, чей текст **содержит полный URL вместе с ключом**, и он уходит клиенту через `writeProviderError` (`server.go:1117`) и обработчики `/api/test-provider` (`server.go:1084`).
Это регрессия именно Go: объекты ошибок Node не содержали URL. Особенно неприятно, что кнопка «Проверить провайдера» нажимается ровно тогда, когда провайдер недоступен, то есть в момент утечки.

### 2.2. Пустой `ADMIN_PASSWORD` вне production открывает весь API `S1`
`server.go:193-200` — при пустом пароле и `s.prod == false` вызывается `next()` **без проверки**. `s.prod` определяется по `NODE_ENV`/`GO_ENV` (`server.go:48`), а в `docker-compose.yml:11-21` ни одна из них не задана в блоке `environment`. Открывается в том числе `POST /api/autotrade/execute`. Дополняет картину `docker-compose.yml:26-27` — порт 3001 опубликован на хост в обход Caddy.
Конфигурация должна отказывать закрыто.

### 2.3. Ограничение частоты запросов утрачено полностью `S2`
Node вешал `apiLimiter` на `/api/` и `uploadLimiter` на загрузку (`server.js:76-77`). В Go и в Caddy ограничителя нет. Последствия: неограниченный перебор пароля на `/api/login`; неограниченные `POST /api/calc/*`, которые теперь считают бэктест **на сервере**, в одном процессе с планировщиком торговли; неограниченный bcrypt на `/api/auth/hash-password`.

### 2.4. CSP утрачен `S3`
Node отдавал полную политику через helmet (`server.js:39-59`). Caddy ставит только HSTS, `X-Content-Type-Options` и `Referrer-Policy` (`Caddyfile:14-19`) — **CSP и `frame-ancestors` отсутствуют**. `nginx.conf` заголовки ставит, но обслуживает старый React-фронт, а Go-SPA идёт мимо него.

### 2.5. Сессионная кука без `Secure` `S4`
`server.go:276`. Токен уйдёт открытым текстом при любом обращении по `http://`.

### 2.6. Нет ограничения размера тела запроса `S5`
`readJSON` (`server.go:172-175`) декодирует поток без `MaxBytesReader`; во всём `go/internal` его нет ни разу. Node ограничивал 5 МБ.

### 2.7. Неполные таймауты сервера `S6`
`main.go:38` задаёт только `ReadHeaderTimeout`. (Исходящие клиенты таймауты имеют везде — здесь всё в порядке.)

### 2.8. «Запомнить меня» игнорируется, срок сессии всегда 30 суток `S7`
`server.go:253` читает поле, `server.go:275` его не использует. Протухшие сессии не вычищаются.

### 2.9. Прочее
- Сравнение пароля в открытом виде не constant-time (`server.go:264-268`) — унаследовано от Node, не регрессия `S8`.
- Ошибка `crypto/rand` игнорируется (`server.go:317-321`) `S9`.
- `PATCH /api/settings` возвращает 200 при некорректном JSON `S11`.
- `limit` в `/api/autotrade/logs` без верхней границы.
- Контейнер запускается от root (`docker/go.Dockerfile` без `USER`).
- Токен Webull хранится в открытом виде, файл БД доступен на чтение группе и всем.

### 3.2. Вкладки анализа выродились в статические
Вложенные вкладки «Опционы», «BuyAtClose», «BuyAtClose4», «Без стоп-лосса», «Пополнения» **не имеют ни одного настраиваемого параметра** — всё захардкожено в вызовах `API.calc` — и лишены графика equity. Профессиональный график цены сведён к голым свечам: пропали маркеры сделок, наложение EMA, панели IBS и объёма, отметки сплитов, экспорт в CSV.

### 3.3. Деградация вместо отсутствия
- Ручное закрытие сделки монитора: полноценная форма с датой, ценой, подстановкой живой котировки и Exit IBS → голый `window.prompt()` с одной ценой.
- Модалка редактирования сделки потеряла `entryIBS`, `exitIBS`, `quantity`, `isHidden`, `isTest`.
- Конфигурация автоторговли на /broker: около 20 полей → 4 строки только для чтения.

### 3.4. Системные проблемы
- **Обработка ошибок отсутствует в большинстве обработчиков мутаций** (`app.js`): создание и правка сплитов, дней календаря, watch-тикеров, ручных сделок, EMA-оповещений — без `try/catch`. Ошибка API превращается в необработанное отклонение промиса без какой-либо реакции интерфейса.
- **Валидация не делается ни на клиенте, ни на сервере**: коэффициент сплита, поля ручных сделок, числовые настройки.
- **Скрытые (`isHidden`) сделки монитора больше не фильтруются** — засоряют историю и всю статистику /watches.
- **Нигде нет форматирования времени в биржевой зоне** — сырые ISO-строки на балансе, ордерах и в логах. Это ровно тот случай wall-clock времени, для которого CLAUDE.md требует явную `America/New_York`.
- Повторная проверка авторизации при переходах между страницами и глобальный перехват 401 отсутствуют; после входа теряется исходная страница.

### 3.5. Функциональные баги в самом SPA
- Вкладка «Сплиты» в мульти-тикерном режиме запрашивает сплиты по `state.ticker`, а не по тикерам, для которых считался бэктест.
- Импорт JSON сплитов в формате `{"symbol": ..., "events": [...]}` перебирает `Object.entries` и создаёт тикеры с именами `SYMBOL` и `EVENTS`.
- `handleTestProvider` (`server.go:1072-1114`) обрабатывает только три провайдера; кнопки проверки **Polygon и Webull** всегда отвечают «Unknown provider» — в Node обрабатывались все пять (`routes/quotes.js:341-385`).
- Обновление датасета на /data читает не тот ключ настроек и игнорирует выбранного пользователем провайдера.

## Блок 4. Надёжность и производительность

Детали: [performance-manual.md](performance-manual.md)

### 4.1. Каждая оценка сигнала перечитывает весь датасет с диска `P1`
`evalWatch` (`telegram.go:376`) вызывает `GetOHLC` для каждого тикера при каждой оценке; `GetDataset` (`db.go:301`) выгружает **все** бары без ограничения (за 10 лет это ~2 500 строк), кэша нет. Затем IBS считается по всему массиву ради последнего значения (`telegram.go:383`), и ещё раз весь массив обходит проверка целостности. Умножается на планировщик (каждые 20 с в окне) и на `GET /api/autotrade/status`.

### 4.2. Актуализация цен без троттлинга и с запросом 40 лет истории `M3`, `M4`
`actualize.go:71-83` обходит тикеры **без единой паузы**; `PRICE_ACTUALIZATION_REQUEST_DELAY_MS` (15 с) и `..._JITTER_MS` (2 с), которые Node выдерживал между запросами (`priceActualization.js:55-91`), в Go не читаются нигде. При этом по каждому тикеру запрашивается сорокалетняя история (`actualize.go:69-70`) вместо инкрементальной догрузки. На Alpha Vantage с лимитом порядка 5 запросов в минуту это гарантированное упирание в лимит.

### 4.3. Единственное соединение с БД сериализует приложение `P2`
`SetMaxOpenConns(1)` (`db.go:34`) — разумно для SQLite, но означает, что долгое чтение (см. 4.1) или серия бэктестов останавливают обработку всех запросов, включая контур T-11/T-1.

### 4.4. SPA перерисовывает страницу целиком `P3`
`renderPage()` (`app.js:2133-2151`) уничтожает все графики и заменяет разметку целиком; вызывается 80 раз по файлу — на каждое действие, а не только на смену страницы. Теряются позиция прокрутки, фокус ввода и масштаб графиков.

### 4.5. Гонка при опросе трекеров `A18`
Планировщик каждые 20 с обходит все трекеры (`scheduler.go:151`), одновременно на каждый ордер работает своя горутина (`track.go:118`). Синхронизации нет — двойные обращения к брокеру и дублирующиеся уведомления. Node защищался флагом `inFlight`.

### 4.6. Журнал исполнения обеднён `A19`, `A20`
Node вёл структурированные события с общим `correlationId`, снимком баланса, ответами брокера, помесячной ротацией и отдельным сырым логом Webull. В Go `AppendAutotradeLog` принимает одну плоскую строку, а `Logs()` (`autotrade.go:493-500`) отдаёт **один и тот же массив** в поля `logs`, `autotrade`, `monitor` и `brokerRaw`. Разбор спорного исполнения задним числом невозможен.

### 4.7. Мёртвые настройки автоторговли `A17`
`orderType`, `maxSlippageBps`, `previewBeforeSend`, `executionWindowSeconds` присутствуют в дефолтах (`db.go:589-598`) и в интерфейсе, но не читаются в Go нигде. Переключатели создают ложное ощущение контроля.

## Блок 5. Тестовое покрытие

Харнесс эталонов устроен **правильно**: `scripts/dump-go-goldens.ts` снимает эталоны с работающих TypeScript-движков, Go проверяется против них. Это настоящее доказательство паритета — но покрытие неровное.

- **Движок EMA практически не проверен.** Единственный эталон `googl-ema-trades.json` содержит **одну** сделку: вход 2008-03-04, выход 2025-09-05 по причине `end_of_data`. Зонная логика — множественные лоты, зоны продажи, удаление лотов — не задействована вовсе. Именно там найден дефект 1.2.
- **Слой хранения без единого теста.** Пакет `store` — 1 320 строк, ноль тестовых файлов. В нём жизненный цикл сделок, расчёт P&L при ручном закрытии, слияние настроек (источник дефекта 0.5), управление трекерами, сессии.
- **Эталоны сняты без фиксированной зоны** — в `manifest.json` записано `"tz": "(unset)"`.
- Не покрыты эталонами: ежемесячные пополнения, плечо, решения автоторговли, агрегация T-11/T-1, граничные случаи метрик.
- Разбор ответов провайдеров сверялся только на уровне сигнатур, не построчно — отмечено как незакрытый участок.

## Приложение. Ложные срабатывания

Отсеяно при проверке — в roadmap не входит.

1. **«Дефолты настроек разъехались»** (одна находка была помечена CRITICAL, три — HIGH). `watchThresholdPct`, `resultsQuoteProvider`, `enhancerProvider`, `indicatorPanePercent`, `defaultMultiTickerSymbols` в Go (`db.go:582-588`) совпадают с серверными дефолтами Node (`settings.js:13-21`) **один в один**. Сравнение велось с клиентским стором React (`stores/index.ts:101-107`), который расходился с сервером и в старом стеке; клиент всегда вызывает `loadSettingsFromServer()`, поэтому побеждало серверное значение. Регрессии нет.
2. **«Ветка `high <= low` возвращает 0.5 вместо отказа»** — недостижима: `NormalizeIntradayRange` (`providers/client.go:437-439`) в этом случае возвращает nil.
3. **«Лимитные ордера со проскальзыванием потеряны»** — в живом пути Node сам форсировал `orderType: 'MARKET'` (`autotrade.js:1210, 1539`). Настройка вводит в заблуждение в обеих версиях; это не регрессия.
4. **«Загрузка файлов через multipart не поддерживается»** — поддерживается (`server.go:395`).
5. **`SingleTickerPage.tsx`** — мёртвый код в текущем React (`/results` перенаправляет на `/stocks`); его уникальные возможности исключены из сравнения.

## Порядок работ

**Сначала, до включения автоторговли:** блок 0 целиком. Внутри него первыми — 0.1–0.3 (учёт сделок), 0.5–0.6 (конфиг и пороги), 0.11 (`recover`), 0.13–0.14 (статус ордера). Это связанный узел: пока сделка пишется до исполнения, а статус исполнения определяется поиском подстроки, остальное чинить бессмысленно.

**Параллельно и независимо:** 2.1 (утечка ключей), 2.2 (отказ авторизации в открытую), 2.3 (ограничение частоты) — они не пересекаются с торговым кодом.

**Следом:** 1.5 (автоприменение сплитов — искажает данные для всего остального), затем 1.1 (системная трактовка нуля), затем остальное из блока 1.

**Далее:** блок 5 в части эталонов EMA и тестов слоя хранения — иначе исправления блока 1 нечем будет проверить. Затем блок 3 по убыванию тяжести и блок 4.
