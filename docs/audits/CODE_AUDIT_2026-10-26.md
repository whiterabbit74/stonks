## AUD-186 — OPEN, P2: живой EMA-сигнал смешивает цены до и после сплита

- В отличие от AUD-018, бэктест уже получает ожидающие сплиты, а живой

  события. Проверка: одинаковый сигнал на сырой истории с pending-сплитом

## AUD-187 — OPEN, P1: добавочный вход теряет количество проданной ноги другого брокера

- Код: `go/internal/store/positions.go:765–790,870–902`,
  `go/internal/live/autotrade.go:1612–1667`, `go/internal/live/trade_record.go:150–181`.
- Полный выход одного брокера обнуляет его `leg.Qty`, но общая `Quantity`
  сохраняет исходный размер. В `AttachEntry` любое добавление акций
  заканчивается `p.Quantity = p.ExecutedQty()` — суммой только удерживаемых
  акций. Завершённая нога другого брокера перед этим не выделяется.
- Пример: Webull купил 1, Robinhood — 1; Quantity=2. Webull вышел,
  у Robinhood осталась 1. Дополнительная тестовая покупка Robinhood на 1
  разрешена `manualOrder`, когда прежние заявки завершены. Теперь его Qty=2
  и общая Quantity=2, хотя в этой строке было 3 купленные акции и 1 проданная.
  Закрытая часть Webull отдельно не записана. Позднее `detachExitedLegTx`
  вычисляет проданное как `Quantity - ExecutedQty() = 0`, и восстановить
  завершённый круг уже не может.
- Связано с AUD-117, но причина другая: тот выделяет собственную завершённую
  ногу входящего брокера, здесь добавляет акции сосед. Нужно сохранять
  количество завершённой части либо выделять её перед пересчётом.
  Проверка: BUY W → BUY R → SELL W → дополнительный BUY R, затем выход
  и повторный вход; закрытые части плюс остаток не теряют акции.

## AUD-180 — REOPENED, P2: накопленная средняя второго ордера используется как цена его добавочной части

- Код: `go/internal/store/positions.go:796–804,843–887`,
  `go/internal/store/live_persist.go:469–496`,
  `go/internal/store/aud169_entry_replay_test.go:59–100`.
- Исправление `2725751` складывает два однократных исполнения и рост
  единственного ордера. Но когда нога содержит ордер A и часть B, очередное
  накопленное исполнение B даёт `newly` как разность количеств, а в
  `weightedPrice` передаётся средняя цена всего B.
- Пример метода хранилища: A=10 по 100; B сначала 2 по средней 120,
  затем 4 по средней 130. Правильно: (1000+520)/14 = 108.571429.
  Код получает (1240+2×130)/14 = 107.142857. Стоимость новых двух акций
  по двум накопленным ответам составляет 520−240=280, а не 260.
- В движке нужен повторный ответ с выросшим количеством после записанного
  исполнения, например после сбоя финальной записи статуса. Обычные
  частичные ответы рабочего ордера пока только сохраняются в трекере.
  Частота внешнего сценария не проверялась. Контракт накопленных исполнений
  поддерживается тестами, но сочетание с несколькими ордерами не покрыто.
- Это оставшийся случай AUD-180. Нужно учитывать изменение стоимости
  конкретного ордера вместе с количеством. Проверка: A/B/B из примера,
  затем идентичный повтор без изменения учёта.

## AUD-191 — OPEN, P2: срок остановки HTTP не ограничивает ожидание планировщика

- Код: `go/cmd/server/main.go:93–117`,
  `go/internal/scheduler/scheduler.go:176–183`,
  `go/internal/live/actualize.go:140–158`; `docker-compose.yml`.
- После сигнала остановки `serve` синхронно вызывает `onShutdown`, который
  ждёт активный тик, фоновые обновления и трекеры. Только после возврата
  создаётся контекст на 60 секунд для HTTP Shutdown. Таким образом,
  `shutdownTimeout` не ограничивает первую, потенциально долгую часть.
- Между запросами актуализации штатно есть задержки по 15 секунд;
  задача не получает отмену остановки. Процесс продолжает принимать HTTP
  всё время ожидания. В compose нет собственного `stop_grace_period`,
  согласованного с длительностью завершения. Фактическое принудительное
  завершение контейнера здесь не измерялось.
- Отдельно от AUD-N01: тот запретил закрывать БД под задачей, но не ограничил
  ожидание. Нужен единый срок и прекращение приёма запросов до ожидания
  задач с сохранением незавершённых заявок. Проверка: заблокированная
  фоновая задача, сигнал остановки, срок и отказ новых соединений.
