Read-only проход по всему проекту: `go/internal/live`, `scheduler`, `store`, `httpapi`,
`providers`, `webull`, `robinhood`, `backtest`, `ibs`, `tradingdate`, SPA (`go/web`), `mcp/`.
Исходники **не менялись**. Базовая линия: `go vet ./...` чист, `TZ=Pacific/Auckland go test ./...`
зелёный на момент проверки.

Формат находки: `ID • важность • где • что • почему это баг • похожие места`.

Важность:
- **P0** — может привести к неверной сделке, потере ордера или пропуску торгового дня.
- **P1** — неверные данные/отчёты оператору, скрытая потеря состояния.
- **P2** — производительность, лишние перерисовки, мёртвый код, UX.

## Часть 1. Живая торговля (`go/internal/live`)

### F-01 • P0 • `autotrade.go:323` `decideLiveAction` — выход по позиции, которой у брокера нет

```
if heldErr == nil && len(held) > 0 {
    if _, ok := held[sym]; !ok { return none("broker_position_mismatch", …) }
}
```

Проверка «символ есть у брокера» выполняется **только когда `len(held) > 0`**. Если брокер
успешно ответил и вернул **ноль позиций**, а в журнале `broker_trades` висит открытая
сделка, ветка проверки пропускается целиком, и решение уходит `action=exit`.

Псевдокод как есть:

```
если журнал держит SYM и выходы разрешены:
    если брокер ответил И у брокера есть хоть одна позиция:
        если SYM не среди них -> mismatch
    # брокер ответил "позиций нет" -> сюда не заходим
    если IBS > highIBS -> ВЫХОД
```

Псевдокод как должно быть: `если брокер ответил (heldErr == nil) и SYM не среди held -> mismatch`,
независимо от `len(held)`.

Фактического голого шорта не будет: `sizeOrder("exit", …)` (`sizing.go:376`) перечитает позиции
и вернёт `No broker position found for SYM`. Но цепочка отрабатывает неправильно: оператор
видит в Telegram «Закрываем SYM», в логах `execution_blocked`, вместо честного
`broker_position_mismatch`, и лишний раунд обращений к брокеру тратится из бюджета T-1.

Похожие места: та же ветка в `executeAll` (`execute_all.go:62`) использует ту же функцию —
дефект один на оба пути.

### F-02 • P0 • `execute_all.go:62` — решение по каждому брокеру строится на котировках чужой книги

`executeAll` вызывает `decideLiveAction(ev.Quotes, ev.Symbols, held, …)` для каждого брокера,
но `ev.Quotes` собран в `EvaluateWindow` **только** для watch-списка плюс символа открытой
позиции **дефолтного** брокера:

```
open, held, heldErr := e.booksFor("webull", e.defaultBroker(), …)   // autotrade.go:258
… если open.symbol нет в списке -> добавить в quoteSymbols        // autotrade.go:271-278
```

Если Robinhood держит тикер, которого нет ни в watch-списке, ни у Webull, котировки для него
не запрашивались → `decideLiveAction` не находит строку → `open_position_quote_unavailable`
→ **выход по этой позиции не проверяется вообще**, каждый день, молча.

Это ровно тот сценарий, ради которого добавляли P0-5, — исправление сделали для одного
брокера и не распространили на `brokerSnapshot()`.

### F-03 • P1 • `execute_all.go:209` — снимок баланса читается не у того брокера

```
go e.logBalanceSnapshot(corr, symbol, action)
```

`logBalanceSnapshot` (`autotrade.go:898`) внутри работает с `e.Broker` — дефолтным (Webull)
адаптером, — хотя ордер отправляется в `br`. При отправке через Robinhood в
`autotrade_logs` попадает баланс Webull под записью о сделке Robinhood. Это тот же класс
дефекта M2 («есть правильный помощник, вызывают соседний неправильный»), что и прошлые
F02/F04/S06.

Дополнительно: горутина запускается без ожидания и без контекста — она переживает и запрос,
и завершение T-1, и продолжает ходить в сеть после дедлайна.

### F-04 • P1 • `telegram.go:560+` `buildT1Text` — при двух брокерах отчёт T-1 молчит об исполнении

`appendExec` разбирает `res.Broker` двумя типами: `OrderResult` и `map[string]any` с ключами
`submitted`/`quantity`/`error`. Но `executeAll` кладёт в `ev.Broker`:

- один брокер отправлял → сам результат (ок);
- **любое другое число** → `map[имя брокера] -> результат` (`execute_all.go:96-104`).

Во втором случае `br["submitted"]` — nil, `br["error"]` — nil, поэтому в сообщение не попадает
**ни строки** об отправке: оператор видит «Открываем SYM по $X» и ничего про то, ушла заявка
или нет.

Там же зашита подпись `Webull:` для любого брокера — Robinhood-ордер подписывается как Webull.
`brokerLabel()` в этом же файле уже существует и не используется здесь.

### F-05 • P1 • `evalWatch` и `watchThresholds` берут пороги из разных источников

- `telegram.go:578` `evalWatch`: `low = ibs.DefaultLowIBS`, если у watch нет `lowIBS`;
  настройки `autoTrading.lowIBS` **не читаются**.
- `config.go:242` `watchThresholds(watch, cfg)`: fallback идёт на `liveLowIBS(cfg)` —
  на настройки.

`EvaluateWindow` использует **обе**: `ev.entry`/`ev.exit` (и, следовательно, строки T-11 и
`bestEntryRow` в T-1) считаются по дефолту `0.10`, а фактическое решение
(`decideLiveAction` → `liveLowOrDefault(q)`) — по значению из настроек.

Итог: если оператор поставил `lowIBS = 0.05` в настройках, T-11 показывает «вошли бы в SYM»,
а T-1 не входит; или наоборот. По CLAUDE.md это ровно то расхождение, которого не должно быть
(«монитор и автотрейдер обязаны ходить через `ibs.IsEntrySignal`… чтобы пороги не разъезжались»).

### F-06 • P1 • `lowIBS = 0` не считается невалидным, `highIBS = 0` — считается

`config.go:249-256` и `telegram.go:580-587`: `highIBS == 0` → `highInvalid = true`, подставляется
дефолт, `decideLiveAction` отдаёт `invalid_high_ibs`. Для `lowIBS == 0` симметричной проверки нет:
значение принимается как есть, `IsEntrySignal(ibs, 0)` требует `ibs < 0` → **вход по тикеру
навсегда выключен, без единого предупреждения**. Оператор, стерший поле в форме, получает
молчаливо мёртвый тикер.

### F-07 • P1 • `telegram.go:168,172` — ошибка чтения журнала выглядит как «нечего делать»


Это механизм M1 из прошлого разбора, воспроизведённый в самой критичной точке дня.

### F-08 • P1 • `store.Settings()` возвращает дефолты вместо ошибки, и это снимает защиту

`db.go:846`:


### F-09 • P1 • `autotrade.go:42` `PatchAutoConfig` — сохранение настроек может не произойти


### F-13 • P1 • `e.now()` вызывается дважды при вычислении времени до закрытия

`autotrade.go:918` (`outsideExecutionWindow`) и `deadline.go:65` (`t1Deadline`):

```
p := tradingdate.CurrentTimeNYSE(e.now())
nowSec := p.Hour*3600 + p.Minute*60 + e.now().Second()
```

Два независимых снимка часов. Если между ними пересекается граница минуты, часы/минуты берутся
из одного момента, а секунды — из следующего: `nowSec` уезжает на 60 секунд. На T-1 бюджет
считается от `secondsUntilClose`, то есть дедлайн может оказаться на минуту раньше или позже
реального. Вероятность мала, цена — пропущенный или обрезанный ордер.

Правильно: один `now := e.now()`, всё остальное — из него.

## Часть 3. Хранилище (`go/internal/store`)

### F-24 • P1 • `MergeOHLC` переписывает весь датасет ради одного бара

`live_persist.go:15` → `SaveDataset` (`db.go:506`), который делает

### F-28 • P2 • CSRF-защита пропускает запрос без `Origin` и без `Sec-Fetch-Site`

`ratelimit.go:148-155`. Для современных браузеров этого достаточно (кросс-сайтовый POST всегда

а не на проверке. Cookie стоит `SameSite=Lax`, что закрывает основной вектор — так что это

### F-29 • P2 • `limitAPI = 500 / 15 мин` против того, как рендерит SPA

`ratelimit.go:16`. SPA не опрашивает по таймеру (это плюс), но каждая перерисовка страницы

## Часть 7. Продолжение: трекеры, брокерские клиенты, актуализация

### F-36 • P0 • `order_parse.go:56` `fillQtyFrom` считает заказанное количество исполненным

```
func fillQtyFrom(detail map[string]any) float64 {
    return firstPositive(
        detail["filled_qty"], detail["filled_quantity"], detail["cum_qty"],
        detail["deal_quantity"],
        detail["qty"], detail["quantity"],      // <- это НЕ исполненный объём
    )
}
```

`qty`/`quantity` в ответе брокера — это объём **заявки**, а не факт исполнения. Два потребителя
принимают это за доказательство сделки:

1. `track.go:340` — «страховка» на нераспознанный статус:

```
if ordered := asFloat(t["quantity"]); ordered > 0 && fillQtyFrom(detail) >= ordered-1e-9 {
    status = "filled"
}
```

Комментарий рядом утверждает: «A fully executed quantity is proof of a fill regardless of what
the broker calls the state». Но если брокер не вернул `filled_qty` (типично для только что
принятой заявки), `fillQtyFrom` вернёт заказанные 10 штук, они сравняются с `ordered` — и
**неисполненная заявка помечается `filled`**, трекер финализируется, `recordFill` заводит
сделку в журнал, в Telegram уходит «исполнено». Дальше движок считает, что позиция есть,
а у брокера её нет.

2. `trade_record.go:108` — `reportedQty := fillQtyFrom(detail)` с комментарием «the only
   evidence of a partial fill». Тот же дефект: частичное исполнение неотличимо от полного.

Правильно: два разных геттера — `filledQtyFrom` (только поля исполнения) и `orderedQtyFrom`
(fallback на `qty`/`quantity`), и в проверку «страховки» пускать только первый.

### F-37 • P1 • `track.go:514` — потеря финального статуса трекера дублирует сделку и блокирует вход

`finalizeTrackerStatus` записывает сделку и только потом штампует статус:

```
e.recordFill(t, detail, status)          // сделка уже в журнале
_ = e.DB.SetOrderTrackerStatus(id, status)
```

`errcheck_test.go` (появился по ходу этого аудита) держит этот сайт в allowlist с
обоснованием «poll already observed the broker status; a failed stamp retries on the next tick».
Обоснование верно наполовину: повтор действительно будет — и он снова вызовет `recordFill`
для той же заявки. То есть цена сбоя не «штамп поставится позже», а:

- трекер остаётся `pending` → следующий вход блокируется `AnyPendingTrackerFor`
  (`execute_all.go:132`) с `pending_tracker_exists`, молча, до успешной записи;
- каждый повторный опрос заново заводит запись о том же исполнении.

Правильно: либо один транзакционный «записать сделку + закрыть трекер», либо идемпотентный
`recordFill` по `clientOrderId`.

Тот же сайт (`SetOrderTrackerStatus`) покрывает и `markBrokerDisconnected` (`track.go:416`),
и `markExecutionUnknown` (`track.go:428`) — там последствие мягче: заявка остаётся `pending`
вместо `execution_unknown`, то есть оператор не увидит нужного статуса в UI.

Рядом `deletePhantom` (`trade_record.go:356,359`) — если DELETE не прошёл, фантомная открытая
сделка остаётся и блокирует входы. Соседняя `logJournalSQLError` (`trade_record.go:324`) в
таком случае и логирует, и поднимает `trackerPersistBlock`; здесь — ни того, ни другого.
