# Полный аудит подсистем — 2026-09-05

Read-only аудит. Ничего не правится, только фиксируются находки.
Каждая находка: **что** → **где** (file:line) → **почему баг** → **как проверить**.

Легенда приоритетов:
* **P0** — теряются деньги / данные, или прод падает.
* **P1** — неверное поведение в штатном сценарии.
* **P2** — деградация UX, лишняя работа, шум.
* **P3** — чистота, риск на будущее.

## B. Хранилище (`internal/store`) — проверено чтением кода

### B1 (P0, деньги). `CloseTradeByID`: проверка «уже закрыта» и запись не связаны

`go/internal/store/db.go:1310-1335`:

```go
existing, err := d.GetTrade(table, id)          // читаем
if fmt.Sprint(existing["status"]) != "open" {   // решаем
    return existing, fmt.Errorf("Trade is already closed")
}
...
_, err = d.SQL.Exec(`UPDATE `+table+` SET status='closed', exit_date=?, exit_price=?,
    ... WHERE id=?`, ...)                       // пишем — БЕЗ AND status='open'
```

Классический check-then-act. `WHERE` сопоставляет только `id`. Два пути доходят
до этой функции из **разных горутин**:

* `go/internal/httpapi/server.go:1498` → `CloseMonitorTrade` — горутина HTTP-хендлера
  (ручная кнопка «закрыть сделку»);
* `go/internal/live/trade_record.go:86` (`closeTradeWithPnL`) — горутина движка,
  вызывается из `monitor.go:430` и `trade_record.go:239/246/303` при разборе
  исполнения у брокера.

Если ручное закрытие и автоматическое совпадут по времени, оба прочитают
`status=="open"`, оба пройдут проверку, оба выполнят `UPDATE`. Второй **молча**
перезапишет `exit_price` / `exit_date` / `pnl_absolute` / `pnl_percent` /
`holding_days` значениями из своего (уже устаревшего) снимка. Ошибки не получит
никто. Это порча финансовой записи о реальной сделке.

Почему это P0, а не гипотетика: `MaxOpenConns=1` сериализует сами запросы, но
**не** промежуток между `GetTrade` и `Exec` — между ними Go-код, и соединение в
это время свободно для второй горутины.

Как чинить: перенести проверку в сам `UPDATE` —
`... WHERE id=? AND status='open'`, затем `RowsAffected()`; `0` строк →
возвращать «already closed». Тогда решение и запись атомарны на уровне SQLite.

Проверка: тест, который дёргает `CloseTradeByID` дважды подряд с разными
`exitPrice` — сейчас оба вызова успешны, побеждает последний.

### B2 (P1, данные). Ни один цикл чтения строк не проверяет `rows.Err()`

Во всём репозитории 14 циклов `for rows.Next()` (все — в `internal/store`), и
`rows.Err()` не вызывается **ни разу**:

```
db.go:365   hasColumn                 db.go:1352  ListTrades
db.go:417   ListDatasets              db.go:1458  ListEMAAlerts
db.go:477   GetDataset      <-- бары  db.go:1605  GetOHLCLast     <-- бары
db.go:620   ListSplits                db.go:1675  ListTickers
db.go:640   AllSplits                 live_persist.go:156  ListAutotradeLogsKind
db.go:994   ListWatches               live_persist.go:269  listBlockingTrackers
                                      live_persist.go:311  ListPendingTrackers
                                      live_persist.go:335  ListRecentTrackers
```

По контракту `database/sql` `rows.Next()` возвращает `false` **и** в конце
данных, **и** при ошибке ввода-вывода посреди выборки. Без `rows.Err()`
вызывающий получает укороченный срез и `err == nil` — то есть обрезанные данные,
неотличимые от полных.

Два места делают это опасным:

* `GetDataset` и `GetOHLCLast` грузят исторические бары. Обрезанный ряд молча
  уедет и в бэктест, и в расчёт живого IBS — цифры будут выглядеть правдоподобно
  и будут неверны.
* `listBlockingTrackers` кормит защиту от дублирования ордеров. Обрезанный
  список = движок думает, что незакрытых заявок нет, хотя они есть.

Как чинить: после каждого цикла `if err := rows.Err(); err != nil { return nil, err }`.

Проверка: подменить драйвер на падающий после N строк — сейчас вернётся короткий
срез с `nil`-ошибкой.

## C. Бэктест и метрики — проверено чтением кода

### C1 (P1, цифры). Три разные формулы CAGR под одним именем

В `internal/metrics/metrics.go` живут **три** независимые реализации CAGR с
**тремя разными** политиками для периода короче года:

| Реализация | Строки | Период < 1 года | Кто использует |
|---|---|---|---|
| `Calculator.cagr` | 66-74 | **не годуется** — возвращает простую доходность | `clean.go:50,206`, `margin.go:274,293,304` (и `/api/calc` 129/148/199) |
| `BacktestMetrics` | 444-456 | годуется всегда, пол периода **0.1 года** (~36.5 дн.) | `single.go:386`, `ema.go:582` |
| `CAGR()` | 382-391 | годуется всегда, **пола нет** | `bac4.go:262` |

Одна и та же кривая капитала даст три разных числа в поле, которое во всех трёх
случаях называется `CAGR`. На отрезке ~14 календарных дней с итогом +2 %:

* `Calculator.cagr` → **2 %** (годовая доходность подменена абсолютной);
* `BacktestMetrics` → `1.02^(1/0.1) − 1` ≈ **21.9 %**;
* `CAGR()` → `1.02^(365.25/14) − 1` ≈ **67 %**, и чем короче окно, тем сильнее
  взрыв (на однодневном окне — сотни процентов).

Пользователь сравнивает `/api/calc/backtest`, `/api/calc/single-position` и
`/api/calc/buy-at-close-4` на одном периоде и видит несопоставимые цифры, по
которым принимает решение о стратегии.

**Дополнительно (моя находка поверх этого):** `Calculator` считает от `cagr`
ещё две метрики — `calmar` (`metrics.go:125`) и `alpha` (`metrics.go:207`). На
периоде меньше года в них подставляется **не CAGR, а абсолютная доходность**,
то есть Calmar и Alpha на коротких бэктестах занижены тем же дефектом, и это
уже не видно из названия поля.

Как чинить: одна реализация, одна явная политика для периода < 1 года
(либо честно годовать, либо возвращать `0`/пометку «период слишком короткий» —
но **одинаково везде**), остальные две удалить.

Проверка: прогнать одну и ту же кривую (10000 → 10200, 14 дней) через
`metrics.New(...).All().CAGR`, `metrics.BacktestMetrics(...).CAGR` и
`metrics.CAGR(...)` — три разных числа.

### C2 (P1). `RunClean` не открывает позицию на последнем баре данных

`go/internal/backtest/clean.go:75`:

```go
if ibssig.IsEntrySignal(ibs, lowIBS) && nextBar != nil {
```

`nextBar` нужен **только** ветке `EntryExecution == "nextOpen"` (строка 79,
цена входа `nextBar.Open`). Для режима по умолчанию `"close"` цена входа —
`bar.Close` (строка 88), следующий бар не требуется вообще. Условие вынесено
наружу обеих веток, поэтому в основном режиме валидный сигнал входа на
последнем баре датасета **молча игнорируется**.

Это расходится с соседями: `single.go:281-322` и `bac4.go:82-103` такого
ограничения не имеют и позицию на последнем баре открывают. Никакого правила в
`CLAUDE.md`, которое выводило бы последний день данных из-под входа, нет —
похоже на остаток копипасты после сведения движков на общий `runDailyEngine`
(коммиты `404dc87`…`3eeca9e`).

Как чинить: занести проверку `nextBar != nil` внутрь ветки `nextOpen`.

Проверка: датасет из 3 баров, у последнего IBS < `lowIBS`. `RunBacktest` даст 0
сделок, `RunBuyAtClose4` и `RunSinglePosition` на тех же данных — одну.

### C3 (P1, цифры). Сплиты учитывает только `RunClean`; остальные четыре движка торгуют неоткорректированными ценами

`splits.AdjustOHLC` во всём репозитории вызывается из трёх мест:

## E. Живой торговый контур — проверено чтением кода

Два независимых прохода (мой и агентский) сошлись на одном и том же P0 — это

### E1 (P0, деньги). Подтверждение B1: блокировки нет ни на одном из путей

Пути до `store.CloseTradeByID`:

* `httpapi/server.go:1498` → `CloseMonitorTrade` — **вообще мимо движка**, без

* `live/monitor.go:430` (`applyConsistencyAction`) — без блокировки.

мутации в `db.go` (строки 287, 519, 560, 653, 671) обёрнуты в `d.SQL.Begin()`.
`CloseTradeByID` — единственная, которая нет.

### E2 (P1, деньги). Ключи резервации в ручном и автоматическом путях лежат в разных пространствах имён

Обе ветки защищаются одной картой `e.reservations` под `e.mu`, но строят ключ
по-разному.

`go/internal/live/execute_all.go:113-118` (автоматический путь):

```go

    key = symbol + ":" + action     // для входа символ НЕ добавляется — намеренно
}
if brokerName != "" {

```

`go/internal/live/autotrade.go:1131` (ручной путь — `TestBuy`, `ClosePosition`):

```go

```

Автоматический вход намеренно бесимённый: на брокера должен приходиться один вход

окно: он проверяется **до** отправки, а трекер записывается **после** успешной

нарушает правило `CLAUDE.md` «держим позицию, пока она не закрыта полностью».

Смягчение: ручной путь заперт за `WEBULL_ENABLE_LIVE_TEST_BUY=true`. Проверять,
включён ли он на проде, я не стал — это read-only аудит без доступа к VPS.

Как чинить: строить ключ одной функцией для обоих путей. Для `entry` — без
символа, в обоих местах.

### E3 (P2). Выход закрывает две таблицы двумя не атомарными вызовами

`trade_record.go:233-247`: сперва закрывается строка в `broker_trades`, затем

## F. Планировщик, провайдеры, Telegram — проверено чтением кода

### F1 (P0, деньги + данные). Битый бар от провайдера молча затирает хороший — и на автоматическом пути его никто не проверяет

Это цепочка из четырёх звеньев, каждое проверено отдельно.

**Звено 1 — провайдер превращает мусор в ноль.** `providers/client.go:742-755`:

```go
func num(v any) float64 {
    ...
    case string:
        f, _ := strconv.ParseFloat(n, 64)   // ошибка выброшена -> 0
        return f
    }
```

Непарсящееся значение поля становится `0`, а не ошибкой. Ответ провайдера,
деградировавший частично (известный режим отказа во время их собственных
аварий), проходит разбор «успешно».

**Звено 2 — запись безусловно перетирает.** `store/live_persist.go:23-24`:

```sql
INSERT INTO ohlc (...) VALUES (...)
ON CONFLICT(ticker, date) DO UPDATE SET
  open=excluded.open, high=excluded.high, low=excluded.low,
  close=excluded.close, adj_close=excluded.adj_close, volume=excluded.volume
```

Никакого условия: обнулённый бар заменяет собой ранее сохранённый хороший бар за
ту же дату.

**Звено 3 — проверка есть, но только на одном из двух путей.** У `MergeOHLC`
ровно два вызывающих:

| Путь | Файл | Валидация |
|---|---|---|
| ручное обновление датасета | `httpapi/server.go:872` | **есть** — `validateBars` на строке 849 |
| ночная автоактуализация | `live/actualize.go:140` | **нет** |

`actualize.go:135-141` считает провалом только `err != nil || len(hist.Rows) == 0`.
Ответ, который разобрался и содержит мусор, признаётся успехом. То есть страховка
стоит на пути, за которым следит человек, и отсутствует на пути, который ходит
сам по ночам.

**Звено 4 — сама проверка неполна.** `httpapi/integrity.go:8-34`, `validateBars`
ловит: пустой набор, отсутствующую дату, дубль даты, немонотонность и `high < low`.
Не ловит: нули, отрицательные цены, `NaN`/`Inf`, `close` вне `[low, high]`, дату
в будущем. Обнулённый бар (`0,0,0,0`) проходит её насквозь: `high < low` — ложь.

**Во что это выливается.** `indicators.go:138-153`:

```go
if high < low || close < low || close > high { result[i] = math.NaN(); continue }
if high == low { result[i] = 0.5; continue }
```

У бара `0,0,0,0` выходит `high == low` → **IBS = 0.5**. Не `NaN`, который был бы
отброшен в `ibs.asFinite`, а совершенно правдоподобное число ровно посередине
между порогами 0.10 и 0.75. В бэктесте этот день молча становится «ничего не
происходит», и цифры стратегии оказываются неверными без единого признака ошибки.

Живой контур этим напрямую не отравляется: `evalWatch` (`telegram.go:611-613`)
берёт IBS из котировки (`ibsFromQuote`), а не из сохранённых баров. Это
проверено и это хорошая новость. Сохранённые бары в живом контуре используются
для `EvaluatePriceIntegrity` (`telegram.go:630`), и там нули отфильтрованы явно
(`integrity.go:38-44` пропускает бары с `Close <= 0`) — тоже корректно.

Как чинить: (а) валидировать бары **в самом `MergeOHLC`**, а не у вызывающих —
тогда путь нельзя обойти; (б) расширить проверку на нули, отрицательные, `NaN`,
`close` вне диапазона и будущие даты; (в) в `num()` различать «нет значения» и
«ноль».

    ...

    if until < 0  && until >= -5 { reportMissedTelegram(..., "t1",  ...) }

`reportMissedTelegram` — единственный механизм, сообщающий оператору «T-11/T-1 не
сработали». Он вложен внутрь `if trading`. Если импорт календаря Webull
(`RunCalendarExtend`) ломается надолго (например, протух токен) и покрытие
календаря отстаёт от `today`, `trading` становится `false` на весь день: нет
превью T-11, нет решения T-1, нет автоторговли — и **нет предупреждения**, потому
что код уведомления недостижим.

Единственный ранний сигнал — разовое сообщение «Календарь истекает» при падении
запаса ниже 14 дней. Пропустил его оператор — сам день аварии проходит в тишине.

Как чинить: вынести `reportMissedTelegram` (или отдельный алерт
«calendar-coverage-expired») наружу условия `if trading`.

### F3 (P1). Провал отправки в Telegram проглатывается именно на пути планировщика

`go/internal/live/telegram.go:345-357`:

```go

    out.Text = text

    } else {

        out.Success = true

```

`scheduler.go:229` зовёт агрегацию именно с `ForceSend: true`. Значит **любой**
сбой плановой отправки T-11/T-1 (протухший токен, 429 от Telegram, сетевой сбой)

возникает — повтор в следующем окне возможен.

неудачных отправок в `/api/status`; отдельный канал оповещения — по вкусу.

## H. Сквозная проверка: тот же дефект в других местах

Задача требовала, найдя баг, искать ему подобных по всему проекту. Главный
найденный шаблон — **check-then-act без транзакции и без условия в `WHERE`**.
Я прошёлся по всем 25 `UPDATE` в `internal/store` и по их вызывающим.

### H1 (P0, деньги). `ResolveTracker` — тот же шаблон на пути исполнения заявок

`go/internal/live/track.go:501-540`:

```go
t := e.DB.GetOrderTracker(clientOrderID)            // читаем
if t == nil { return nil, fmt.Errorf("tracker not found") }
if !resolvableTrackerStatus(fmt.Sprint(t["status"])) {
    return nil, fmt.Errorf("tracker already resolved")   // решаем
}
...
e.finalizeTrackerStatus(t, detail, "filled")        // пишем
```

`finalizeTrackerStatus` (`track.go:557-563`):

```go

if err := e.stampTrackerStatus(id, status); err != nil { return }   // ПОТОМ статус
```

`stampTrackerStatus` → `store.SetOrderTrackerStatus` (`live_persist.go:209-212`):

```sql
UPDATE order_trackers SET status=?, updated_at=datetime('now')
WHERE client_order_id=?          -- условия на текущий статус нет
```

**Блокировки нет.** `e.mu` в `track.go` берётся в других местах (кэш `orderMeta`,
строки 191-238, 308-321, 590-637), но **не** вокруг `ResolveTracker` и не вокруг
`finalizeTrackerStatus`.

Два независимых входа доходят сюда одновременно:

* ручной — HTTP `POST /api/autotrade/trackers/{clientOrderId}/resolve` (кнопка оператора);
* автоматический — колесо опроса, `track.go:393` и `track.go:534`, когда брокер
  наконец сообщает финальный статус.

Оба читают статус, оба видят «ещё не разрешён», оба идут писать. И порядок в
`finalizeTrackerStatus` делает хуже: **сделка пишется до того, как ставится
статус-предохранитель**, — то есть окно между решением и защёлкой максимально
широкое. Комментарий в коде объясняет этот порядок («чтобы ожидающий не увидел
filled-трекер без строки»), но при этом сам порядок и создаёт гонку.

**Где именно рвётся.** `recordFill` (`trade_record.go:91-249`) идемпотентен
**наполовину**:

* ветка `entry` (строка 176) защищена естественным ключом:
  `if existing := e.getTrade("broker_trades", clientOrderID); existing != nil { ...; return }` —
  id строки и есть `clientOrderID`, поэтому повторная запись входа не задваивается.
  Это сделано правильно.
* ветка `exit` (строки 233-248) такого ключа **не имеет**: она ищет открытую
  строку через `openTradeBySymbol(...)` и зовёт `closeTradeWithPnL(...)`. Два
  параллельных выхода найдут **одну и ту же** открытую строку (ни один ещё не
  зафиксировал закрытие) и оба уйдут в `CloseTradeByID` — прямиком в гонку B1/E1.

Итог: **выход из позиции — единственный путь без ключа идемпотентности, и он же
ведёт в единственный `UPDATE` без условия.** Два дефекта складываются.

Как чинить (одним движением закрывает B1, E1 и H1):
1. `SetOrderTrackerStatus` → `UPDATE ... WHERE client_order_id=? AND status NOT IN (финальные)`, проверять `RowsAffected()`;
2. `CloseTradeByID` → `... WHERE id=? AND status='open'`, проверять `RowsAffected()`;
3. решение о том, «можно ли действовать», принимать по результату этого условного
   `UPDATE`, а не по отдельно прочитанному снимку.

Проверка: два параллельных вызова `ResolveTracker` для одного `clientOrderID` с
`action == "exit"` — сейчас оба проходят проверку статуса.

### H2 (P2). Ошибки записи статуса «исполнение неизвестно» выбрасываются

## I. Псевдокод основных контуров и сверка с правилами

### I1. Тик планировщика (`scheduler.RunTick`, каждые 20 с)

```
RunTick(now):
    p     = CurrentTimeNYSE(now)          # явная биржевая зона          OK
    today = TodayNYSE(now)                # торговый день биржи, не UTC  OK
    cal   = ParseCalendar(db.GetCalendar())
    trading = IsTradingDay(p, cal)

    if trading and calendarCoverage(cal) < today:
        log("calendar-coverage-expired")
        trading = false                   # <-- F2: гасит и уведомления тоже

    if trading:
        sess   = TradingSession(p, cal)   # учитывает сокращённые дни    OK
        until  = sess.CloseMin - nowMin
        if 0  <= until < 10:  reportMissedTelegram("t11")   # внутри if trading  F2
        if -5 <= until < 0:   reportMissedTelegram("t1")    # внутри if trading  F2
        if until in [10..12] or until in [0..2]:
            RunTelegramAggregation(until)  # <- обе ступени входят сюда
    PollTrackers()                         # вне if trading               OK
    RunTokenHealth()
    if not trading: RunCalendarExtend(); return
    if 15 <= (nowMin - sess.CloseMin) <= 31:
        go RunPriceActualization()         # <-- F1: без валидации баров
        RunAutotradeLogRotation()
    RunCalendarExtend()
```

Расхождения: **F2** (уведомление о пропуске недостижимо, когда календарь
просрочен), **F1** (актуализация цен пишет бары без проверки).

### I4. Размещение ордера (`submitEvaluated` / `manualOrder` → `placeMarket`)
