Разрешённые изменения: этот отчёт и существующий реестр. Код не исправляется.
Метод: чтение исходников, прослеживание вызовов и сопоставление с прежними находками.
Приложение, тесты, браузер, сервер, базы и внешние сервисы не запускаются.
Сценарии ниже выведены из кода, а не воспроизведены запуском.
P1 — высокий приоритет (деньги/целостность данных); P2 — обычный приоритет;
P3 — малый приоритет. OPEN — не исправлено; REOPENED — прежняя находка
имеет подтверждённый незакрытый путь. Проверка отсутствия всех возможных багов
статическим аудитом не гарантируется.

## Находки

### AUD-146 — REOPENED, P1: массовое удаление сплитов оставляет цены пересчитанными

- Код: `go/web/js/app.js:3859` → `go/internal/httpapi/server.go:1178-1186`
  → `go/internal/store/db.go:1047-1050`; сравнение с `DeleteSplit:1024-1045`
  и `ReplaceSplits:843-881`.
- Сценарий: исходная цена 120, применён сплит 2:1, сохранённая цена 60.
  Удалить все события тикера кнопкой интерфейса. `DeleteSplits` делает только
  `DELETE FROM splits`; цены остаются 60. Затем вновь добавить событие 2:1
  и применить: цена станет 30 вместо 60. `MergeOHLC` также теряет сведения,
  позволяющие привести свежие сырые бары к сохранённой базе цен.
- Причина: восстановление цен добавлено в удаление одного события и замену
  списка, но не в массовое удаление. Это тот же корень AUD-146, новый ID не нужен.
- Исправление `89115c7` сохраняется в истории; этот путь им не закрыт.
  Направление исправления: массовое удаление через ту же транзакционную
  перебазировку цен, что используется при замене списка на пустой.
- Проверка: статическая цепочка вызовов на `990601a`; runtime не выполнялся.

### AUD-168 — OPEN, P1: повтор даты в PATCH сплитов многократно пересчитывает цены

- Код: `httpapi/server.go:1121-1167`, `httpapi/helpers.go:90-103`,
  `store/db.go:994-1021` (все пути относительно `go/internal/`).
- PATCH принимает массив событий без проверки уникальности дат. `UpsertSplits`
  читает `prev` один раз и после `rebaseApplied` не обновляет коэффициент в карте.
- Сценарий: применён коэффициент 2, цена 60. Отправить два события одной даты
  с коэффициентами 3 и 4. Первое даёт 60×2/3 = 40, второе 40×2/4 = 20;
  таблица хранит 4, правильная цена — 120/4 = 30. Даже два одинаковых события
  с новым коэффициентом 3 дают повторный пересчёт вместо одного.
- Это отдельная причина от AUD-146: перебазировка есть, но повторно использует
  устаревшую базу внутри одной транзакции. Аналог `ReplaceSplits` удаляет дату
  из `prev` и откатывается при дубликате первичного ключа; там этот сценарий иной.
- Исправление: отвергать дубли дат либо обновлять текущую базу после каждого
  события. Проверка только по коду `990601a`, исправляющего коммита нет.

### AUD-169 — OPEN, P1: повтор входа после закрытия восстанавливает старую позицию

- Код: `live/trade_record.go:159-188`, `store/positions.go:801-878`,
  `store/positions_migrate.go:182-198`, `live/track.go:619-642`.
- `AttachEntry` ищет только `status='open'` по символу. Защита от повторов
  сравнивает ID только найденной открытой ноги. Если старую позицию уже закрыли,
  создаётся новая структура с `ID = f.OrderID`, после чего `INSERT OR REPLACE`
  перезаписывает закрытую строку этим ID: исчезают дата/цена выхода и прибыль.
  Если по тикеру уже есть новый вход, старое исполнение попадает в новую строку.
- Достижимый порядок: исполнение BUY записано, запись конечного статуса трекера
  не удалась; позиция закрыта через журнал; повтор опроса BUY вновь вызывает
  `AttachEntry`. Между записью исполнения и статуса нет общей транзакции.
- AUD-115 защищает повторы SELL через `claimFillTx`; аналогичной устойчивой
  защиты для BUY нет. Новый корень, а не повтор AUD-115.
- Исправление: учитывать уже записанный ID входа независимо от текущего статуса
  позиции. Проверка только по коду `990601a`, исправляющего коммита нет.
