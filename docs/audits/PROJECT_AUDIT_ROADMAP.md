# Сплошной аудит проекта: расхождения между интерфейсом, конфигом и движком

Read-only проход по всему дереву на `main @ 2297b85`, 2026-09-04.

Это не разбор одного экрана. Здесь искался **класс** дефектов, а не место: интерфейс
что-то утверждает, конфиг что-то хранит, а движок делает другое (или не делает ничего).
Тот же класс, что нашёлся на страницах брокеров — их разбор вынесен в
`BROKER_PAGES_ROADMAP.md` и здесь не дублируется, только перекрёстные ссылки.

Формат задачи: **где → что сейчас → почему неверно → что сделать → чем закрыть**.
Пути от корня репозитория, символы — по именам функций.

Пуш и деплой по этому файлу не запускать — правило в `CLAUDE.md`.

## Как это искалось

Чтобы результат был воспроизводим, а не «Клод опять что-то заметил», — пять
механических проходов. Каждый можно повторить одной командой.

| Проход | Что искали | Команда |
|---|---|---|
| 1 | Ручки SPA, которые никто не зовёт, и эндпоинты, до которых не дотянуться | сверка имён в `go/web/js/api.js` с вызовами `API.*` в `app.js` и с `HandleFunc` в `server.go` |
| 2 | Ключи настроек: кто пишет, кто читает | сверка `name="…"` в `pageSettings` с `settings["…"]` в Go и с дефолтами в `store/db.go` |
| 3 | Правила, продублированные в JS и в Go | grep по константам порогов, режимов капитала, резервов |
| 4 | Мутирующие хендлеры, которые не проверяют результат | `rg '_ = s\.DB\.' go/internal/httpapi` |
| 5 | Инвариант дат из `CLAUDE.md` | grep из самого `CLAUDE.md`, раздел «Как проверять» |

Чего этот проход **не** покрывал, чтобы не создавать ложного ощущения полноты:
корректность самого торгового движка (это `AUTOTRADE_ROADMAP.md`), математику
бэктеста, безопасность и провайдеров данных.

# Класс 1. Интерфейс утверждает то, чего система не делает

## P-1 (P0). `UpsertWatch` затирает открытую позицию при частичном апдейте

**Где.** `go/internal/store/db.go`, `(*DB).UpsertWatch`. Вызывается из
`handleWatchPost` (`POST /api/telegram/watch`) и `handleWatchPatch`
(`PATCH /api/telegram/watch/{symbol}`) в `go/internal/httpapi/server.go`.

**Что сейчас.** Функция — полный upsert строки, а недостающие поля подменяет молчаливыми
дефолтами:
```go
high, _ := w["highIBS"].(float64); if high == 0 { high = 0.75 }
low,  _ := w["lowIBS"].(float64);  if low  == 0 { low  = 0.1  }
thr,  _ := w["thresholdPct"].(float64); if thr == 0 { thr = 0.3 }
open := 0; if v, ok := w["isOpenPosition"].(bool); ok && v { open = 1 }
```
и дальше `ON CONFLICT(symbol) DO UPDATE SET` **все** колонки, включая
`is_open_position`, `entry_price`, `entry_date`, `current_trade_id`, которые берутся из
`w[...]` как есть — то есть `nil`, если их не прислали.

**Почему неверно.** `PATCH` по смыслу частичный. Отправь `{"lowIBS": 0.12}` — и в одной
транзакции:
- `highIBS` вернётся к `0.75`, затерев настроенный порог выхода;
- `thresholdPct` вернётся к `0.3`;
- `isOpenPosition` станет `0` — **открытая позиция помечается закрытой**;
- `entry_price`, `entry_date`, `current_trade_id` обнулятся — **цена и дата входа стёрты**.

Это не гипотеза про будущий код: `POST` с той же функцией уже вызывается из SPA
(`watch-form` на `/watches` шлёт `{symbol, lowIBS: 0.1, highIBS: 0.75}`). Добавь в
мониторинг тикер, который там уже есть и держит позицию, — позиция исчезнет из
`telegram_watches`, а сделка останется в `trades`. Дальше это ловит только
`/api/monitor/consistency`, и то постфактум.

**Что сделать.**
1. Разделить операции. `UpsertWatch` оставить полным upsert-ом для создания;
   добавить `PatchWatch(symbol string, fields map[string]any) error`, который строит
   `UPDATE telegram_watches SET <только присланные колонки> WHERE symbol = ?`.
   Список разрешённых колонок — явный whitelist в коде, не из ключей запроса.
2. `handleWatchPatch` перевести на `PatchWatch`.
3. `handleWatchPost` (создание) сделать идемпотентно-безопасным: если строка уже есть,
   **не** трогать `is_open_position`, `entry_*` и `current_trade_id`. Проще всего — в
   `ON CONFLICT DO UPDATE` перечислять только пороги и `chat_id`.
4. Отличать «поле не прислали» от «прислали ноль». Сейчас `low == 0` означает и то и
   другое, поэтому порог `0` в принципе невыразим. Проверять наличие ключа
   (`v, ok := w["lowIBS"]`), а не значение.

**Чем закрыть.** Go-тест в `go/internal/store`: создать watch с открытой позицией и
непустыми `entry_price` / `current_trade_id`, применить патч только с `lowIBS`,
прочитать строку — изменился ровно `low_ibs`, остальное на месте. Второй тест: повторный
`POST` по существующему символу не сбрасывает `is_open_position`.

## P-2 (P0). Одиннадцать хендлеров глотают ошибку БД и отвечают `ok: true`

**Где.** `go/internal/httpapi/server.go`. Полный список найден `rg '_ = s\.DB\.'`:

| Хендлер | Строка вида |
|---|---|
| `handleWatchDelete` | `_ = s.DB.DeleteWatch(...)` |
| `handleWatchPatch` | `_ = s.DB.UpsertWatch(body)` |
| `handleEMAAlertDelete` | `_ = s.DB.DeleteEMAAlert(...)` |
| `handlePatchTrade` | `_ = s.DB.PatchTrade("trades", ...)` |
| `handleDeleteTrade` | `_ = s.DB.DeleteTrade("trades", ...)` |
| `handlePatchBrokerTrade` | `_ = s.DB.PatchTrade("broker_trades", ...)` |
| `handleDeleteBrokerTrade` | `_ = s.DB.DeleteTrade("broker_trades", ...)` |
| `handleDeleteSplit` | `_ = s.DB.DeleteSplit(...)` |
| `handleDeleteSplits` | `_ = s.DB.DeleteSplits(...)` |
| импорт сплитов | `_ = s.DB.UpsertSplits(ticker, events)` |
| refresh датасета | `_ = s.DB.UpsertSplits(id, hist.Splits)`, `_ = s.DB.UpdateDatasetMetadata(...)` |

Каждый после этого отвечает `200 {"ok": true}`.

**Почему неверно.** SQLite открыт с `MaxOpenConns=1` и WAL — ошибка записи не экзотика:
блокировка, нет места, битая схема после ручной правки. В этот момент интерфейс говорит
«Сохранено» / «Удалено», а данных нет. Для `handlePatchTrade` это особенно плохо: SPA
закрывает модалку и не перечитывает список, так что расхождение всплывёт только на
следующей загрузке страницы — или не всплывёт вовсе.

Хуже всего сочетание с P-1: `handleWatchPatch` и молча теряет поля, и молча теряет ошибку.

**Что сделать.** Механически, по одному шаблону:
```go
if err := s.DB.DeleteWatch(sym); err != nil {
    writeJSON(w, 500, map[string]any{"error": err.Error()})
    return
}
writeJSON(w, 200, map[string]any{"ok": true})
```
Ровно как это уже сделано в `handleWatchPost` и `handlePutSettings` — образец в том же
файле, ничего изобретать не надо. Исключений не делать: если где-то ошибка действительно
не важна, написать это комментарием, а не подчёркиванием.

На стороне SPA заодно проверить, что тосты «Сохранено» стоят **после** успешного ответа,
а не рядом с вызовом. Точки, где надо посмотреть: обработчики `data-edit-bt`,
`data-bd`, `data-dw`, `#set-form`.

**Чем закрыть.** Тест с DB-заглушкой, возвращающей ошибку: каждый из перечисленных
эндпоинтов отвечает `500`, а не `200`. Проще всего — таблица `{method, path}` и один
подтест на строку.

## P-3 (P1). UI печатает `≤` и `≥` там, где сравнение строгое

**Где.** `go/web/js/app.js`: `pageWatches` (колонки порогов), `pageBroker` — вкладка
«Мониторинг» (колонка `Threshold`).

**Что сейчас.**
```js
<td>≤ ${(w.lowIBS ?? 0.1).toFixed(2)}</td>
<td>≥ ${Number(w.highIBS ?? 0.75).toFixed(2)}</td>
```

**Почему неверно.** `CLAUDE.md` формулирует это как инвариант: «Thresholds are strict on
both sides: entry `ibs < lowIBS`, exit `ibs > highIBS` … An IBS of exactly `0.10` is not
an entry». Движок так и делает — через `ibs.IsEntrySignal` / `ibs.IsExitSignal`. Даже
подсказка на странице настроек говорит правильно: «Сравнение строгое с обеих сторон:
ровно 0.10 — это не вход». А таблица мониторинга рядом печатает `≤ 0.10`. Пользователь,
который смотрит на IBS `0.100` и на `≤ 0.10`, ждёт входа, которого не будет.

**Что сделать.** Заменить на `< ` и `> ` в обеих таблицах. Заголовки колонок сделать
однозначными: «Вход, IBS <» и «Выход, IBS >» вместо `Threshold`.

**Чем закрыть.** `rg '≤|≥' go/web/js/app.js` — ни одного вхождения рядом с IBS.

## P-4 (P1). Раскраска IBS идёт по хардкоду, а не по порогам тикера

**Где.** `go/web/js/app.js`, `pageBroker`, вкладка «Мониторинг»:
```js
const ibsCls = ibs == null ? '' : (ibs < 0.10 ? 'text-emerald-600' : (ibs > 0.75 ? 'text-red-600' : ''));
```

**Почему неверно.** В той же строке таблицы рядом лежат `w.lowIBS` и `w.highIBS` — и
именно они решают на самом деле (`watchThresholds` в `go/internal/live/config.go`: порог
тикера перекрывает глобальный). Тикер с `lowIBS = 0.15` и текущим IBS `0.12` — это вход,
а ячейка будет серой. И наоборот: `lowIBS = 0.05`, IBS `0.08` — зелёная ячейка без
входа. Цвет здесь не украшение, по нему принимают решение глазами.

**Что сделать.** Считать по строке:
```js
const lo = Number(w.lowIBS ?? (ac.lowIBS ?? 0.1));
const hi = Number(w.highIBS ?? (ac.highIBS ?? 0.75));
const ibsCls = ibs == null ? '' : (ibs < lo ? 'text-emerald-600' : (ibs > hi ? 'text-red-600' : ''));
```
Строгие сравнения — те же, что в `ibs.IsEntrySignal` / `IsExitSignal`. Дефолт брать из
`state.autoConfig`, а не из литерала — см. P-13.

**Чем закрыть.** Поставить тикеру `lowIBS = 0.20` и убедиться, что IBS `0.15` красится
зелёным, а не серым.

## P-5 (P1). `brokerDecisions` посчитан специально для UI, но SPA его не читает

**Где.** Считает `executeAll` в `go/internal/live/execute_all.go` (`ev.BrokerDecisions`),
структура — `EvalResult` в `go/internal/live/autotrade.go`. Читает только
`go/internal/live/telegram.go`. В `go/web/js/app.js` — ни одного упоминания.

**Что сейчас.** Плитка «Последнее решение» на странице брокера берёт
`st.state.lastResult.decision` — единственное «витринное» решение, которое `Evaluate()`
считает по книге **Webull**: `e.booksFor("webull", e.defaultBroker(), ...)`.

**Почему неверно.** Комментарий в коде рядом с полем прямо описывает задачу, которую
поле должно было решить: «this is the real per-broker picture executeAll acted on, so the
UI does not show one broker's decision as if it applied to all of them». Серверная
половина сделана, клиентская — нет. На `/robinhood` плитка «Последнее решение» показывает
решение Webull, включая символ и причину.

**Что сделать.** В `pageBroker` читать
`st.state.lastResult.brokerDecisions?.[kind]` и падать на общий `decision` только когда
per-broker записи нет (старый прогон до этой правки). Причины показывать как есть —
`broker_disabled`, `NEEDS_REAUTH`, `allowNewEntries_false` — с русской расшифровкой,
той же, что в P-7 из `BROKER_PAGES_ROADMAP.md`. Один словарь причин на весь SPA, не два.

**Чем закрыть.** Прогнать `POST /api/autotrade/evaluate` при разных флагах брокеров и
убедиться, что две страницы показывают разные причины.

# Класс 2. Ручки, которые ни на что не влияют

## P-6 (P1). «Окно исполнения, сек» не влияет ни на что

**Где.** Настройка `executionWindowSeconds`: поле `autoWindow` в `pageSettings`,
санитайзер в `go/internal/live/config.go`, дефолт `90` в `go/internal/store/db.go`,
гейт `(*Engine).outsideExecutionWindow` в `go/internal/live/autotrade.go`.

**Что сейчас.** Гейт применяется по условию `executionWindowApplies(trigger)`:
```go
switch trigger {
case "manual_execute", "scheduler":
    return true
}
return false
```
Дальше — факты, каждый проверяется одним grep:
- `"scheduler"` как значение триггера **не передаётся нигде** (`rg '"scheduler"' go/internal`
  даёт только эту строку определения);
- `"manual_execute"` приходит только из `handleAutoExecute` (`POST /api/autotrade/execute`);
- `API.execute` в `go/web/js/api.js` объявлен, но **не вызывается ни разу** в `app.js`;
- реальный торговый путь — `telegram_t1` (`executeWindow(w, "telegram_t1")` в
  `go/internal/live/telegram.go`), и он через это окно осознанно не проходит.

**Почему неверно.** Настройка выставляется, валидируется, хранится и показывается на двух
экранах, но в проде не применяется ни разу. Хуже: её подсказка описывает несуществующий
элемент интерфейса — «планировщик и кнопка «Исполнить» отправят заявку, только если…».
Кнопки «Исполнить» в SPA нет (`rg 'Исполнить' go/web/js` находит только этот же текст).
Человек читает про предохранитель, которого нет.

**Что сделать.** Выбрать одно из двух и не оставлять как есть:
- **(а)** вернуть кнопку «Исполнить» на вкладку «Автоторговля» страницы брокера — она
  зовёт `API.execute()`, окно становится настоящим предохранителем ручного запуска.
  Кнопка отправляет **реальные заявки**, так что ей нужно подтверждение, как у
  `askDelete`, и явная подпись, что это боевой ордер;
- **(б)** удалить настройку целиком: поле из формы, `executionWindowSeconds` из
  `autoTradingNumberFields` и из дефолтов, `outsideExecutionWindow` и
  `executionWindowApplies` из движка, обе подсказки из UI.

Рекомендация — **(а)**: ручной прогон в T-1, когда планировщик не сработал, это реальный
сценарий, а окно — единственное, что защищает от случайного нажатия среди дня. Но решение
за владельцем: (б) честнее, чем оставить как сейчас.

**Чем закрыть.** Либо кнопка есть и `rg 'API\.execute' go/web/js/app.js` находит вызов,
либо `rg 'executionWindow' go` не находит ничего.

## P-7 (P1). Настройки комиссий не читает никто

**Где.** `go/web/js/app.js`, `pageSettings`, вкладка «Общие»: `commissionType`
(три радиокнопки), `commissionFixed`, `commissionPercentage`.

**Что сейчас.** Поля отрисованы, значения сохраняются в `settings`, и на этом всё:
- в Go ключи `commissionFixed` / `commissionType` не встречаются нигде;
- `commissionPercentage` встречается **только** в `go/internal/httpapi/ui_test.go` —
  и там тест прямо запрещает их использовать:
  ```
  if strings.Contains(dsBlock, "commissionPercentage") || strings.Contains(dsBlock, "st.commission") {
      t.Fatal("defaultStrategy must not inject settings commission")
  }
  ```
- бэктест считает комиссию из `strategy.RiskManagement.Commission`, а дефолт стратегии —
  `Commission{Type: "percentage", Percentage: 0}` (`go/internal/types/types.go`);
- в `app.js` эти ключи нигде не читаются, кроме самой формы.

**Почему неверно.** Отключение — осознанное и закреплено тестом. Не убрали только сам
экран. Пользователь выставляет комиссию 0.1%, сохраняет, видит «Сохранено» и считает, что
бэктест теперь с комиссией. Он без комиссии.

**Что сделать.** Удалить три поля из вкладки «Общие» и убрать `commissionFixed` /
`commissionPercentage` из принудительного `Number(...)` в обработчике `#set-form`.
Ключи из БД можно не вычищать — они безвредны, но упомянуть в коммите, что строка
`settings` их ещё содержит.

Если комиссии нужны по существу — это отдельная задача «прокинуть комиссию из настроек в
`defaultStrategy`», и начинать её надо со снятия того самого запрета в `ui_test.go`,
осознанно. Не смешивать с удалением экрана.

**Чем закрыть.** `rg -i commission go/web/js` — пусто.

## P-8 (P1). Пороги тикера названы главными, но задать их негде

**Где.** Текст в `pageSettings`: «У каждого тикера на странице «Мониторинг» есть
собственные пороги, и они важнее этих: здесь задаётся только значение по умолчанию».
Форма добавления в `pageWatches`:
```js
await API.addWatch({ symbol: e.target.symbol.value, lowIBS: 0.1, highIBS: 0.75 });
```

**Что сейчас.** Движок действительно предпочитает пороги тикера
(`watchThresholds` в `go/internal/live/config.go`). Но в SPA:
- нет ни одного элемента для их **редактирования** — таблицы `/watches` и вкладки
  «Мониторинг» только показывают;
- при добавлении тикера пороги жёстко `0.1` / `0.75`, а не дефолты из `autoConfig`.

**Почему неверно.** Два следствия. Первое: «главные» пороги у всех тикеров всегда
одинаковы и равны литералу из `app.js`. Второе, важнее: пользователь меняет пороги по
умолчанию в настройках на `0.12` / `0.70`, добавляет тикер — и тикер приходит с `0.1` /
`0.75`, молча перекрывая только что настроенное значение. Настройка «по умолчанию»
не действует ни на что, потому что перекрывающее значение проставляется всегда.

**Что сделать.**
1. При добавлении не слать пороги вовсе — пусть сервер подставит свои
   (после P-1 это будет корректно), либо слать текущие
   `state.autoConfig.lowIBS / highIBS`. Второй вариант честнее: то, что видно в
   настройках, и попадает в новый тикер.
2. Добавить редактирование: на `/watches` — кнопка «Пороги» у строки, модалка с двумя
   полями, `PATCH /api/telegram/watch/{symbol}`. **Делать только после P-1**, иначе
   каждое редактирование будет закрывать открытую позицию.
3. В строке показывать, откуда порог: свой у тикера или унаследованный дефолт.

**Чем закрыть.** Меняем дефолты в настройках → добавляем тикер → у него новые пороги.
Редактируем пороги у тикера с открытой позицией → позиция на месте (тест из P-1).

# Класс 4. Мусор в общем хранилище

## P-15 (P1). Сохранение автоторговли сорит чужими ключами в `/api/settings`

**Где.** `go/web/js/app.js`, обработчик `submit` формы `#set-form`; приёмная сторона —
`handlePatchSettings` в `go/internal/httpapi/server.go`.

**Что сейчас.** Обработчик собирает `body` из всего `FormData`, отправляет
автоторговлю в свой эндпоинт, а затем вычищает из `body` ограниченный список ключей:
```js
for (const k of ['autoEnabled', 'autoQuote', 'entryCapitalMode', 'autoAllowEntries', 'autoAllowExits',
  'autoLowIBS', 'autoHighIBS', 'autoWindow', 'autoSlippage']) delete body[k];
```
и шлёт остаток в `PATCH /api/settings`. В списке нет:
- `autoEntryReserve` — уезжает в настройки строкой вида `"0.50"`;
- `webullEnabled`, `webullAllowEntries`, `webullAllowExits`, `robinhoodEnabled`,
  `robinhoodAllowEntries`, `robinhoodAllowExits` — это `<input type="checkbox" name="…">`
  внутри той же формы, поэтому отмеченные приезжают в `FormData` как `"on"`.

Ключи `autoAllowEntries` / `autoAllowExits` в списке, наоборот, лишние — таких полей в
форме давно нет.

`handlePatchSettings` кладёт **любой** ключ в общий объект настроек
(исключены только `autoTrading`, `api`, `telegram`), а `(*DB).SaveSettings` сериализует
объект целиком в JSON-блоб — whitelist-а нет ни на одном уровне.

**Почему неверно.** В строке настроек навсегда оседают `webullAllowEntries: "on"` и
подобное — вторая, устаревающая копия флагов, которые на самом деле живут в
`autoTrading.brokers`. Дальше кто-нибудь (человек или код) прочитает эту копию и получит
состояние на момент последнего сохранения формы. Ровно тот же механизм, что описан в
`BROKER_PAGES_ROADMAP.md` → B-6, только там дубль попадает в торговый конфиг, а тут —
в настройки. Плюс `state.settings` на клиенте засоряется тем же мусором через
`state.settings = { ...state.settings, ...body }`.

**Что сделать.**
1. Перевернуть логику: не «удалить известные лишние», а **отправлять только известные
   нужные**. Собрать явный список ключей вкладки «Общие» / «API» и класть в `body`
   только их. Тогда добавление поля в форму автоторговли не сможет протечь в настройки.
2. Добавить whitelist в `handlePatchSettings`: набор допустимых ключей настроек уже есть
   де-факто — это ключи дефолтов в `store/db.go`. Неизвестный ключ отвергать `400`,
   а не сохранять молча.
3. Отдельным коммитом — одноразовая чистка: удалить из строки настроек ключи, которые
   не входят в whitelist. Делать только после п. 2, иначе они вернутся.

**Чем закрыть.** Go-тест: `PATCH /api/settings` с ключом `webullAllowEntries` отвечает
`400` и не меняет строку. Руками: сохранить вкладку «Автоторговля», затем
`GET /api/settings` — никаких `*Enabled` / `*Allow*` / `autoEntryReserve`.

## P-16 (P1). Пороги тикера не валидируются на сервере

**Где.** `handleWatchPost` / `handleWatchPatch` → `(*DB).UpsertWatch`.
Для сравнения — `sanitizeAutoTradingConfig` в `go/internal/live/config.go`.

**Что сейчас.** Глобальные пороги защищены: значения зажимаются в `[0, 1]`, а при
`low >= high` санитайзер откатывает **оба** к предыдущим или к
`ibs.DefaultLowIBS` / `DefaultHighIBS`. Пороги тикера не проверяются никак: что прислали,

**Почему неверно.** Пороги тикера приоритетнее глобальных (`watchThresholds`), то есть

остановлено, а `handleWatchPost` принимает `map[string]any` прямо из тела запроса.

**Что сделать.** Вынести проверку порогов в одну функцию (например,

`sanitizeAutoTradingConfig`, и из обоих watch-хендлеров. Правило одно: зажать в `[0, 1]`,
при `low >= high` — отказ `400` для явно присланной пары (в отличие от конфига, где
исторически принят молчаливый откат; для нового API честнее ошибка).

**Чем закрыть.** Тест: `POST /api/telegram/watch` с `lowIBS = 0.9, highIBS = 0.5`
отвечает `400`, строка не создана.

**Где.** `go/internal/providers/client.go` (разбор `Time Series (Daily)` Alpha Vantage) и

**Чем закрыть.** Grep из `CLAUDE.md` возвращает только места, каждое из которых —
