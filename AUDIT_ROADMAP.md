## 1. Короткий вердикт

Кодовая база заметно «повзрослела» относительно обоих прошлых аудитов: большая часть P0/P1 из
`ROADMAP.md`/`AUTOTRADE_ROADMAP.md` по текущему дереву **закрыта** (мьютекс+снапшот брокеров,
измерение «брокер» в журнале, листинг-lag → `execution_unknown`, аренда T-1 и
`t1_execution_finished`, дедлайн T-1 с пробросом ctx в брокерские вызовы, classified-здоровье
токенов, `/healthz`+`/readyz`, requireJSON почти везде, PruneAutotradeLogs, rate limit, origin-гейт,
CSP, redact секретов, `_ = readJSON` остался только в семействе `calc`). Это подтверждается кодом, а
не только комментариями.

При этом найдено **свежее и остаточное**, часть — уровня денег/операций (раздел 3). Главные:

1. **Уведомления об исполнении захардкожены на «Webull»** даже для трекеров Robinhood
   (`track.go:486,491`, `trade_record.go:148,255`) — оператор пойдёт проверять не того брокера.
2. **`pollTracker` при отсутствии именованного брокера молча падает на `defaultBroker`** — трекер
   Robinhood может опрашиваться через Webull, и «not found» от чужого брокера способен
   финализировать трекер как `terminal_absent` (удаление строки журнала по чужому ответу).
3. **Импорт календаря Webull доверяет полноте ответа**: отсутствующие будни в запрошенном окне
   навсегда записываются как «holiday» (только добавляются, никогда не удаляются), а
   `webullCoverageThrough` выставляется на конец окна независимо от того, сколько дней реально
   вернул Webull. Ложный holiday = молчаливый пропуск T-11/T-1 и актуализации в настоящий торговый
   день (док-разбор — в разделе 6.6).
4. **`Consistency`/страница «Мониторинг» видят только первую открытую `broker_trades` и только
   позиции `defaultBroker`** — при двух открытых позициях на двух брокерах вторая не участвует в
   сверке; «сверка» рапортует зелёное при невидимой второй позиции.
5. **Guard pending-трекера fail-open на ошибке БД**: `AnyPendingTrackerFor`/`listBlockingTrackers`
   при ошибке чтения возвращают nil → submitEvaluated разрешает повторную заявку, хотя первая могла
   уйти (остаток P1-7, теперь на контуре дублей).
6. **Псевдо-версионирование схемы**: `schema_meta.version` всегда пишется =1, реальной миграционной
   лестницы нет; ensureColumn закрывает только 10 колонок из ~30 добавленных после первого
   CREATE TABLE — любая БД, созданная старой версией, ломается в рантайме SQL-ошибками (P2-3 всё
   ещё открыт, просто прод сегодня «случайно сходится»).
7. **Фейковые «Early close»-подписи**: `ShortDayName` помечает `12-24` и `07-03` как сокращённый
   день всегда, но когда 25.12 или 04.07 выпадает на субботу, наблюдаемый выходной — пятница
   (24.12/03.07), т.е. это полное закрытие, а не early close (2020, 2026). Плюс Juneteenth считается
   праздником для лет **до 2022**, когда биржа в этот день работала (сказывается на fallback-
   календаре без импорта).
8. **Окна T-11/T-1 по-прежнему живут в одном последовательном тике** 20 c: задержка тика >60 c
   вокруг минуты 11/1 молча съедает сообщение дня (P1-8 остаётся частично открытым; lease спасает
   только от дублей T-1, а не от пропуска).
9. **UI/UX**: полный пересбор shell при каждом `renderPage()`, `authCheck()` на каждый переход
   (сеть + рендер), тосты/модалки перерисовывают `#overlay-root` целиком; часть страниц глушит
   ошибки API в пустые массивы (`/webull`, `/robinhood`); раздел 5.
10. **Доки/env разошлись с кодом**: `.env.example` содержит мёртвые переменные Node-стека
    (`SETTINGS_FILE`, `WATCHES_FILE`, `SPLITS_FILE`, `TRADE_HISTORY_FILE`, `DB_DIR`, `TLS_CA`,
    `DOMAIN`, `ADMIN_USERNAME` и т.п.), но не содержит реально читаемых `WEBULL_ENABLE_LIVE_TEST_BUY`,
    `WEBULL_LIVE_TEST_BUY_MAX_QUANTITY`, `ROBINHOOD_ENABLE_LIVE_TEST_BUY`, `FRONTEND_ORIGIN`,
    `WEBULL_TOKEN_EXPIRES_AT`; `go/INVENTORY.md` не знает про robinhood-oauth, `brokers/health`,
    trackers-resolve и `/readyz`.

Сильных дефектов расчётов (бэктест/IBS/EMA/опционы/сплиты) в этом проходе не найдено — контуры
покрыты golden-тестами, прошлый аудит провёл сверку; в этот проход точечно перепроверены модули
A1 (раздел 3.7). Блокеров уровня «не включать live» из **новых** находок нет, но пункты 1–5
рекомендуется закрыть до торговли на двух брокерах одновременно.

## 2. Легенда приоритетов

- **P0 — деньги/данные**: риск двойной/потерянной заявки, неверной записи журнала, тихого пропуска
  торгового дня, расхождения реальной и показанной позиции.
- **P1 — ложь о состоянии**: система сообщает/показывает не то, что есть (оператор действует неверно).
- **P2 — качество/эксплуатация**: миграции, доки, обработка ошибок, перф.
- **P3 — глубина защиты/мелочи**: security-гигиена, косметика, UX-детали.
- **[R]** — требует runtime/прод-проверки, по статике не доказывается.

## 3. Находки по подсистемам

### 3.1 Live-движок: исполнение, трекеры, журнал

**AU-P0-1. Уведомления о fill/reject/частичном/slippage жёстко говорят «Webull»** (новое, остаток
мультиброкерности).
- `track.go:486` — `<b>Webull исполнено</b>`; `track.go:491` — `<b>Webull статус заявки</b>`;
  `trade_record.go:148` — «Webull: частичное исполнение»; `trade_record.go:255` — «Webull:
  проскальзывание … bps».
- Трекер уже знает брокера (`t["broker"]`, строка пишется в `SaveOrderTracker`), а в
  `submitEvaluated` для ambiguous-сообщения брокер подставляется правильно — то есть это просто
  недоделка, а не архитектурное ограничение.
- Последствие: при исполнении на Robinhood оператор получает «Webull исполнено», идёт проверять
  Webull-кабинет; при частичном/сложном дне это съедает драгоценные минуты.
- Чинится: параметризация `brokerLabel()` во всех 4 местах + тест на текст сообщения.

**AU-P0-2. `pollTracker`: чужой брокер опрашивается через defaultBroker** (новое).
- `track.go:281-288`: `br := e.defaultBroker()`; имя брокера из трекера учитывается только если
  `BrokerNamed(name)` вернул не-nil. Если брокер отвязан (reconnect/рестарт с пустой БД,
  detach при disconnect), трекер Robinhood молча опрашивается через Webull.
- `OrderDetail` Webull на чужой id возвращает «не нашли»; для Robinhood-адаптера это
  `ErrOrderUnavailable` (специально, из-за listing lag), но generic-брокеры/тесты и Webull-путь
  могут вернуть not-found → `finalizeTracker(t,"terminal_absent")` → `deletePhantom` удалит
  открытую строку журнала по ответу **другого** брокера.
- Фикс: если `broker` в трекере задан и `BrokerNamed` его не знает — не опрашивать вовсе, а
  помечать трекер `execution_unknown`/алертить «брокер не подключён», никогда не падать на
  default.

**AU-P0-3. Guard pending-трекера fail-open на ошибке БД** (остаток P1-7, теперь на контуре дублей).
- `submitEvaluated` (`execute_all.go:113-140`) спрашивает `AnyPendingTrackerFor` /
  `FindPendingTrackerBroker`; обе функции (`store/robinhood.go:144-191`,
  `store/live_persist.go`) при `err != nil` возвращают `nil`.
- При сбое чтения (диск, WAL-локи, повреждение) первая заявка могла уйти, трекер не виден →
  вторая заявка с новым id уходит без каких-либо признаков проблемы.
- Фикс: различать «нет pending» и «БД не ответила»; во втором случае — блокировать вход с
  `journal_unavailable` (механика уже есть в `Evaluate` и `executeAll`).

**AU-P0-4. `Consistency()` видит только одну открытую broker-позицию и только default-брокера**
(новое, остаток P0-3 из прошлого аудита).
- `monitor.go`: `openB := store.OpenBrokerTradeFor(rows, "")` — первая открытая строка любого
  брокера; `held := e.liveHeldSymbols()` → `heldSymbolsOn(e.defaultBroker())` (webull).
- Сценарий: открыта позиция на Webull **и** на Robinhood. Сверка сравнивает monitor-строку только
  с первой broker-строкой (порядок — как вернул `ListTrades`), вторая позиция в «Мониторинг» не
  видна вообще; позиция только на Robinhood не порождает `live_broker_position_without_journal`.
- Это диагностическая (не торговая) дыра, но именно на неё смотрит оператор перед T-1 и именно
  её показывает страница сверки. Торговые гейты (`booksFor` в `execute_all.go`) брокеров
  различают, поэтому severity P0, а не P0-деньги.

**AU-P1-1. T-1: окно «один тик в минуту» без страховки от пропуска** (подтверждение P1-8, частично
открыт).
- `scheduler.go:139-170`: единственный тикер 20 c; все джобы — последовательно в `RunTick`.
  `RunTelegramAggregation` срабатывает только при `until==11`/`until==1` (`scheduler.go:404-412`).
- Если предыдущий `RunTick` (PollTrackers/health/Actualize/календарь) занял >60 c или тик «проскочил»
  минуту, сообщение T-11/T-1 за день не уходит: состояние `aggregate_send_state` не знает, что окно
  прошло (для T-1 lease защищает от дублей, но не от пропуска; для T-11 нет и lease).
- Частичные смягчения уже есть: `MarkT1ReportSent` ставится после успешной отправки, при сбое
  Telegram репорт повторяется со следующим тиком той же минуты.
- Фикс: джоб-очередь с дедлайнами на джоб; окно T-11/T-1 должно резервироваться до наступления
  (claim за N минут), а пропуск — алертить.

**AU-P1-2. `Consistency`/`Reconcile` и «позиция в журнале vs позиция брокера»: monitor-проекция
одна на всех** (связано с AU-P0-4). Таблица `trades` («m-…») не имеет измерения брокера, при
двух брокерах обе ноги ссылаются на одну monitor-строку или создают конфликт
`linked_monitor_trade_*`. Прошлый аудит требовал измерения «брокер» в позиции; в `broker_trades`
оно есть, в monitor-проекции — нет. [R] сценарий «два брокера, две позиции» прогнать на
`-race`/fault-injection.

**AU-P1-3. Выход по не-подтверждённой цене**: `fillPriceFrom` может вернуть 0 → `recordFill`
пишет `unconfirmedPrice=true`, но всё равно создаёт/закрывает строку журнала с ценой 0
(`trade_record.go`), а `closeTradeWithPnL` посчитает PnL по нулевой цене. Частично это уже
покрыто P2-1 прошлого аудита (фиктивная цена); сейчас код помечает `fill_price_unconfirmed` в
логах, но **не помечает саму сделку** — в UI цена 0/$0 выглядит как реальная. Предлагается
`entry_price=NULL` + бейдж «цена не подтверждена» до ручного ввода.

**AU-P2-1. `reduceOpenQuantity` и апдейты журнала пишутся с игнорированием ошибок SQL**
(`trade_record.go:176-177, 205-207, 278`): `_, _ = e.DB.SQL.Exec(...)`. При сбое записи журнал
тихо расходится с брокером, а Consistency это потом не увидит (см. AU-P0-4). Учитывая
`MaxOpenConns(1)`+WAL, вероятность мала, но контур денежный — стоит логировать и поднимать
блокировку как для трекера.

**Подтверждено как закрытое (по коду):** P0-1 (снапшот брокеров под `mu`, `AttachBroker`/
`DetachBroker` блокируются, `submitEvaluated` получает брокера параметром), P0-2
(`execution_unknown` снимается только оператором через `ResolveTracker`, `track.go:420+`, роут
`POST /api/autotrade/trackers/{id}/resolve`), P0-4 (listing-lag: `ErrOrderUnavailable` +
`ListingLagWait` + `markExecutionUnknown`), P0-5 (lease T-1 + `t1_execution_finished` +
`MarkT1ReportSent` после отправки), P1-1 (дедлайн T-1: `execWindow`/`attemptContext`/ctx в
брокеры), P1-2 (`trackerPersistFail` + `ClearTrackerPersistBlock` + роут), P0-6 (оба брокера
проверяют тело ответа на `client_order_id`, `webull_broker.go:100-137`,
`robinhood_broker.go:96-118`).

### 3.2 Брокеры

**Webull (`live/webull_broker.go`, `webull/client.go`)**
- Код размещения зрелый: свой `client_order_id`, проверка эха id (`order_place_id_mismatch` →
  Ambiguous), MARKET/DAY/CORE захардкожены осознанно, `ResolveInstrumentID` перед заявкой, qty для
  SELL допускает дробь (`formatOrderQuantity`), BUY — целые.
- Остаточное: **частичное исполнение входа не «дозакрывается»** (см. P1-9 прошлого аудита) — при
  `partially_filled` вход журналируется частичным количеством и повторный добор остатка не
  отправляется; конвергенция происходит только если брокер сам доисполнит. Для стратегии «вся
  позиция по сигналу» недобор = уменьшенная позиция с полным IBS-риском. [R] проверить политику
  Webull по остатку.
- `LiveBroker.token()` отдаёт DB-токен, клиент берёт его как функцию — ок; `EnvBrokerDB(nil)` без
  ключей возвращает nil → `CanSubmit` и гейты это учитывают.

**Robinhood (`live/robinhood_broker.go`, `robinhood/*`)**
- Адаптер поверх MCP-тулов: tradability → review (blocking-алерт) → place; тело ответа проверяется
  (`recognizableRobinhoodOrder`), rejected/cancelled не считаются Submitted; ref_id генерируется на
  стороне движка (`asUUID`).
- **AU-P2-2.** `agenticAccount()` кэширует аккаунт в памяти и **не читает** сохранённый из БД
  `account_number` при старте — при каждом рестарте процесса первый вызов любого метода делает
  дополнительный `get_accounts`. Не баг, но лишний сетевой вызов в контуре T-1 (уже учтено
  дедлайном). [R]
- **AU-P2-3.** `CancelOrder(clientOrderID)` шлёт в `cancel_equity_order` `order_id=clientOrderID` —
  вызывается из `cancelOpenOrdersBeforeEntry` с id из списка открытых заявок (это настоящие id
  Robinhood), т.е. контракт соблюдается, но название параметра и отсутствие `asUUID` здесь
  хрупки: любой другой будущий вызов с нашим ref_id молча уйдёт неверным. Унифицировать.
- **AU-P2-4.** Robinhood `OrdersByState(all=false)` и `OrderDetail` тянут **весь** список заявок
  (`get_equity_orders`) и фильтруют на клиенте; при большом объёме истории это медленно и
  увеличивает шанс усечения страницы — ровно тот класс проблем, для которого в Webull уже сделан
  listing-lag-механизм. Проверить пагинацию тула. [R]
- Остальное (OAuth PKCE, pending-state, revoke) выглядит аккуратно; полный разбор `robinhood/service.go`
  и `mcp.go` не выполнялся — вынести в Phase 1 (раздел 8).

### 3.3 Планировщик, календарь, актуализация

**AU-P0-5. Календарный импорт может навсегда записать будни как праздники** (новое).

### 6.1 Тик планировщика
```
каждые 20 c (один поток):
  today = TodayNYSE(now)
  if торговый день и покрытие календаря НЕ истекло:
     if минут до закрытия ∈ [10..12] или [0..2]:

         if до закрытия == 1  → T-1 цикл (см. 6.2)

**Несоответствия:** (а) все джобы в одном потоке без дедлайнов — тяжёлый джоб двигает окна

определяется по импортированному календарю + расчётному fallback, где Juneteenth считается
праздником до 2022 (AU-P2-5).

  MarkT1ExecutionFinished(только если recBlock == nil)
текст T-1 → Telegram
if отправлено → MarkT1ReportSent
```
**Несоответствия/риски:** (а) если выход исполнился через 6–40 c (медленный fill), повторный вход в
этом же цикле уже не делается — вход дня теряется, хотя заявка физически ещё успела бы (это
осознанный компромисс «fill-бюджет 5 c», стоит показать в UI/логах явно); (б) crash между
`MarkT1ExecutionFinished` и `MarkT1ReportSent` = день с исполненной заявкой без отчёта; при
рестарте отчёт переотправится (execDone-ветка), но текст будет по «новой» Evaluate — ок, но
зафиксировать в тесте; (в) при `blocking != nil` заявки не шлются, а `MarkT1ExecutionFinished`
**не** ставится — следующий тик той же минуты повторит полный reconcile-цикл (это by-design
retry, но только пока минута не ушла).

### 6.3 Отправка заявки с идемпотентностью (placeMarket)
```
for attempt 1..3:
  if дедлайн(T-1) истёк → abort + алерт оператору
  cid = новый client_order_id
  res = broker.PlaceMarketCfg(cid)      // ctx = остаток бюджета
  if res.Submitted → return ok
  landed, queryFailed, detail = orderLanded(cid)  // спросить брокера по cid
  if queryFailed → return AMBIGUOUS (трекер заводится, повтор НЕ шлём)
  if landed:
      if статус rejected/cancelled → return rejected (повтор НЕ шлём)
      return ok-as-landed
  sleep 750 мс; повтор с новым cid
```
**Несоответствия:** (а) синхронный отказ брокера (например, «недостаточно средств»), при котором
заявка **не** листится, выглядит как «не landed» → ещё 2 повтора с новыми cid (3 реальные попытки
вместо 1); для T-1 это сжигает бюджет. Различать детерминированный отказ (по коду ошибки) и
транзиентный. (б) `orderLanded` для Robinhood: not-found в списке = `ErrOrderUnavailable`
(осознанно, listing lag) — но тогда после **любого** сбоя отправки у Robinhood всегда Ambiguous,
повторов не будет вовсе; проверить, что rejected-заявки Robinhood попадают в выдачу
`get_equity_orders` (иначе rejected не распознается как rejected). [R]

### 6.4 Трекер и журнал
```
pollTracker(t):
  br = BrokerNamed(t.broker); if нет → br = defaultBroker      // ← AU-P0-2!
  detail = br.OrderDetail(cid)
  if not-found → finalize(terminal_absent) → deletePhantom      // риск по чужому брокеру
  if unavailable(lag) → через 60 c → execution_unknown (блок входов до ручного resolve)
  if final (filled/rejected/cancelled/…) → finalizeTrackerStatus
finalizeTrackerStatus:
  recordFill(...)          // журнал: entry → broker_trades + trades("m-…")
  SetOrderTrackerStatus(final)
  Telegram «Webull исполнено/статус»                          // ← AU-P0-1!
```
**Несоответствия:** (а) см. AU-P0-2 (чужой брокер); (б) см. AU-P0-1 (чужой бренд в сообщении);
(в) `recordFill` для entry при `partially_filled` пишет строку с фактическим qty, но добор не
контролируется (P1-9 остаток); (г) SQL-апдейты журнала без проверки ошибок (AU-P2-1).

### 6.5 Решение и исполнение по брокерам (Evaluate → executeAll)
```
Evaluate():  // единая оценка
  quotes по universe = мониторинг(+символ открытой позиции)
  open/held по defaultBroker (для сводки)
  decide: exit если open и IBS>high; entry — тикер с минимальным IBS<low
executeAll(w, ev, snaps):
  для каждого брокера из снапшота:
     enabled/allowEntry/allowExit = brokerFlags(cfg, имя)
     if health NEEDS_REAUTH/MISSING → skip
     open, held = книги ЭТОГО брокера (журнал broker_trades по имени)
     action = decideLiveAction(...)   // своё решение на каждый брокер
     if entry → guard pending-трекер (fail-open на ошибке БД — AU-P0-3)
     submitEvaluated(w, ..., br)
```
**Несоответствия:** торговые гейты брокеров корректны и разведены; диагностическая Consistency —
нет (AU-P0-4). fail-open на ошибке чтения pending — AU-P0-3.

### 6.6 Календарный импорт
```
start = coverage+1 (или today); end = start+29
items = Webull.CalendarDays(start,end)
if items пусто → ошибка
for день ∈ [start..end], если будний:
    if день НЕ в items:
        holidays[год][ммдд] = HolidayName(день)   // навсегда; удаления нет
    else if тип == HALF_DAY: shortDays[...] = ...
coverageThrough = end; save
```
**Несоответствие:** предположение «Webull вернул полное окно» не проверяется; хвост окна, который
Webull ещё не опубликовал (или ответ обрезан), превращается в фейковые праздники, и это
необратимо без ручного PATCH (AU-P0-5). Плюс `cov >= "2000-01-01"` — строковое сравнение корректно
для YYYY-MM-DD.

### 6.7 Сайзинг
```
entry: funds = max(cash, NLV−Σпозиции) × multiplier(режим)
       funds = min(funds, buyingPower)
       reserve = max(2.2%|0, minReserve 0.5%, entryReservePct, maxSlippageBps/10000)
       qty = floor(funds × (1−reserve) / price); если 0 → ошибка
exit:  qty = позиция брокера (дробь сохраняется, сплит-остатки продаются целиком)
```
**Ок:** резерв снизу ограничен, маржинальные режимы не превышают buyingPower, целые лоты на вход.
**Замечание:** `standard_safe` резервирует 2.2%, но hint в UI говорит «с запасом 2.2% под market
buy Webull» — для Robinhood тот же резерв, текст в UI общий для обоих брокеров (мелочь, P3).

### 6.8 SPA-цикл
```
navigate(path):
  pushState; state.page=…
  if user → API.authCheck() (сеть!) → возможно handleUnauthorized
  renderPage():  page-root.innerHTML = pageHTML(...)   // + Charts.destroy при смене контекста
  привязка всех слушателей заново
```
**Несоответствия/риски:** authCheck на каждый переход (AU-P3-12); полный пересбор + потеря фокуса;
гонка «быстрый переход пока летит fetch» — ответы старых страниц могут прийти после нового
рендера и перетереть state (нет отмены/проверки актуальности). [R] проверить на медленной сети.

## 8. Роадмап (что делать, в каком порядке)

### Phase 0 — быстрые исправления контуров денег (1–2 дня)
1. **AU-P0-1**: параметризовать имя брокера в 4 Telegram-сообщениях + тест на текст.
2. **AU-P0-2**: `pollTracker` не опрашивает default-брокера по чужому трекеру; неизвестный брокер →
   `execution_unknown` + алерт.
3. **AU-P0-3**: `listBlockingTrackers`/`AnyPendingTrackerFor`/`FindPendingTrackerBroker` различают
   «пусто» и «ошибка»; ошибка БД в submitEvaluated → блок входа `journal_unavailable`.
4. **AU-P0-5**: импорт календаря: проверка полноты хвоста окна, coverageThrough только по факту,
   сверка с расчётным календарём NYSE, алерт на расхождение; ручной «пересчитать день».
5. **AU-P0-4**: Consistency по всем открытым broker-строкам и по каждому подключённому брокеру
   (не только default); вторая позиция больше не невидима.

**Гейт 0:** fault-injection тесты: «БД упала в момент entry», «трекер robinhood при отвязанном
robinhood», «Webull вернул 20 дней из 30», «два брокера с двумя открытыми позициями» — все
заканчиваются блокировкой/алертом, ни одна — тихим дублем/потерей.

### Phase 1 — планировщик, календарь, сообщения (2–3 дня)
6. **AU-P1-1**: джобы с собственными дедлайнами; окно T-11/T-1 резервируется заранее; пропуск окна
   → алерт. Замер p50/p95/p99 джобов.

   когда импорт недоступен; виджет «календарь не импортирован» на странице Календарь/Мониторинг.
9. **AU-P1-3**: цена исполнения «не подтверждена» → `NULL` + бейдж в UI до ручного ввода;

    полный выходной в пятницу).
11. Роадмап-мелочи: добор частичного входа (решить политику), явный «fill-бюджет» в UI T-1.

**Гейт 1:** три тика внутри окна актуализации = один проход; «проскоченная» минута T-11 даёт алерт;
короткий день без импорта определяется расчётно; прогон `-race` сценариев OAuth+тик.
