# Roadmap исправлений безопасности

Источник: [SECURITY_AUDIT.md](SECURITY_AUDIT.md), ревизия аудита `558efee`. Три находки уровня P2, P0/P1 нет.

Правила для исполнителя:

- Задачи независимы. Делай их по порядку: A → B → C.
- **Один законченный пункт = один `git commit`.** Не смешивай пункты в одном коммите.
- Пуш и деплой **запрещены**, пока пользователь явно не попросит в текущем сообщении.
- На production не ходить: ни `ssh`, ни `./deploy.sh`, ни `docker` на сервере.
- Перед коммитом обязательно: `cd go && go build ./... && go test ./...` — зелёное.
- Если пункт не получается — остановись и напиши об этом, не придумывай обходной путь.

## A. SEC-02 — журнал HTTP растёт без ограничений (начни отсюда)

Проблема: неавторизованный человек шлёт запросы с длинным `?param=...`, получает `429`, но каждый такой
запрос всё равно дописывается в файл журнала целиком. Файл ничем не ограничен → диск может кончиться.

Файл: `go/internal/httpapi/accesslog.go`.

### A1. Обрезать длинные поля в записи журнала

В функции `accessLog` (около строки 65) запись `apiLogRec` заполняет `Path` и `Query` без ограничения длины.
Уже есть готовый хелпер `clip(s string, n int) string` (строка 168) — он ровно для этого.

Сделай:

- `Path:` → `clip(r.URL.Path, 256)`
- `Query:` → `clip(redactQuery(r.URL.RawQuery), 512)`

Больше в этом шаге ничего не меняй.

Проверка: `cd go && go test ./internal/httpapi/`.
Коммит: `fix(security): clip path and query in HTTP access log`

### A2. Не писать полную запись для отклонённых запросов

В той же функции `accessLog`, после того как посчитан `status`, добавь: если `status == http.StatusTooManyRequests`
(429), в записи не сохраняются `Query`, `UA`, `Body` — то есть эти поля остаются пустыми.
Метод, путь, статус, IP, время остаются как есть, чтобы отказы по-прежнему были видны в журнале.

Проверка: `cd go && go test ./internal/httpapi/`.
Коммит: `fix(security): drop request details from rejected-request log entries`

### A3. Ротация журнала по размеру

Сейчас `appendHTTPLog` (около строки 218) меняет имя файла только раз в месяц (`httpLogPathFor`) и пишет в него
бесконечно. Нужен предел по размеру.

Сделай в `appendHTTPLog`:

1. Добавь рядом с другими константами в начале файла: `const httpLogMaxBytes = 64 << 20` (64 MiB) и
   `const httpLogKeep = 3` (сколько старых файлов хранить).
2. Перед записью строки узнай текущий размер открытого файла (`httpLogFile.Stat()` → `Size()`).
3. Если `размер + len(line) > httpLogMaxBytes`:
   - закрой файл (`httpLogFile.Close()`, `httpLogFile = nil`);
   - сдвинь старые: `path.2` → `path.3`, `path.1` → `path.2`, `path` → `path.1` (`os.Rename`, ошибку
     «файла нет» игнорируй);
   - удали то, что вышло за `httpLogKeep` (`os.Remove` на `path.<httpLogKeep+1>`, ошибку «нет файла» игнорируй);
   - открой файл заново теми же флагами и правами `0o640`, что и сейчас.
4. Дальше пиши строку как раньше.

Ошибки ротации логируй через `log.Printf` и **не роняй запрос** — журнал не должен ломать обслуживание.

Тест — добавь в `go/internal/httpapi/` (или в существующий `accesslog_test.go`, если он есть):
через `DATASETS_DIR` во временном каталоге временно поставь маленький лимит, напиши много строк
и проверь, что файлов не больше `httpLogKeep + 1` и каждый не больше лимита.
Если менять константу из теста неудобно — сделай её переменной `var httpLogMaxBytes int64 = 64 << 20`.

Проверка: `cd go && go test ./...`.
Коммит: `feat(security): rotate HTTP access log by size`

**Критерий приёмки A:** поток отклонённых запросов с 64 KiB-параметром больше не даёт неограниченного роста;
число и размер файлов журнала ограничены и подтверждены тестом.

## B. SEC-01 — резервный архив с брокерскими токенами читают все локальные пользователи

Проблема: `backup-from-server.sh` кладёт архив со всей БД (в ней access/refresh токены брокера,
см. `go/internal/store/robinhood.go:48-58`) в общий `/tmp` с правами `0644`. Любой другой пользователь
хоста может его скопировать. Плюс `set -e` при сбое `scp` завершает скрипт **до** удаления файла на сервере.

Файл: `backup-from-server.sh`. Больше ничего не трогай.

Сделай:

1. Локальная сторона: сразу после `set -e` добавь `umask 077`. Тогда `$BACKUP_DIR` и скачанный архив
   доступны только владельцу.
2. Удалённая сторона (внутри строки `ssh "$SERVER" "..."`):
   - в начало этого блока добавь `umask 077`;
   - вместо жёстких путей `/tmp/stonks-backup-staging` и `/tmp/stonks-backup.tar.gz` используй
     приватный каталог: `STAGING=$(mktemp -d /tmp/stonks-backup.XXXXXX)`, архив клади в него же
     (`$STAGING/../` не надо — проще: отдельный `mktemp -d` для архива, либо архив рядом со staging внутри
     каталога, созданного `mktemp -d`);
   - путь архива нужно вернуть на локальную сторону, чтобы `scp` знал, что качать. Самый простой способ:
     сделать удалённый путь предсказуемым внутри одного `mktemp -d`, например заранее сгенерировать имя
     локально (`REMOTE_DIR="/tmp/stonks-backup.$TIMESTAMP.$$"`) и на сервере создать его через
     `mkdir -m 700 "$REMOTE_DIR"`. Это проще, чем парсить вывод `mktemp`, — используй этот вариант.
   - `chmod 600` на готовый архив.
3. Очистка при сбое: на локальной стороне добавь
   `trap 'ssh "$SERVER" "rm -rf \"$REMOTE_DIR\"" >/dev/null 2>&1 || true' EXIT`
   **до** первого `ssh`. Тогда падение `scp` всё равно удалит временные файлы на сервере.
   Существующий явный `ssh ... rm -f` можно оставить или убрать — важно, чтобы `trap` покрывал сбой.
4. Существующие `echo`-сообщения и структуру вывода сохрани.

Проверка **без production** (сервер не трогать):

```bash
bash -n backup-from-server.sh
```

и отдельно, во временном каталоге, убедись, что при `umask 022` архив всё равно получается `0600`:

```bash
d=$(mktemp -d) && (cd "$d" && umask 022 && umask 077 && echo test > a.txt && tar -czf a.tar.gz a.txt && ls -l a.tar.gz) ; rm -rf "$d"
```

Права должны быть `-rw-------`. Реальные данные и сервер не использовать.

Коммит: `fix(security): restrict backup archive permissions and clean up on failure`

**Критерий приёмки B:** при исходном umask `022` второй локальный пользователь не может прочитать архив;
искусственный сбой передачи удаляет удалённые временные файлы.

## C. SEC-03 — сборочный Go 1.25.8 с известными дырами в стандартной библиотеке

Проблема: локальный компилятор `go1.25.8`, а `deploy.sh` собирает production-бинарник именно им.
`govulncheck` нашёл 13 достижимых записей в `go/` и 14 в `mcp/`. Нужен Go **не ниже 1.25.13**
(в нём закрыты все записи из таблицы аудита, кроме уже закрытых раньше).

Это единственный пункт, где нужно менять окружение, а не код. Действуй так:

### C1. Обновить локальный Go

Обнови до последнего поддерживаемого патч-релиза ветки 1.25 (минимум 1.25.13) или новее.
Как именно — зависит от того, как Go установлен на этой машине (Homebrew: `brew upgrade go`;
установщик с go.dev — скачать новый пакет). Если обновление требует пароля пользователя —
**не пытайся его обойти**, напиши пользователю, что нужно сделать, и останови пункт C здесь.

Проверка: `go version` показывает `go1.25.13` или новее.

### C2. Поднять минимум в go.mod

В `go/go.mod` строка 3: `go 1.25.0` → `go 1.25.13`.
Если в `mcp/go.mod` тоже стоит `1.25.x` ниже — подними так же.

Проверка: `cd go && go build ./... && go test ./...`, затем `cd ../mcp && go test ./...`.

### C3. Зафиксировать версию образа в MCP

`mcp/Dockerfile:1` использует плавающий `golang:1.25-alpine`. Замени на точный тег,
например `golang:1.25.13-alpine` (или тот патч, до которого обновился в C1).

### C4. Повторно прогнать сканер

```bash
cd go && go run -exec 'env GOOS=linux GOARCH=amd64' golang.org/x/vuln/cmd/govulncheck@v1.7.0 ./...
```

и то же самое в `mcp/`. Ожидание: записи из таблицы SEC-03 пропали.
Если что-то осталось — **не подавляй и не игнорируй**, выпиши оставшиеся ID в ответ пользователю.

Коммит (одним, после C2–C4): `chore(security): require patched Go toolchain and pin MCP builder image`

**Критерий приёмки C:** `govulncheck` для `GOOS=linux/amd64` чист в обоих модулях; версия Go в сборке
подтверждена через `go version`.

Отдельно, **только по явной просьбе пользователя** и только когда будет разрешён доступ на production:
пересобрать и выкатить бинарник, проверить его версию через `go version -m`, а также проверить там
права архивов и лимиты журналов. Сам этого не делай.

## Что делать НЕ надо

Аудит явно отнёс это к незакрытым замечаниям, а не к уязвимостям. Не трогай в рамках этого roadmap:

- `BUILD_ID` в HTML (`go/internal/httpapi/server.go:1925-1934`) — экранирования нет, но `deploy.sh` ставит
  туда Git-хэш, и CSP Caddy ограничивает скрипты. Отдельная задача, не эта.
- `X-Forwarded-For` при `TRUST_PROXY=true` — штатный compose публикует порт только на loopback.
- Ответ административного `webull token/create` — endpoint и так требует админ-сессии.

Не «улучшай» авторизацию, ratelimit, CORS и cookie: аудит их проверил, они в порядке.
