# A. Пороги IBS: три разных режима валидации одного и того же числа

Корень: понятие «порог IBS» реализовано в проекте **четырьмя** независимыми
кусками кода с **несовместимой** семантикой значения `0`. CLAUDE.md прямо требует
обратного: «Монитор и автотрейдер должны ходить через `ibs.IsEntrySignal` /
`ibs.IsExitSignal`, чтобы живые пороги не разъехались с бэктестом». Через
предикаты они ходят — но **значение порога** до предиката доезжает уже другое.

Три режима:

| путь | код | что делает с `lowIBS = 0` |
|---|---|---|
| бэктест | `backtest/single.go:50` → `types.F64Or` | 0 сохраняется → `ibs < 0` → **входов нет** |
| API порогов тикера | `httpapi/server.go:1300` → `ibs.SanitizeThresholds` | 0 **валиден и принимается** (`ibs_test.go:72` это утверждает) |
| движок live | `live/config.go:215`, `live/autotrade.go:470` | 0 трактуется как «не задано» → **подменяется на 0.10** |

## A1 — P1 — Порог `lowIBS = 0` молча превращается в 0.10, и движок торгует то, что оператор выключил

**Файлы:** `go/internal/live/config.go:215-223`, `go/internal/live/autotrade.go:470-481`

```go
func liveLowIBS(cfg map[string]any) float64 {
	if !cfgHas(cfg, "lowIBS") { return ibs.DefaultLowIBS }
	low := asFloat(cfg["lowIBS"])
	if low == 0 { return ibs.DefaultLowIBS }   // <-- 0 == "не задано"
	return low
}
```

```go
func liveLowOrDefault(row map[string]any) float64 {
	...
	v := asFloat(th["lowIBS"])
	if v != 0 { return v }                     // <-- то же самое
	return ibs.DefaultLowIBS
}
```

**Сценарий отказа.** Оператор хочет временно отключить входы по конкретному
тикеру и ставит ему `lowIBS = 0` — «вход только если IBS строго меньше нуля»,
то есть никогда. `POST /api/live/watch` пропускает это значение: валидатор
`validateWatchThresholds` зовёт `ibs.SanitizeThresholds(0, 0.75)`, а тот
документирован как принимающий весь `[0, 1]` и возвращает `nil`. Значение
ложится в БД. Бэктест с этим же параметром покажет ноль сделок. Но на T-1
`liveLowOrDefault` видит `0`, считает его отсутствующим и возвращает **0.10** —
и движок открывает позицию на реальные деньги по порогу, который оператор
явно снял. Расхождение live и бэктеста ровно то, которое CLAUDE.md запрещает.

**Почему это не ловится тестами:** `ibs_test.go:72` утверждает, что
`SanitizeThresholds(0, 1)` — валидная пара, а тесты live проверяют только
непустые пороги. Два теста согласованы каждый со своим куском кода, и
противоречие между кусками не проверяет никто.

## A2 — P1 — `highIBS = 0` в глобальном конфиге навсегда запирает открытую позицию

**Файлы:** `go/internal/live/config.go:131-133`, `:146-160`, `:225-234`,
`go/internal/live/autotrade.go:344-346`, `go/web/js/app.js:2979`

`sanitizeAutoTradingConfig` защищает пару порогов от инверсии так:

```go
low, lok := finiteNumber(next["lowIBS"])
high, hok := finiteNumber(next["highIBS"])
if lok && hok && high > 0 && low >= high {   // <-- high > 0 выключает проверку
	...откат к предыдущим значениям...
}
```

Условие `high > 0` **само себя обезоруживает** ровно в том случае, который надо
поймать: при `highIBS = 0` пара заведомо инвертирована (`low >= high` для любого
`low >= 0`), но guard пропускает её, и ноль сохраняется в конфиг.

Дальше `liveHighIBS` возвращает `(DefaultHighIBS, invalid=true)`, флаг
`highIBSInvalid` доезжает до решения, и:

```go
if row != nil && asBool(row["highIBSInvalid"]) {
	return none("invalid_high_ibs", sym, row)   // выход не рассматривается
}
```

**Сценарий отказа.** В форме автотрейдинга поле «Выход, IBS выше» имеет
`min="0"` (`app.js:2979`), то есть ноль вводится штатно. Оператор сохраняет 0
(например, стёр поле и браузер отдал `0`). Форма сохраняется **без ошибки** —
`sanitizeAutoTradingConfig` никогда не возвращает `error`, он молча правит.
С этого момента при любой открытой позиции движок на каждом T-1 отвечает
`invalid_high_ibs` и **не выходит из позиции никогда**, пока человек не заметит.
Позиция висит через ночь и выходные вопреки правилу «держим до полного
закрытия, потом можно перезайти».

Ту же пару для отдельного тикера API **отвергает** с 400
(`SanitizeThresholds(0.1, 0)` → `low >= high`). То есть один и тот же ввод
через одну страницу запрещён, а через соседнюю — принят и опасен.

## A3 — P2 — Глобальный конфиг автотрейдинга чинит ввод молча, а не отвечает ошибкой

**Файл:** `go/internal/live/config.go:119-160`

`sanitizeAutoTradingConfig` не имеет пути возврата ошибки вообще: `clamp`,
подстановка дефолта, откат к предыдущему значению. Оператор вводит
`maxSlippageBps = 5000`, получает «сохранено» и живёт с 1000. Вводит
`entryReservePct = 0.9` — получает 0.1. UI не показывает, что значение
заменили: `app.js` перерисовывает форму из ответа, но человек не сравнивает.

Соседний путь порогов тикера (`httpapi/server.go:1302`) на тот же класс ввода
отвечает `400` с текстом. Две ручки одной системы ведут себя противоположно.

**Корень A1–A3 один:** нет единственного места, где определено, что такое
валидный порог. `ibs.SanitizeThresholds` создана ровно для этого и вызывается
**из одного места на весь проект** (`httpapi/server.go:1300`), а три остальных
пути имеют собственные правила.

## B1 — P2 — Access-log пишется до рейт-лимита, поэтому забаненный клиент всё равно раздувает диск

**Файлы:** `go/internal/httpapi/server.go:110`, `go/internal/httpapi/accesslog.go:70-134,224-257`

```go
h := s.accessLog(recoverMiddleware(s.checkOrigin(s.rateLimit(s.mux))))
```

`accessLog` — самый внешний слой цепочки, `rateLimit` — самый внутренний. Значит
запись в `http-access-YYYY-MM.jsonl` происходит **до** того, как лимитер вернёт
429, и происходит для каждого отклонённого запроса.

Код в `accesslog.go:94-99` явно знает про этот случай и при `429` не пишет
query/UA/длину тела — но саму запись (IP, путь, метка времени, статус) пишет
всё равно.

**Сценарий отказа.** Неаутентифицированный клиент упирается в лимитер и просто
продолжает слать запросы. Каждый отвергнутый запрос — строка в лог-файле.
Ротация только по размеру, с `httpLogKeep = 3`, то есть ограничение сверху есть,
но оно порядка трёх файлов максимального размера, а не «поток отклонённых
запросов ничего не стоит». На той же машине лежит SQLite с торговыми данными.

## B2 — P3 — Лимитер чистит всю карту бакетов на каждом запросе под общим мьютексом

**Файл:** `go/internal/httpapi/ratelimit.go:36-56`

```go
for k, b := range l.buckets {
	if now.After(b.reset) { delete(l.buckets, k) }
}
```

Полный проход по карте на **каждый** вызов `allow()`, под единственным
мьютексом, сериализующим все проверки лимита в процессе. При множестве
различных ключей это O(n) на запрос на горячем пути. Severity низкая только
потому, что `clientIP()` при `TRUST_PROXY=false` не даёт злоумышленнику
наплодить ключи с одного соединения.

## B3 — P3 — Origin-проверка пропускает запросы без `Origin` и без `Sec-Fetch-Site`

**Файл:** `go/internal/httpapi/ratelimit.go:141-160`

```go
if origin == "" {
	if strings.EqualFold(r.Header.Get("Sec-Fetch-Site"), "cross-site") { return 403 }
	next.ServeHTTP(w, r)
	return
}
```

Любой не-браузерный клиент с угнанной кукой проходит эту проверку насквозь.
Реальной защитой от CSRF здесь работает `SameSite=Lax` на куке
(`server.go:436`), а Origin-проверка — вторичный слой с дырой. Флажу потому,
что комментарии подают её как самостоятельный контроль.

## B4 — Расхождение документации и кода: пустой `ADMIN_PASSWORD`

**Файл:** `go/internal/httpapi/server.go:280-284, 379-383, 488-492`

CLAUDE.md пишет «пустой пароль отключает аутентификацию вне прода». Код на
любом защищённом маршруте при пустом `ADMIN_PASSWORD` отдаёт
`503 {"error":"Auth not configured"}` — и в дев-режиме тоже. Поведение
**безопаснее** документированного (fail closed), то есть это не дыра, но
разработчик, который поверит CLAUDE.md, получит 503 вместо входа.

## B5 — Проверено и признано НЕ багом (чтобы не переоткрывать)

- `serveWeb` (`server.go:1924-1950`): `filepath.Clean` применяется к уже
  укоренённому пути запроса до `Join`, поэтому ведущие `..` срезаются по
  документированной семантике `Clean`; обхода каталога нет. Агент проверил
  отдельной программой.
- `recoverMiddleware`: стек уходит только в серверный лог, клиенту — общий текст.
- `checkPassword` (`server.go:473-486`): постоянное время и для bcrypt, и для
  plaintext-конфигурации, тайминг-оракула по неизвестному пользователю нет.
- Robinhood OAuth: verifier и `state` лежат на сервере под ключом `state` и
  потребляются ровно один раз (`TakeRobinhoodPending`, delete-on-read); реплей
  закрыт, `state` сверяется до обмена.
- `s.testAuthToken` (`server.go:111-121`) выставляется только из `_test.go`,
  из окружения не достижим — это не обход аутентификации в проде.
- Доверие `X-Forwarded-For` включается только при `TRUST_PROXY=true` и берёт
  **правый** элемент, который дописывает Caddy.
- Гонок по картам нет: `buckets`, `httpLogFile`/`httpLogName`, `lastPurge` —
  каждый под своим мьютексом и только через него.
- `handleAutoExecute` пробрасывает `r.Context()` в `ExecuteCtx`; долгие
  эндпоинты явно снимают write deadline, а не гоняются с `WriteTimeout`.
- Двойных `WriteHeader` не найдено ни в одном из проверенных обработчиков.

# C. Торговый календарь: расписание T-11/T-1 сдвинуто на три часа два раза в год

Это самый тяжёлый кластер. Проверено не чтением, а запуском кода: временный
`_test.go` в `internal/tradingdate`, вывод приложен, файл удалён.

## C1 — P1 — Ранним закрытием считается среда ПЕРЕД Днём благодарения, а не пятница ПОСЛЕ него

**Файлы:** `go/internal/tradingdate/holidays.go:141-145`,
`go/internal/scheduler/scheduler.go:79-88`, `:113-127`

```go
	y, _, _ := split(ymd)
	thanks := NthWeekdayOfMonth(y, time.November, time.Thursday, 4)
	if ymd == AddDays(thanks, -1) {          // <-- минус один день
		return "Thanksgiving Eve"
	}
	return "Early Close"
```

`AddDays(thanks, -1)` — это **среда** перед Днём благодарения. У NYSE среда
перед Днём благодарения — **полная сессия до 16:00**. Сокращённая сессия до
13:00 — это **пятница после** Дня благодарения, то есть `AddDays(thanks, +1)`.

Фактический вывод кода:

```
year=2025 thanksgiving=2025-11-27 | WED 2025-11-26 -> ShortDayName="Thanksgiving Eve" | FRI 2025-11-28 -> ShortDayName="Early Close"
year=2026 thanksgiving=2026-11-26 | WED 2026-11-25 -> ShortDayName="Thanksgiving Eve" | FRI 2026-11-27 -> ShortDayName="Early Close"
year=2027 thanksgiving=2027-11-25 | WED 2027-11-24 -> ShortDayName="Thanksgiving Eve" | FRI 2027-11-26 -> ShortDayName="Early Close"
```

`computedShortDay` считает днём с ранним закрытием всё, что получило имя,
отличное от дефолтного `"Early Close"`:

```go
name := tradingdate.ShortDayName(date)
return name != "" && name != "Early Close"
```

Отсюда `TradingSession` берёт `CloseMin`, а от него отсчитываются T-11 и T-1.
Получаются **две зеркальные ошибки по три часа каждая**:

**Среда перед Днём благодарения.** `CloseMin = 13:00`. Обзор T-11 уходит в
12:49, решение и ордера T-1 — в 12:59. Реальное закрытие в 16:00. Значит
IBS считается по середине сессии, а не по закрытию; выбирается не тот тикер
(IBS ещё три часа будет ходить), и ордер уходит по цене, которая закрытием
не является. Прямое нарушение правила из CLAUDE.md «Execute trades **only at
the official session close**».

**Пятница после Дня благодарения (Black Friday).** `CloseMin = 16:00`. T-11
в 15:49, T-1 в 15:59. Биржа закрылась в 13:00 почти три часа назад. Ордера
уходят в закрытый рынок — отказ брокера либо постановка в очередь на
следующую сессию, то есть исполнение по цене другого дня.

## C2 — P1 — Ошибку C1 нельзя исправить из интерфейса календаря

**Файлы:** `go/internal/scheduler/scheduler.go:66-74`, `go/internal/httpapi/server.go:1183-1215`

```go
func IsShortDay(p tradingdate.NYSEParts, cal Calendar) bool {
	if yearMap := cal.ShortDays[y]; yearMap != nil {
		if _, ok := yearMap[mmdd(p)]; ok { return true }
	}
	return computedShortDay(p)      // <-- ИЛИ, а не «вместо»
}
```

Импортированный календарь и вычисленный объединяются по **ИЛИ**. Значит:

- пометить Black Friday сокращённым днём через UI **можно** — ИЛИ сработает;
- снять ошибочную пометку со среды перед Днём благодарения **нельзя**.
  `deleteNested(shortDays, year, mmdd)` в `server.go:1188` удалит запись из
  сохранённого календаря, а `computedShortDay` тут же вернёт её обратно.

То есть у оператора, который заметил проблему в среду утром, нет способа
починить её до закрытия. Комментарий в `scheduler.go:76-78` описывает
`computedShortDay` как «fallback, когда в импортированном календаре нет
записи», но кода, который бы делал его именно fallback, нет — есть безусловное ИЛИ.

## C3 — P2 — Засеянный по умолчанию календарь не содержит ни одного реального сокращённого дня, кроме 24 декабря

**Файл:** `go/internal/store/db.go:716-719`

```json
"shortDays": {
  "2025": {"12-24": {"name": "Christmas Eve", "type": "short"}},
  "2026": {"12-24": {"name": "Christmas Eve", "type": "short"}}
}
```

У NYSE сокращённых сессий три: 3 июля (когда рабочий день), пятница после
Дня благодарения, 24 декабря. В сиде есть только третья. Для первых двух
система целиком полагается на `computedShortDay`, а он, по C1, ошибается в

вычисляемый путь. Смягчает то, что в `RunTick` есть отдельная защита
`calendar-coverage-expired`, но она про `holidays`, не про `shortDays`.

## C4 — P3 — `NYSEHolidayDates(year)` возвращает дату чужого года и один несуществующий выходной

**Файл:** `go/internal/tradingdate/holidays.go:30-40, 93-99`

`ObservedFixed` переносит субботний праздник на пятницу. Для 1 января это
неверно: у NYSE перенос на предыдущую пятницу не применяется, когда эта
пятница — последний торговый день года. 31 декабря 2021 биржа работала.

Фактический вывод:

```
NYSEHolidayDates(2022) = [2021-12-31 2022-01-17 2022-02-21 2022-04-15 2022-05-30
                          2022-06-20 2022-07-04 2022-09-05 2022-11-24 2022-12-26]
```

Первый элемент — из 2021 года и торговым выходным не является; записи про
Новый год 2022 в списке нет вообще. Годы с 1 января в субботу: 2022, 2028, 2033.

Сейчас это **не стреляет**: `NYSEHolidayDates` во всём проекте не вызывается,
а `IsNYSEHoliday("2021-12-31")` возвращает `false` (проверено), потому что
ищет по году самой даты. То есть баг заперт в неиспользуемой функции. P3 —
но функция экспортирована, лежит рядом с используемыми и выглядит готовой
к употреблению.

## C5 — P2 — Битая дата не отвергается, а тихо превращается в правдоподобную

**Файл:** `go/internal/tradingdate/date.go:56-95`

`split()` на непарсящемся входе возвращает `(0, 0, 0)`, и вызывающий код
спокойно строит из этого `time.Time`. `utcMidnight` при ошибке парсинга
падает в `Sscanf` с дефолтами 1970-01-01. Фактический вывод:

```
AddDays("garbage", 1) = "-0001-12-01"
DaysBetween("garbage", "2024-01-01") = 19723
DayOfWeek("garbage") = 4
```

Ни одна из трёх функций не сообщает об ошибке. `DayOfWeek` вернул «четверг»
для строки `garbage` — а на `DayOfWeek` завязаны выходные. CLAUDE.md требует
(правило 5), чтобы дата неправильного вида **отвергалась**; `Parse` это
делает, а арифметика на строке-дате — нет, и вызывающему не обязательно
проходить через `Parse`.

## C6 — P3 — `Parse` принимает мусор после даты

**Файл:** `go/internal/tradingdate/date.go:17`, `:161-169`

`isoPrefix = ^(\d{4})-(\d{1,2})-(\d{1,2})` не закреплён с конца. Фактически:

```
Parse("2024-01-15TRAILINGJUNK") = {IsValid:true Date:"2024-01-15" Format:"YYYY-MM-DD"}
```

Для полноценных ISO-таймстампов (`2024-01-15T00:00:00Z`) это и есть желаемое
поведение, поэтому severity низкая. Но отличить `2024-01-15T00:00:00Z` от
испорченной строки в CSV провайдера функция не может, а по CLAUDE.md именно
`Parse` — граница, на которой мусор должен останавливаться.

# D. Планировщик: что проверено и оказалось крепким, и где остаётся хрупкость

Честно: планировщик написан аккуратнее, чем я ожидал, и половина классических
дыр здесь закрыта. Перечисляю сначала закрытое, чтобы будущие аудиты это не
переоткрывали, потом — что действительно осталось.

## D0 — Проверено и НЕ баг

- **Тайм-ауты HTTP есть везде.** Ни одного `http.DefaultClient`, `http.Get`
  или `http.Post` во всём дереве. Все девять клиентов сконструированы с
  `Timeout` (providers 30s, robinhood 20s/30s, webull 15s + отдельный
  `TradeHTTPTimeout`, telegram 15s). Сервер тоже с полным набором:
  `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`
  (`cmd/server/main.go:57-62`).
- **Двойного запуска нет.** Актуализация цен под `actualizeMu.TryLock()`
  (`scheduler.go:494`), поэтому из 51 возможного тика в окне
  `after ∈ [15,31]` работу делает ровно один. Телеграм-слоты берутся
  атомарными claim-ами (`ClaimAggregateT11`, `ClaimMissedT1`), а не
  паттерном «прочитал–проверил–записал».
- **Паника в задаче не убивает планировщик** — `recover` стоит и в теле
  горутины тикера, и внутри `RunTick` (`scheduler.go:172-180`, `:193-198`).
- **Переход на летнее время не ломает расписание.** Всё wall-clock идёт через
  `tradingdate.CurrentTimeNYSE(now)` с явной зоной `America/New_York`, а
  `time.Ticker` монотонный — сдвига стрелок он не видит, двойного срабатывания
  на осеннем переводе не будет.
- **Однодневные задачи защищены маркерами** (`lastCalendarImportDate`,
  `lastAutotradeLogPruneDate`), и маркер ставится даже когда сама задача
  вернула ошибку — то есть цикл «падаем и повторяем каждые 20 секунд» закрыт.
- **Пропуск окна детектируется.** `reportMissedTelegram` шлёт в Telegram
  «Пропущен T-11» / «Пропущен T-1», причём под тем же атомарным claim-ом, так
  что сообщение уйдёт один раз, а не 1400 раз за вечер.
- **Ротация логов автотрейдинга ограничена с двух сторон** — и по возрасту,
  и по числу строк (`autotradeLogRetentionDays`, `autotradeLogMaxRows`).

## D1 — P2 — `RunTick` получает время из канала тикера, а не текущее

**Файл:** `go/internal/scheduler/scheduler.go:166-169, 186, 199-200`

```go
case now := <-tick.C:
	...
	RunTick(db, deps, now, onEvent)
```

`now` — это метка времени **тика**, а не момента начала обработки.
`time.Ticker` не копит тики: канал буферизован на один, лишние отбрасываются.
Значит если предыдущий `RunTick` шёл дольше периода, следующая итерация
получит из канала метку, устаревшую на длительность просрочки, и посчитает
`until := sess.CloseMin - nowMin` по старым часам.

Практический предел просрочки задан тайм-аутами клиентов (30 секунд на
провайдера), то есть перекос порядка десятков секунд, а не часов. Поэтому P2,
а не P1. Но лечится это одной строкой (`now := time.Now()` внутри тела), и
пока строка не написана, решение о сделке в принципе может считаться по
устаревшим часам.

## D2 — P2 — Вся сделка держится на том, что хоть один тик попадёт в конкретную минуту

**Файл:** `go/internal/scheduler/scheduler.go:226-231`, `:482-485`

Окна в `RunTick` широкие (`until ∈ [10,12]` и `until ∈ [0,2]`), но настоящий
шлагбаум внутри:

```go
func RunTelegramAggregation(db *store.DB, deps Deps, until int) int {
	// Node runTelegramAggregation returns wrong_time unless the clock minute is exactly 11 or 1.
	if until != 11 && until != 1 {
		return 0
	}
```

То есть **работа делается только когда `until` ровно 11 или ровно 1**. Широкие
окна снаружи — не запас прочности, они просто расширяют диапазон, в котором
функция будет вызвана и ничего не сделает. Реальный запас — три тика по 20
секунд внутри одной минуты.

**Сценарий отказа.** `RunTick` выполняется дольше 60 секунд и «перешагивает»
минуту, в которой `until == 1`. Тогда ордера за этот день не уходят вообще:
приходит только телеграм «Пропущен T-1». Сегодня это маловероятно — тяжёлые
однодневные задачи (`RunCalendarExtend`, `RunTokenHealth`) успевают
отметиться маркером задолго до закрытия, а всё остальное на горячем пути
ограничено тайм-аутами. Но запас прочности здесь — секунды, и он держится на
свойстве, которое нигде не проверяется тестом.

Связка с D1 усиливает обе: устаревшая метка времени как раз и есть способ
«перешагнуть» точную минуту.

## D3 — P3 — `reportMissedTelegram` вызывается на каждом тике до конца суток

**Файл:** `go/internal/scheduler/scheduler.go:220-225`

```go
if until < 10 { reportMissedTelegram(..., "t11", until, ...) }
if until < 0  { reportMissedTelegram(..., "t1",  until, ...) }
```

`until` после закрытия уходит в минус и растёт по модулю: в 20:00 ET это −240.
Условия остаются истинными до полуночи, то есть примерно **1400 вызовов** за
вечер, каждый из которых делает `db.AggregateState(chat, today)` — запрос к
SQLite, у которой `MaxOpenConns = 1`, то есть к тому же единственному
соединению, что и всё остальное. Дубликатов сообщений нет (claim атомарный),
так что это чистая трата, а не баг поведения. Но это ещё и три запроса в
минуту к тому же соединению, через которое ходят трекеры ордеров.

# E. Операционные скрипты и контейнеры

## E1 — P0 — `cleanup-server.sh` уничтожает боевую базу, и в предупреждении об этом нет ни слова

**Файл:** `cleanup-server.sh:33-60` (функция `cleanup_docker`), вызов — `:145`

```bash
docker stop $(docker ps -aq) 2>/dev/null || true
docker rm   $(docker ps -aq) 2>/dev/null || true     # удалены ВСЕ контейнеры
...
docker rmi  $(docker images -q) 2>/dev/null || true
docker system prune -af
docker volume prune -f                                # <-- вот здесь
docker network prune -f
```

`docker volume prune` удаляет тома, **не привязанные ни к одному контейнеру**.
Строкой выше скрипт удалил все контейнеры до единого. Значит на момент
`volume prune -f` дангляющими стали все именованные тома из
`docker-compose.yml`:

- `stonks_db` — SQLite с торговой базой (`/data/db/trading.db`);
- `stonks_datasets` — все загруженные датасеты OHLC;
- `stonks_state` — состояние и access-логи;
- `caddy_data` — аккаунт и сертификаты Let's Encrypt;
- `caddy_config`.

Флаг `-f` снимает подтверждение. Обычный `docker system prune -af` именованные
тома не трогает (для этого нужен `--volumes`), так что убивает именно
отдельная строка `docker volume prune -f`.

**Почему это не заметят.** Предупреждение, которое скрипт показывает перед
`read -p "Продолжить? (y/N)"` (`:124-129`), перечисляет ровно четыре пункта:

```
  - Все остановленные контейнеры
  - Старые Docker образы
  - Временные файлы
  - Старые бэкапы (старше 30 дней)
```

Ни томов, ни базы, ни сертификатов в списке нет. Оператор, прочитавший
предупреждение целиком и нажавший `y`, о потере базы не предупреждён никак.

Дальше скрипт сам советует (`:170`) `docker compose up -d`. Compose создаёт
именованные тома заново — **пустыми**. Сервис поднимается, `healthcheck` на
`/readyz` зелёный, `./health-check.sh` (тоже рекомендованный, `:171`) проверяет
наличие контейнеров и отвечает «всё хорошо». То есть уничтожение данных
происходит бесшумно: снаружи система выглядит здоровой, просто вся история
сделок, датасеты и сертификаты исчезли.

Бэкап скрипт не делает и наличие бэкапа не проверяет — `backup-from-server.sh`
существует, но никак с этим не связан.

## E2 — P2 — Контейнер `server` не имеет ни одного ограничения, которыми обвешан `mcp`

**Файл:** `docker-compose.yml:2-40` против `:41-70`

Сервис `mcp` (транскрипция YouTube, денег не касается) закрыт полностью:

```yaml
    read_only: true
    tmpfs: [ "/tmp:size=16m,noexec,nosuid,nodev" ]
    cap_drop: [ ALL ]
    security_opt: [ "no-new-privileges:true" ]
    pids_limit: 64
    mem_limit: 128m
    cpus: "0.35"
```

Сервис `server` — тот, который держит токены брокеров, ключи провайдеров и
ставит ордера на реальные деньги — не имеет **ничего** из этого списка: ни
`cap_drop`, ни `no-new-privileges`, ни `pids_limit`, ни `mem_limit`, ни
`cpus`. Защита выстроена ровно наоборот приоритетам. Часть объяснима
(`read_only` невозможен — процессу нужна запись в `/data`), но `cap_drop: ALL`
и `no-new-privileges` возможны, и в Dockerfile уже есть непривилегированный
`USER app` (uid 10001), то есть половина работы сделана.

Отсутствие `mem_limit` вдобавок значит, что бэктест на большом датасете может
съесть память всей VPS и утянуть за собой Caddy и mcp.

## E3 — P2 — Тег `:latest` по умолчанию позволяет молча поднять старый образ

**Файл:** `docker-compose.yml:3`

```yaml
image: ${SERVER_IMAGE:-stonks-server:latest}
```

`deploy.sh` выставляет `SERVER_IMAGE`/`BUILD_ID` на время своего запуска. Но
`restart: unless-stopped` и любой ручной `docker compose up -d` на VPS (а
именно его советует `cleanup-server.sh:170`) выполняются уже без этих
переменных и берут `stonks-server:latest`. Если что-то однажды перетегировало
`latest` — например `docker tag stonks-server:latest-backup stonks-server:latest`
из `cleanup_docker` (`cleanup-server.sh:53`) — в проде окажется предыдущая
сборка, и никакой сигнал об этом не поднимется. `BUILD_ID` в `environment`
есть, то есть версия наружу отдаётся, но сравнивать её не с чем.

## E4 — P3 — Только `deploy.sh` написан строго; остальные скрипты — на голом `set -e`

```
backup-from-server.sh        set -e
cleanup-server.sh            set -e
health-check.sh              set -e
test-telegram.sh             set -e
deploy.sh                    set -euo pipefail
```

Нет `-u` — опечатка в имени переменной разворачивается в пустую строку. Нет
`-o pipefail` — в конвейере учитывается только последняя команда. Конкретное
место, где это сходится с разрушительной операцией:

```bash
ls -1td ${pattern} 2>/dev/null | tail -n +6 | xargs rm -rf 2>/dev/null || true
```
(`cleanup-server.sh:93`)

`${pattern}` без кавычек, `xargs` без `-r` и без `-0`. Имя каталога с пробелом
разъедется на два аргумента `rm -rf`. Провал `ls` не остановит конвейер,
потому что `pipefail` выключен.

`deploy.sh` при этом сделан правильно и даже отказывается выкатывать грязное
дерево (`:14-19`) — то есть автор знает, как надо; просто соседние скрипты
писались раньше и по-другому.

## E5 — P3 — Caddyfile проксирует на два апстрима, которых нет в compose

**Файл:** `caddy/Caddyfile:40-44, 62-72`

```
handle_path /music/* { reverse_proxy musicplay:3001 }
...
macdiff.com { reverse_proxy macdiff:8080 ... }
```

Ни `musicplay`, ни `macdiff` в `docker-compose.yml` не описаны. Caddy 2
резолвит апстрим в момент запроса, поэтому старт не падает — эти маршруты

служит только 502 в проде.

Заодно: у `caddy` единственного из трёх сервисов нет `healthcheck`, хотя
именно он держит 80 и 443.

## E6 — P3 — `test-telegram.sh` мёртв: он ходит без авторизации за полем, которого больше нет

**Файл:** `test-telegram.sh:13, 22-23`

```bash
SETTINGS_RESPONSE=$(curl -s "https://mktorder.com/api/settings" || echo "")
BOT_TOKEN=$(echo "$SETTINGS_RESPONSE" | grep -o '"botToken":"[^"]*"' | cut -d'"' -f4 || echo "")
```

Два независимых основания, по которым это не может сработать:

1. `GET /api/settings` обёрнут в `s.auth` наравне со всеми остальными
   маршрутами (`httpapi/server.go:124-134`) — анонимный `curl` получит 401.
2. `botToken` вообще не входит в `allowedSettingsKeys` (`store/db.go:794-823`);
   настройки Telegram живут не здесь. Даже авторизованный запрос этого поля
   не вернёт.

Скрипт всегда доходит до «❌ Telegram настройки не найдены или пусты» и
выходит с кодом 1. Держать в репозитории скрипт, который выглядит рабочим
инструментом проверки, но всегда падает, — это ловушка для того, кто в
следующий раз будет чинить уведомления в спешке.

Отдельно отмечу как **проверенное и корректное**: `clientSettings`
(`server.go:617-628`) вырезает `polygonApiKey`, и это единственный секрет
среди разрешённых ключей настроек — значит выдача не течёт. А access-лог
редактирует секреты по широкому регэкспу
(`accesslog.go:25`: `password|passwd|secret|token|authorization|cookie|api[_-]?key|...`)
и в query, и рекурсивно в JSON-теле. Секреты в `http-access-*.jsonl` не попадают.

# F. Движок live: исполнение ордеров

Находки агента по `engine.go`/`monitor.go`/`autotrade.go`/`execute_all.go`/
`deadline.go`/`config.go`/`brokers.go`.

## F1 — P2 — Оценка «успею ли ещё одну попытку» считает меньше, чем попытка стоит

**Файлы:** `go/internal/live/autotrade.go:552-605`, `go/internal/live/deadline.go:97-106`

```go
start := e.now()
res, err = e.placeMarketOnce(attemptCtx, symbol, side, qty, try, br)
cancel()
lastDur = e.now().Sub(start)
...
landed, queryFailed, detail := e.orderLanded(w, try.ClientOrderID, br)   // не замерено
...
e.sleep(submitRetryStep)                                                 // не замерено
```

`deadlineExceeded(w, lastDur)` использует `lastDur` как оценку стоимости
следующего цикла и решает, начинать ли ещё одну попытку до закрытия. Но
реальный цикл — это `placeMarketOnce` **плюс** сетевой round-trip
`orderLanded` **плюс** фиксированные 750 мс `submitRetryStep`. Замеряется
только первое слагаемое, поэтому оценка систематически занижена.

**Следствие.** У самой границы закрытия движок решает, что бюджета хватает,
начинает попытку, и она обрывается собственным контекстом на полпути между
«отправлено» и «подтверждено». Это худший из возможных исходов — `Ambiguous`:
неизвестно, встал ордер или нет, ровно в момент закрытия. Чистого раннего
отказа через `abortPlaceForDeadline` не происходит, хотя ради него механизм
и сделан. Тестов на этот путь нет.

## F3 — P2 — Тот же баг «0 значит не задано», ещё в двух местах

Корень тот же, что в кластере A, но это независимые реализации, и одна из них
— именно та, по которой принимается решение.

**`go/internal/live/config.go:250-269`, `watchThresholds`:**

```go
if watch["lowIBS"] != nil {
	if v := asFloat(watch["lowIBS"]); v != 0 { low = v }
}
...
h := asFloat(watch["highIBS"])
if h == 0 { highInvalid = true } else { ... }
```

Персональный `lowIBS: 0` у тикера молча игнорируется в пользу глобального
значения; персональный `highIBS: 0` помечает весь watch как `highIBSInvalid`
и блокирует выходы по этому тикеру. `config_test.go` и `decide_live_test.go`
ни разу не ставят пороги ровно в 0.

**`go/internal/live/autotrade.go:468-490`** — это те самые
`liveLowOrDefault`/`liveHighOrDefault`, которые `decideLiveAction` вызывает
на строках 344 и 383. То есть подмена происходит не при сохранении конфига,
а **в момент принятия решения о сделке**.

Все остальные числовые поля санитайзера зажаты с двух сторон (`lowIBS`,

## F5 — P3 — Проверка провайдера чувствительна к регистру и молча роняет поле

**Файл:** `go/internal/live/config.go:161-163`

```go
if s, ok := input["provider"].(string); ok && enumIn(s, "finnhub", "webull", "robinhood") {
	next["provider"] = s
}
```

`"Webull"` не пройдёт `enumIn`, поле будет отброшено, останется прежнее

# G. Котировки и провайдеры

## G1 — P0 — Одиночный запрос котировки отдаёт первую попавшуюся строку, если символ не совпал, и это попадает прямо в решение T-1

**Файлы:** `go/internal/providers/client.go:619-636` (`pickSnapshotRow`),
`:508-527` (`webullQuote`), `:214-226` (`Quote`),
`go/internal/live/telegram.go:880-895` (`fetchLiveQuote`)

```go
func pickSnapshotRow(data any, symbol string) map[string]any {
	rows := snapshotRows(data)
	want := strings.ToUpper(symbol)
	var first map[string]any
	for _, row := range rows {
		m, ok := row.(map[string]any)
		if !ok { continue }
		if first == nil { first = m }
		if strings.ToUpper(rowSymbol(m)) == want { return m }
	}
	return first          // <-- символ не совпал ни разу: отдаём первую строку
}
```

Пакетный путь ровно от этого защищён, и в нём стоит комментарий, из которого
видно, что автор про одиночный путь знал:

```go
// Strict symbol match: unlike the single-symbol path there is no
// "first row wins" fallback here — a mislabelled row would hand one
// ticker's IBS to another.
```
(`client.go:576-578`)

**Почему это доезжает до денег.** Два пути не альтернативны, они **соединены
последовательно**:

```go
// telegram.go:884-891
q, batched := e.cachedProviderQuote(symbol, p)
var err error
if !batched {
	q, err = qs.Quote(symbol, p)      // одиночный путь, тот самый fallback
}
```

`prefetch` кладёт в кэш только строки, прошедшие **строгую** проверку символа
(`telegram.go:824-841`). Всё, что строгую проверку не прошло, остаётся
`missing` — и тут же добирается одиночным запросом, у которого проверки нет.
То есть архитектура такая: строгий фильтр выбрасывает подозрительную строку,
а следующий шаг её принимает.

**Сценарий отказа.** Webull отдаёт снапшот со строкой, у которой поле символа
пустое или переименовано (смена схемы API — а `rowSymbol` уже умеет несколько
алиасов, значит схема там менялась). Строгий путь строку отбрасывает.
Одиночный путь берёт её как котировку запрошенного тикера. `ibsFromQuote`
считает IBS по чужим `open/high/low/current`. На T-1 это значение сравнивается
с порогом входа, и движок покупает **не тот инструмент** — либо входит, когда
у реального тикера сигнала нет.

Проверка `ibsFromQuote(q)` на «usable range» здесь не спасает: у чужой строки
диапазон совершенно нормальный, просто принадлежит другой бумаге.

Тем же путём ходят и `httpapi/server.go:1571` (тот же паттерн
«batch, потом одиночный добор»), `:1599`, `:1655`, `:1789`.

Тестов, которые подсовывают одиночному пути строку с чужим символом, нет:
`client_test.go` покрывает только алиасы полей и пустой снапшот.

## G2 — P1 — Ошибка «unauthorized» приводит к повторной отправке того же ордера

**Файл:** `go/internal/robinhood/service.go:292-307`

```go

	s.MCP.mu.Lock(); s.MCP.ready = false; s.MCP.session = ""; s.MCP.mu.Unlock()
	return s.MCP.CallToolCtx(ctx, name, args)     // те же args, повторно
```

Это единственная точка, через которую проходят **все** вызовы MCP-инструментов,

`PlaceMarketCfg` и переживает ретрай (`args` не меняются) — но нигде в
проекте нет ни проверки, ни комментария, ни теста, подтверждающего, что MCP-

уважает. Тестов на ретрай изменяющего инструмента нет.

Минимальная защита — не ретраить изменяющие инструменты вовсе, а возвращать
`Ambiguous` и отдавать разбирательство трекеру ордеров, который для этого и
написан.

## G3 — P2 — Гонка при инициализации MCP-сессии

**Файл:** `go/internal/robinhood/mcp.go:79-101`


## G5 — P3 — `ParseCallbackURL` не проверяет, что callback ведёт на наш собственный redirect URI

**Файл:** `go/internal/robinhood/service.go` (`ParseCallbackURL`), тестов нет

**Файлы:** `go/internal/metrics/metrics.go:64-72` против `:439-449`

```go
	if c.initialCapital <= 0 || years <= 0 { return 0 }

	return (math.Pow(finalValue/c.initialCapital, 1/years) - 1) * 100   // нет проверки finalValue

```

## I1 — P1 — Неэкранированный текст ошибки брокера может целиком отменить сообщение о решении T-1

**Файлы:** `go/internal/live/telegram.go:312-332` (`execOutcomes`), `:421-422`,
`:345-355` (`finishSend`), `go/internal/live/transport.go:72`

```go
decision += fmt.Sprintf("• %s ошибка: %s", label, one.Error)   // сырой текст
...
text = "<b>...</b>\n" + strings.Join(decisionLines, "\n")
e.Send(chat, text)      // HTTPTelegram.Send отправляет parse_mode: "HTML"
```

`one.Error` — это `OrderResult.Error`, куда дословно кладут строки ошибок:
HTTP- и MCP-сбои, ошибки разбора JSON, текст валидации от брокера. Например
`robinhood_broker.go:111`:

```go
fmt.Sprintf("order %s by Robinhood: %s", status, robinhoodOrderStatus(detail))
```

где `robinhoodOrderStatus` для любого значения, которого нет в
`MapRobinhoodOrderState` (`robinhood_broker.go:516-535`), проваливается в
сырую строку `state`/`status` брокера. То же в `webull_broker.go:100, 116,
123, 146, 150-151` — `Error` берётся из `err.Error()` и текста ответа.

**Почему это ломается.** Всё сообщение уходит с `parse_mode: "HTML"`
(`transport.go:72`). Telegram Bot API отклоняет **весь** `sendMessage` с
400 «can't parse entities», если в тексте есть неэкранированные `<`, `>` или
непарный `&` вне валидного тега. Текст ошибки брокера — ровно то место, где
такое встречается естественно: «quantity must be < 1000 shares», HTML-страница
ошибки от шлюза, сырой JSON от MCP-инструмента.

`HTTPTelegram.Send` (`transport.go:84-93`) вернёт это ошибкой, а `finishSend`
(`telegram.go:345-355`) запишет её только в `out.Reason` — отдельного алерта
нет. Планировщик всегда вызывает `Aggregate` с `ForceSend: true`
(`scheduler.go:487`), поэтому **сделка на T-1 всё равно исполнится**, а
подтверждение оператору о том, что именно произошло, — то самое, которого
требует рабочий процесс T-1, — молча не придёт. Причём не придёт именно
тогда, когда что-то пошло не так: в успешном сообщении сырого текста брокера нет.

Во всём пакете `go/internal/live` нет ни одного вызова `html.EscapeString`
(проверено grep-ом). `transport_telegram_test.go:21-22` проверяет только, что
`parse_mode == "HTML"`, но не то, что динамический контент экранирован.

# J. SPA

Реконструкция цикла отрисовки (из кода):

```
renderPage(opts):
  gen = ++pageGen
  если не залогинен -> отрисовать логин, выход
  создать оболочку (один раз)
  если !opts.keepCharts -> Charts.destroy()      // сносит ВСЕ живые графики
  page-root.innerHTML = pageHTML()               // ВСЕГДА полная пересборка поддерева
  paintOverlay()
  await afterRender(gen)                         // грузит данные, перевешивает все слушатели
  если (gen !== pageGen) выход                   // защита от устаревшей отрисовки
```

Важное: **цикла перерисовки по таймеру нет**. Приложение полностью событийное,
`renderPage` запускается действиями пользователя; единственный `setInterval` —
обратный отсчёт watch, плюс `requestAnimationFrame` для полноэкранного режима
графика. Поскольку каждый `renderPage` целиком заменяет `innerHTML`, старые
узлы выбрасываются вместе со слушателями — то есть массовой утечки слушателей
здесь нет. Это хорошая новость и она стоит того, чтобы её зафиксировать.

## J2 — P2 — `renderPage({keepCharts:true})` не работает: `Charts.destroy()` пропущен, а контейнеры графиков всё равно уничтожаются

**Файл:** `go/web/js/app.js:3209-3211`, вызовы — `:3097`, `:3134`

`Charts.destroy()` — единственное место, где вызывается `chart.remove()` для

взведена для следующего случая «сохранить оболочку, пропустить полную

**Файлы:** `go/web/js/charts.js:145-153` (`weekKey`), `go/web/js/app.js:2275-2277, 2288, 3634`

Функционально сегодня безопасно: **все** чтения и записи идут через

которого правило и написано. Везде остальное приложение использует явную

`formatDateTimeET()`) — эти календарные места единственные, где для
арифметики над частями даты берётся сырой `Date`.

`applyStoredSplits`/`AdjustOHLC` на новых данных: цены пересчитываются назад по
событиям, которые пользователь считал удалёнными. В интерфейсе никакого
объяснения, почему числа выглядят не так.

## K2 — P2 — `UpsertSplits` пишет пачку без транзакции, в отличие от соседнего `ReplaceSplits`

**Файл:** `go/internal/store/db.go:666-675`

```go
for _, e := range events {
	if _, err := d.SQL.Exec(`INSERT INTO splits ... ON CONFLICT...`, ticker, e.Date, e.Factor); err != nil {
		return err
	}
}
```

`ReplaceSplits` (`db.go:648-664`) свой delete+insert оборачивает в
`tx.Begin()/tx.Commit()`. `UpsertSplits` достижим из трёх HTTP-путей
(`server.go:783`, `:858`, `:1063`), которые могут принести полную историю
сплитов по тикеру одним запросом. Отказ на любом `Exec` после первого
оставляет ранние события уже зафиксированными, а поздние — потерянными:
вызывающий получает одну ошибку на всю пачку, а база остаётся в смешанном
состоянии. Для одного и того же по сути действия — два разных уровня гарантий.

## K3 — P2 — Настоящая ошибка БД неотличима от «не найдено»

**Файлы:** `go/internal/store/db.go:1155-1184` (`GetTrade`), `:1494-1502` (`GetEMAAlert`)

```go
if err := row.Scan(...); err != nil {
	return nil
}
```

Любая ошибка `Scan` — сбой ввода-вывода, заблокированная или повреждённая
база, отсутствующая после неудачной миграции колонка — сворачивается в тот же
`nil`, что и «такой сделки нет». `CloseMonitorTrade`/`CloseTradeByID`
(`db.go:1243`, `:1274`) трактуют `existing == nil` как `"Trade not found"`.

**Следствие на денежном пути:** временный сбой БД при попытке закрыть сделку
выйдет наружу как ошибка формы «404, сделка не найдена» вместо повторяемой
500. Оператор будет искать неправильный идентификатор вместо того, чтобы
повторить операцию.

`GetEMAAlert` — то же самое на уровень выше: `list, _ := d.ListEMAAlerts()`
отбрасывает ошибку, так что реальный сбой запроса выглядит для двух
вызывающих (`httpapi/server.go:1369`, `:1387`) как «алерта не существует».

## K4 — P3 — Проверка срока OAuth-state открывается, а не закрывается при неразобранной метке времени

**Файл:** `go/internal/store/robinhood.go:100-117` (`TakeRobinhoodPending`)

```go
t, perr := time.Parse(time.RFC3339Nano, created)
if perr != nil { t, _ = time.Parse(time.RFC3339, created) }
if !t.IsZero() && time.Since(t) > 15*time.Minute {
	return "", "", fmt.Errorf("oauth state expired")
}
```

Если не разобрался ни один формат, `t` остаётся нулевым, `t.IsZero()` истинно,
и условие `!t.IsZero()` **выключает проверку срока целиком** — state
принимается как ещё действительный. Сегодня не стреляет: `created` всегда
пишется `SaveRobinhoodPending` (`robinhood.go:96`) в `RFC3339Nano`. Но
поведение по умолчанию инвертировано: любое изменение способа заполнения
`created_at` — ручная правка в базе, будущая миграция с другим форматом —
молча снимет пятнадцатиминутную защиту от повторного использования, вместо
того чтобы отвергнуть state.

## K5 — P3 — Статический анализатор «не отбрасывай ошибку записи» не смотрит на сам пакет `store`

**Файл:** `go/internal/store/errcheck_test.go:60-109`

`TestStateWritingDBCallsMustNotBeDiscarded` обходит `internal/live`,
`internal/scheduler`, `internal/httpapi` в поисках отброшенных результатов
методов записи `*store.DB` — но не сам `internal/store`, не `internal/webull`
и не `internal/providers`. Идея защиты отличная; дыра в том, что пакет,
которому она посвящена, из-под неё выведен.

## K6 — Проверено и НЕ баг

- SQL-инъекций нет; конкатенации запросов из пользовательского ввода нет.
- Пропущенных `rows.Close()` и непроверенных `rows.Err()` в
  `db.go`/`live_persist.go`/`robinhood.go` не найдено.
- **Взаимной блокировки на `MaxOpenConns=1` нет:** каждый цикл `rows.Next()`
  в этих файлах проверен отдельно, ни один не выполняет второй
  `Query`/`Exec`/`QueryRow` по тому же хэндлу при открытом курсоре.
- Границы `<` и `<=` на дате сплита в `AdjustOHLC` и `ApplyHolderValue`
  асимметричны, но взаимно согласованы при допущении, что бар, датированный
  днём сплита, уже отражает цену после сплита. Сверено с golden-тестом и
  тестом на реальном сплите GOOGL — не баг.

## K7 — Чего не покрывает ни один тест

`UpsertSplits`, `ReplaceSplits`, `ListSplits`/`AllSplits`/`DeleteSplit`/
`DeleteSplits`, `SaveDataset`/`DeleteDataset` (включая K1), `ListTickers`,
`PruneAutotradeLogs`, `SaveOrderTracker`/`GetOrderTracker`,
`ListEMAAlerts`/`UpsertEMAAlert`/`MarkEMATriggered` и практически весь
`robinhood.go` (`SaveRobinhoodTokens`, `UpsertRobinhoodHealth`, срок в
`TakeRobinhoodPending`, `ClearRobinhoodTokens`) не имеют ни одного прямого
теста. Несколько из них стоят на торговом пути и на пути авторизации брокера.

# L. Системные закономерности: один и тот же баг в разных местах

Отдельная часть задачи была — найдя баг, проверить проект на однотипные.
Ниже пять шаблонов, каждый встречается больше одного раза. Чинить надо
шаблон, а не отдельные точки.

## L1 — Шаблон «ноль означает „не задано“»

Найдено **пять** независимых реализаций:

| место | функция |
|---|---|
| `live/config.go:215-223` | `liveLowIBS` |
| `live/config.go:225-234` | `liveHighIBS` |
| `live/config.go:250-269` | `watchThresholds` |
| `live/autotrade.go:470-481` | `liveLowOrDefault` |
| `live/autotrade.go:482-494` | `liveHighOrDefault` |

Все пять решают одну задачу и все пять решают её так, что законное значение
`0` неотличимо от отсутствия значения. Ни одна не согласована с
`ibs.SanitizeThresholds`, которая явно объявляет `[0, 1]` допустимым
диапазоном и чей тест это утверждает (`ibs_test.go:72`). Подробности — A1, A2, F3.

Проверил, где ещё встречается сам шаблон `!= 0` как признак «задано»:
`store/db.go:1027`, `:1389`, `providers/client.go:347`
(`if v := num(vals["5. adjusted close"]); v != 0`), `backtest/bac4.go:260`.
Последний из них стоит внимания отдельно: скорректированная цена закрытия,
пришедшая от Alpha Vantage как `0`, там трактуется как «поля нет», а не как
испорченные данные, — то же смешение «пусто» и «ноль», только на ценах.

## L2 — Шаблон «личность не совпала — берём первое, что есть»

- `providers/client.go:635` — `pickSnapshotRow` отдаёт первую строку
  снапшота, если ни у одной символ не совпал (**G1, P0**).
- `live/order_parse.go:23-24` — `if first := mapOf(rows[0]); first != nil { return first }`,
  тот же приём на строках ордеров.
- `live/sizing.go:156` — `return first`.

Пакетный путь котировок (`client.go:576-578`) от этого явно защищён, и в нём
стоит комментарий с объяснением, почему. То есть один и тот же автор в одном
и том же файле в одном месте шаблон запретил, а в соседнем оставил — и
соединил их последовательно так, что запрет обходится.

## L3 — Шаблон «NaN доезжает до HTTP-ответа»

`writeJSON` (`httpapi/server.go:234-240`) отправляет заголовок статуса, а
затем **отбрасывает ошибку кодирования**:

```go
w.WriteHeader(code)
_ = json.NewEncoder(w).Encode(v)
```

`encoding/json` на `NaN`/`Inf` возвращает ошибку. Заголовок 200 уже ушёл,
ошибка проглочена, в лог ничего не попадает — клиент получает **200 с
оборванным телом**, и ни у сервера, ни у SPA нет способа понять, что случилось.

Защита от `NaN` в проекте есть, но она **точечная**: собственный
`MarshalJSON` написан ровно для двух типов — `PerformanceMetrics` и
`BacktestMetrics` (`types/metrics_json.go`). Проверено grep-ом: других
`MarshalJSON` во всём дереве нет.

А `types.Trade` (`types/types.go:109-129`) — обычная структура с обычными
`float64`: `EntryPrice`, `ExitPrice`, `PnL`, `PnLPercent`, `Strike`,
`ImpliedVolAtEntry`, `ImpliedVolAtExit`, `OptionEntryPrice`,
`OptionExitPrice`, `Contracts`. Никакой санитизации.

**Готовый маршрут отказа**, собранный из уже подтверждённых находок: H7
(`BlackScholes` делит на `sigma*sqrt(T)` без проверки `sigma == 0`, а
ежедневная переоценка вызывает его без нижней границы волатильности) даёт
`NaN` в `optPrice` → `NaN` попадает в `Trade.PnL` и `Trade.OptionExitPrice` →
список сделок сериализуется `writeJSON` → `json.Marshal` возвращает ошибку →
ответ 200 обрывается на середине, и молча.

То есть H7 — не изолированный дефект расчёта: он смыкается с L3 в отказ,
видимый пользователю как «страница результатов не загрузилась» без единой
строчки в логах.

## L4 — Шаблон «ошибка свёрнута в „не найдено“»

- `store/db.go:1170-1171` — `GetTrade`: любая ошибка `Scan` → `return nil`,
  а вызывающий (`CloseMonitorTrade`, `CloseTradeByID`) трактует `nil` как
  «Trade not found» (K3).
- `store/db.go:1494-1502` — `GetEMAAlert`: `list, _ := d.ListEMAAlerts()`,
  ошибка запроса отброшена, результат тот же.
- `tradingdate/date.go:56-95` — `split`/`utcMidnight`: непарсящаяся дата
  не ошибка, а `(0,0,0)` и 1970-01-01, из которых спокойно строится
  правдоподобный результат (C5).
- `store/robinhood.go:100-117` — `TakeRobinhoodPending`: неразобранная метка
  времени не ошибка, а нулевое время, которое **выключает** проверку срока (K4).

Первые два врут в сторону «данных нет», вторые два — в сторону «всё в
порядке». Второе опаснее: в C5 `DayOfWeek("garbage")` возвращает «четверг»,
а на `DayOfWeek` завязано определение выходных.

## L5 — Шаблон «санитайзер молча чинит вместо того, чтобы отказать»

- `live/config.go:119-160` — `sanitizeAutoTradingConfig` не имеет пути
  возврата ошибки вообще (A3, F4, F5).
- `live/webull_broker.go:64-69` и `live/robinhood_broker.go:339-345` —
  `qty <= 0` превращается в 1 акцию вместо отказа (I2).
- `indicators/indicators.go:130-148` — битый бар (`High < Low`) превращается
  в нейтральный IBS = 0.5 вместо отбраковки (H4).
- `scheduler/scheduler.go:66-74` — `IsShortDay` объединяет импортированный и
  вычисленный календарь по ИЛИ, из-за чего оператор не может **снять**
  неверную пометку (C2).

Соседние подсистемы при этом сделаны наоборот и правильно: пороги тикера
(`httpapi/server.go:1300`) на тот же класс ввода отвечают `400` с текстом,
а `sizeOrder` отклоняет неположительное количество ошибкой раньше брокера.
То есть в проекте сосуществуют две противоположные философии обработки
некорректного ввода, и граница между ними проходит не по важности данных,
а по тому, кто и когда писал конкретный файл.

## Порядок починки

**Сначала — то, что уничтожает данные или деньги:**

1. **E1 (P0)** — `cleanup-server.sh` удаляет боевую БД, сертификаты и датасеты,
   не сказав об этом в предупреждении. Самая дешёвая правка во всём списке
   (убрать одну строку `docker volume prune -f`) и самая тяжёлая цена ошибки.
   Пока не поправлено — скрипт лучше не запускать вообще.
2. **G1 (P0)** — `pickSnapshotRow` может подсунуть чужой тикер в решение T-1.
   Убрать `return first`; пусть несовпадение символа будет ошибкой, как в
   пакетном пути.
3. **G2 (P1)** — не ретраить `place_equity_order` на «unauthorized»;
   возвращать неоднозначность трекеру.
4. **C1 + C2 (P1)** — ранним закрытием считается не тот день, и снять пометку
   из интерфейса нельзя. Две ошибки по три часа, дважды в год.
5. **A1 + A2 (P1)** — пороги IBS: `0` подменяется дефолтом; `highIBS = 0`
   запирает позицию навсегда.

**Затем — то, что искажает результаты:**

6. **H1, H2** — потерянная сделка в `SimulateMargin`; отсутствие ликвидации
   при плече.
7. **L3 + H7** — `NaN` из опционов обрывает HTTP-ответ молча.
8. **I1** — сообщение T-1 не доходит именно тогда, когда что-то сломалось.
9. **J1** — двойной боевой ордер по двойному клику.

**Потом — устойчивость:** F1, I3, K1, K2, K3, D1, D2, E2, E3, G3.

## Замечание о корне

Почти всё тяжёлое в этом списке — не «ошибка в формуле», а **вторая
реализация уже существующего понятия**. Пороги IBS реализованы пять раз,
проверка символа котировки — дважды с противоположными правилами, CAGR —
дважды, win/loss — дважды, санитизация ввода — по двум взаимоисключающим
философиям, сокращённый торговый день — из импортированного календаря **и**
вычисляемого одновременно.

При этом в каждой паре одна из реализаций сделана правильно, а часто рядом
лежит и комментарий, объясняющий, почему так надо. Проект знает верный ответ
на каждый из этих вопросов — он просто хранит рядом и неверный. Инструмент,
который надёжен как молоток, получится не столько из починки перечисленных
точек, сколько из удаления вторых реализаций.
